# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpenDockWatch is a small self-hosted Docker monitoring dashboard: container list/start/stop/restart, live log tailing, a topology ("Flow") graph, and an alerts/events feed. It watches the local Docker daemon and any number of remote hosts over SSH. See `README.md` for the full feature list and `CONTRIBUTING.md` for the release process.

## Commands

```
npm install                                 # deps
cp .env.example .env                        # then fill in AUTH_USER/AUTH_PASS_HASH/SESSION_SECRET
cp config/hosts.example.json config/hosts.json
npm run hash-password -- "your-password"    # generates a bcrypt hash for .env's AUTH_PASS_HASH

npm run dev                                  # node --watch server/index.js, http://localhost:3000
npm start                                    # plain node server/index.js

npm test                                     # syntax-check every server/public-js/scripts file, then node --test
node --test test/docker.test.js              # run a single test file
node --test --test-name-pattern="parseByteString" test/docker.test.js   # run one test by name

npm run lint                                 # eslint .
npm run format                               # prettier --write .
npm run format:check                         # prettier --check .  (what CI runs)

docker compose up -d --build                 # run OpenDockWatch itself in a container
```

CI (`.github/workflows/ci.yml`) runs `npm run lint && npm run format:check && npm test`, plus a parallel job that builds the image. Always run the same three before considering a change done.

**The image builds are cached, and which ones are is a deliberate split.** A cold build was measured at **~107s on a pruned builder**, nearly all of it `apk add python3 make g++` plus better-sqlite3 compiling from source — verified that it really does compile, by building without the toolchain and watching `prebuild-install` fail through to a node-gyp error, so the Dockerfile's comment about there being no musl prebuild is accurate. With a restored layer cache and only the source changed — the shape of a normal CI run — it drops to **~8s**. The two _verification_ builds (`ci.yml`'s `docker-build`, and the one inside `release.yml`'s prepare job) therefore use `cache-from`/`cache-to: type=gha` with `outputs: type=cacheonly`, since nothing consumes the image and it only has to build. **`mode=min`, not `mode=max`** — 82MB of cache against 200MB, and min _still_ reports `CACHED` for the deps stage's `apk` and `npm ci`, which reads wrong (min exports only the final image's layers) but is what buildkit actually does: it records enough of the chain for `COPY --from=deps` to hit without the intermediate stage's layers being exported. Both modes restored in the same ~8-10s, so `max` bought nothing for 118MB more cache. **The build that publishes to Docker Hub (`release-finalize.yml`) is deliberately left uncached**: it is the only build anyone pulls, it runs a handful of times a year, and GitHub evicts caches unused for 7 days, so it would usually be cold regardless.

## Code comments

A comment block attached to a function/method (or a magic number/config constant next to one) is capped at 3 lines. If the full rationale doesn't fit, keep the 3-line version terse and load-bearing, and put the rest here in CLAUDE.md under the relevant module instead of letting it spread across the codebase - this file is already the canonical home for the "why" behind most non-obvious decisions in this repo, so a comment can point here rather than repeat it.

There is no build step for the frontend — `public/js/*.js` is served as-is via native ES modules (`<script type="module">` in `public/index.html`). Most of it (`app.js`, `public/js/components/**`) is only syntax-checked, not unit-tested, since it's Vue/Cytoscape UI code with no meaningful behavior outside a browser - but pure logic with no DOM/cytoscape dependency has no such excuse: `format.js` (ANSI parsing, level detection, byte/rate formatting), `graph.js`'s `buildElements`/`aggregateGroups` (graph-building), and `public/js/lib/spark.js`/`lib/logStream.js` (sparkline coordinate math and the EventSource/buffering factory shared by `LogViewer`/`ContainerDetail`'s log streams - `EventSourceImpl` and the flush `schedule` are injectable specifically so this is testable under `node --test` with a stub source, without a browser) are all unit-tested. `test/format.test.js`, `test/graph.test.js`, `test/spark.test.js`, and `test/logStream.test.js` `import()` their module directly (dynamic import, since `require()` can't load an ES module - `node:test`'s `before()` hook loads each once and shares it across that file's tests). When pulling more logic out of a component in `public/js/components/`, prefer landing it in `public/js/lib/` if it's pure - that's the difference between it being tested and not.

## Architecture

**The server shells out to the `docker` CLI** (`server/docker.js`, via `child_process.execFile`/`spawn`) rather than talking to the Engine API or a Docker SDK. Every function takes a `host` object and prefixes its args with `-H <dockerHost>` when set (`hostArgs()`); a `null`/absent `dockerHost` means the local socket. This is _why_ remote hosts work at all: `-H ssh://user@host` is resolved by the Docker CLI itself using normal SSH key/config, so there's no separate tunneling code to maintain. Hosts are defined in `config/hosts.json` (gitignored, copy from `hosts.example.json`), each with an optional `edges: [{from,to,label}]` list for relationships Docker itself can't see. Hosts can also be added/edited/removed live from the Settings panel (admin-only, `/api/settings/hosts`) — `server/hosts.js`'s `saveHosts()` rewrites the file and the route calls `metricsCollector.addHost/removeHost` and `eventWatcher.addHost/removeHost` for just that one host, so a new SSH host starts being monitored immediately with no process restart (edits are a `removeHost` + `addHost` pair rather than an in-place update, since reconnecting is simpler than diffing what changed). The image's `/etc/ssh/ssh_config.d/opendockwatch.conf` (written by the `Dockerfile`) turns on SSH connection multiplexing (`ControlMaster`/`ControlPersist 10m`) globally, so the several `docker` calls each remote host gets per 5s poll ride one persistent SSH connection instead of opening their own — pure infra, no code involved, since the CLI just shells out to system `ssh`. `checkHost`/`testHostConnection` (the latter backing Settings' "Test connection" button, surfacing real `ssh`/`docker` stderr instead of a boolean) get a longer timeout for SSH hosts than the local-socket default (`checkTimeoutMs()`), since that's the one call that has to pay a slow link's connection-setup cost before multiplexing makes everything after it cheap.

**`server/logger.js`** writes structured single-line audit/debug events (`[opendockwatch] [LEVEL] event key=value ...`) to stdout/stderr - picked up by `docker logs` automatically and by the app's own Log Viewer level filters. Nothing in the server writes to `console` directly except `logger.banner()`, the ASCII boot banner (art, not an event - it's the visual marker for where a restart begins when scrolling back through `docker logs`, and `app.started` carries the same data as a real event immediately after). A failure that only reaches `console.error` is invisible to the Log Viewer's level filters, which is the entire reason this module exists, so new error paths go through it. Never log secrets: `alerts.webhookScheme()` is the only sanctioned way to put a webhook URL in a log line (`discord://…`), shared by `alerts.js` and `index.js`'s settings route so the redaction can't drift between them.

**What gets logged, and the rule for adding more.** The log's job is to let someone reconstruct what the app did without attaching a debugger, so it covers **state transitions and discrete operations, never per-poll steady state** - a line every 5s per host would bury the ones that matter. Currently: lifecycle (`app.started`/`app.shutdown`), auth success/failure, every container action as a **pair** (`container.<action>.requested` before the CLI call, `container.<action>` with `tookMs` after - `docker stop` can sit through its full 10s SIGTERM grace, and logging only on completion left a pressed button invisible until it finished), log-stream and event-stream open/close with `heldSec` (each one holds a `docker logs -f` child and one of the browser's ~6 connections - see the connection budget above), `logs.download` (container logs carry secrets, so exporting them is audit material), host watch start/stop, `docker events` stream start/restart-backoff/stop, host reachability in **both** directions (`host_unreachable` fires an alert, `host.reachable` only logs - nobody wants a webhook for good news, but "did it come back?" has to be answerable), webhook delivery success as well as failure, `alert.muted` for a suppressed alert, `db.pruned` with per-table row counts when the hourly prune actually deletes something, and every failure path. Steady-state polling stays silent by design.

**Pure parsing/graph-building functions are exported from `server/docker.js`** (`parseByteString`, `parseLabels`, `parseHealth`, `networkEdges`, `dependsOnEdges`, …) specifically so `test/*.test.js` can unit-test them directly without mocking `child_process`. When adding docker-CLI-output parsing, keep the parsing pure and separate from the function that actually shells out, and export it.

**Three long-running background jobs.** The first two are started by `server/index.js` on boot; the third is started per host by `metricsCollector` itself, since it exists only to feed it.

- `eventWatcher.js` — one persistent `docker events` process per host (auto-restarts with exponential backoff, capped at 30s). **The restart hangs off `'close'`, never `'exit'`, and that is not interchangeable**: Node emits `'exit'` only for a child that actually ran, so a child that never spawned at all — `docker` off PATH, or an `EAGAIN`/`ENOMEM` fork failure under process pressure — emits `'error'` then `'close'` and no `'exit'` whatsoever (verified on Node 22). Keyed on `'exit'`, that left the host with **no event stream for the life of the process**: no `container_crashed`, `crash_loop` or `unhealthy` alerts, one `events.stream.failed` line, and nothing to bring it back. Nothing else catches it either — `watchdog.js` measures the poll loop, and a host with a dead event stream polls perfectly normally. `'close'` fires in both cases and always follows `'exit'`, so it needs no second handler. `test/eventWatcher.test.js`'s `endChild(child, {spawned})` helper exists to keep tests ending children the way Node actually ends them; asserting on a bare `emit('exit')` is what let this ship. The pending restart is tracked on the watcher's state so `removeHost` can cancel it, and the restart itself re-checks that the map still holds _that same state object_ before reviving anything: an edit through Settings is a `removeHost` + `addHost` pair, so a backoff elapsing after one would otherwise restart the old watcher against the new entry and leave two streams running for one host - every event inserted, published and alerted on twice, with the newer child orphaned where no `removeHost`/`stop` can reach it. Each parsed event line fans out to three places through `ingestEvent`: `db.insertEvent` (persistence), `broadcaster.publish` (live SSE push to the Activity tab), and `alerts.handleEvent` (rule engine). This is the single ingestion point for all event-driven alerts (`container_crashed`, `crash_loop`, `unhealthy`). **`ingestEvent` must never throw**, and that is the reason it exists as its own function rather than as the body of the loop: it runs inside the child process's stdout `'data'` handler, an exception out of an EventEmitter listener is an `uncaughtException`, and `index.js` calls `process.exit(1)` on those — so one `SQLITE_BUSY` on one event line would end monitoring for every host, which is precisely the trade `unhandledRejection` is deliberately not making three paragraphs up. The `try`/`catch` is per event so a bad line doesn't cost the rest of the chunk it arrived in either, and it's exported purely so `test/eventWatcher.test.js` can assert the swallow-and-log contract by mocking `db.insertEvent`/`alerts.handleEvent` to throw, without spawning a real `docker events`. Note that this is about _thrown_ errors only: writing to an SSE response whose client has gone is not one of them — `res.write` on an ended or destroyed `ServerResponse` returns `false` and drops the data rather than throwing or emitting, verified on Node 22 for socket-destroy, write-after-`end`, and a client RST mid-burst, so `sse.js` needs no guard around its write.
- `metricsCollector.js` — polls every host every `POLL_MS` (5s) for containers/info (stats come from the stream below), plus disk usage on a **derived** interval (`nextDiskDelay`, floor 60s); keeps an in-memory snapshot per host (`getSnapshot(hostId)`, used e.g. to avoid an extra docker call just for a container's name in audit logging) and writes samples to sqlite for history charts. Also feeds the threshold-based alerts (`container_cpu`/`container_mem`/`host_cpu`/`host_mem`/`docker_disk`, `handleSample`/`handleHostSample`/`handleDiskUsage` in `alerts.js`). **Reachability is derived from the poll's own calls, not probed separately** — `checkHost` (`docker version`) used to be `await`ed serially in front of every poll, which is a whole extra round trip on an SSH host to re-answer a question the three calls behind it answer for free. It now runs only as a **gate for a host already believed down**, and that asymmetry is the entire design: against a host that is up the probe is pure overhead, while against one that is down a single process failing fast beats three each waiting out their own timeout, so a host stuck offline never advances past the gate. The three calls go through `Promise.allSettled`, not `Promise.all`, because reachability now depends on them and _"one of the three failed" is not the same fact as "the daemon is gone"_: only all three failing marks the host unreachable, and anything less is a failed poll on a host that is demonstrably still answering — firing `host_unreachable` for that would be a worse answer than the probe used to give. A partial failure therefore leaves the snapshot on the previous poll's values exactly as the old single `try`/`catch` around all three did, since half a poll would diff this poll's stats against themselves and write an instant of history that never happened. `markUnreachable` exists because that outcome has three call sites and the alert has to fire exactly once per poll; `docker.js` gained `noteHostFailure`/`noteHostReachable` so `lastCheckError` keeps answering "why is this host down?" whichever path decided it was. `pollHost` is exported purely so `test/metricsCollector.test.js` can drive those branches, and the docker calls it makes go through the module object rather than destructured bindings so they can be stubbed. **Only the calls that actually reached the daemon count towards reachability**, which is why `pollHost` tracks that rather than just reading the settle results: two of the three are routinely answered from memory — stats from `statsWatcher`'s stream, info from `docker.js`'s `HOST_INFO_TTL_MS` cache — and a value served from a buffer proves nothing about the host still being there. Counting one would leave a dead host looking reachable for as long as they stayed warm. `listContainers` is always live, so the live set is never empty. **`docker info` is cached for the same reason it was worth caching at all**: CPU count, total memory, server version and hostname are fixed for a daemon's lifetime, and the two container counts — the only fields that move between polls — are recomputed each poll by `containerCounts` from the `docker ps` output already in hand, so caching costs no freshness. A TTL rather than "once, forever" so a VM resize or a daemon upgrade still lands. Note this shows up as **spawn count, not latency**: the three calls run in parallel, so `pollLastMs` is unchanged — measured at 9 `docker info` processes in 40s before and 2 after.
- `statsWatcher.js` — one persistent `docker stats` process per host, replacing the `docker stats --no-stream` call the poll used to make. **That one call was the poll cycle**: measured at 1.3-2.0s against a _two-container_ daemon, because the CLI has to collect a whole sample cycle before it can print a CPU percentage and only then exits — a third of the poll interval, and one of `run()`'s 12 concurrency slots held for all of it. Same restart/backoff/identity-check machinery as `eventWatcher` above and for the same reasons, and the same never-throw contract on the stdout handler. End to end on one machine, same daemon and same `hosts.json`, `app.vitals`' `pollLastMs` went from a steady **2081ms to 80ms**. Four things about it are load-bearing. (1) **`docker stats` draws a table with cursor-control escapes even when its output is a pipe** — each refresh is `ESC[J ESC[H <rows> ESC[H <rows> ESC[K`, verified byte-for-byte — so a row arrives with an escape glued to the front of the JSON that `JSON.parse` rejects outright. `parseStatsLine` strips them and is pure/exported so that survives without a daemon. It does not try to reconstruct redraw _frames_: nothing here needs to know where one ends. (2) **`getSamples` returns a copy, never the live map.** `pollHost` mutates what it gets (`Object.assign(s, computeIoRates(...))`) and diffs it against the object it kept from the previous poll — aliasing would make those the same object, so every cumulative counter would equal itself and every I/O rate would silently be zero. (3) **It returns `null`, not `{}`, when it has nothing usable** — no rows yet, or no row for `STALE_SAMPLES_MS` (30s) — and `pollHost` falls back to the one-shot call. A stream that is up but no longer printing would otherwise freeze the dashboard on numbers that never advance, which is worse than paying for the slow call; the same reason `exit` clears the samples rather than keeping them warm across a restart. (4) **`docker stats` only reports running containers**, so `retainContainers` prunes against the running set from the same poll's `docker ps` — exactly like `alerts.retainContainers` beside it — or a host that cycles containers accumulates an entry per id it has ever seen. `statsLive` on the vitals line is the count of hosts actually being served from a stream: below `hosts`, someone is paying the one-shot cost on every poll.

**Staying responsive is a design constraint, not an optimization** — the failure this app has to avoid is the one where it's still running but unusable, since that's the one a container restart is the only cure for. Three rules follow from it, and new code has to keep them. (1) _Never leave a request unanswered._ A browser allows ~6 connections per origin over HTTP/1.1 and this app permanently holds some of them open for its SSE streams, so a request that hangs is a connection slot lost — enough of them and the tab can't issue any request at all, including the ones a reload needs, and that state outlives the server recovering. `requestTimeout` in `index.js` answers 504 rather than hanging (SSE routes exempt, matched by path suffix; a late real response is dropped rather than thrown, since a second send would otherwise destroy an already-answered connection), `api.js` puts an `AbortSignal.timeout` on every `fetch`, and `docker.js`'s `run()` escalates SIGTERM→SIGKILL so a CLI blocked on a wedged daemon socket can't leave its promise unsettled forever. (2) _Don't multiply work per viewer._ The collector already has containers/stats/info/reachability/hostname in its snapshot; routes serve from it rather than shelling out per request — `/containers`, `/stats` and `/info` all do (`?fresh=1` on `/containers` is the one opt-out, for the refetch right after a start/stop where up-to-`POLL_MS` staleness is visible) — and **the poll loop asks for all of it in one request, not four**: `GET /hosts/:id/dashboard` returns `{containers, stats, metricsHistory, alerts}`, which is exactly what `app.js`'s cycle used to `await` one after another, at a cost of four round trips, four session-store lookups and four turns of the ~6-connection budget per open tab every `POLL_MS`. Measured in a real browser over ~4 cycles: **18 `/api` requests → 4 in List view, 25 → 10 in Flow**. The four fields are built by `containersFor`/`statsFor`/`hostHistoryFor` plus `db.getAlerts`, and those exist as functions specifically so the bundle cannot drift from the individual routes it duplicates — `test/index.test.js` asserts field-by-field parity against each one. **Those parity assertions need seeded rows to mean anything**, which is why the test inserts host metrics spanning the 1h boundary and alerts across two hosts: against an empty database `metricsHistory` and `alerts` are both `[]` no matter what the bundle asked for, and mutation-testing confirmed that pointing the bundle at the 24h range and dropping its host scope both survived the entire suite until those rows existed. **Topology is deliberately not in the bundle** even though the poll fetches it too in Flow view: it is the one part that can still shell out (its label/mount metadata is cached against the container-id set, which recreating a container invalidates), so folding it in would put a docker call behind four fields that are otherwise pure memory and make the whole response only as reliable as its slowest part. It stays its own route and `refresh()` runs the two through `Promise.all` instead of in series, so Flow view costs two requests and one round trip rather than five and five., `getTopology` caches its three label/mount `docker ps` calls against the container-id set (they can't change without the container being recreated under a new id), and `run()` caps concurrent CLI processes. Client-side, the poll loop is a chained `setTimeout` and never `setInterval` — a cycle awaits five or six requests, so on a slow host an interval starts a second cycle before the first finishes and they stack — plus a backoff on failure and a full stop while the tab is hidden. Anything long-lived that reconnects needs a budget too: `logStream.js` gives up after repeated disconnects with no line in between, since EventSource retries forever and each retry spawns a `docker logs` server-side. **The ~6 connections are a budget to be spent deliberately, and log streams are what spend it** — the Logs tab alone can hold four. So a stream only runs in the views its component is actually part of: `app.js`'s `detailPanelVisible` gates the detail panel (and `setView` closes the bottom Log Viewer) to List and Flow, the Logs tab owns its panes, Activity owns its event stream — worst case four, never six, leaving two for the poll loop. Streams also suspend themselves after `HIDDEN_SUSPEND_GRACE_MS` in a backgrounded tab (`logStream.js`), returning both the connection and the server-side `docker logs -f` child; the grace exists because resuming re-tails and therefore resets the pane, which is wrong for a two-second tab switch and right after a real absence. Raising `MAX_OPEN_LOG_PANES` spends that margin directly. (3) _Recover without a human._ `watchdog.js` measures how long since `metricsCollector` last _completed_ a poll — deliberately a property of the loop, not of Docker, since an unreachable host still completes its poll — and reports unhealthy on `/healthz` then exits after a grace period. The exit is the part that matters: Docker never restarts a container for being unhealthy, and `restart: unless-stopped` only reacts to the process exiting, so self-exit is the only path back. It's injectable (both clocks, `exit`, timer) and unit-tested in `test/watchdog.test.js`. **Recovery time is `STALE_MS + EXIT_AFTER_MS` and a user experiences it as one number**, so treat it as one: detection stays conservative at 120s (24 missed polls, ~3x the worst legitimate cycle of a timing-out SSH host at 20s + the 5s SIGKILL grace + a full 15s semaphore queue wait), but the grace after that is 120s rather than the 600s it started at. Once staleness is confirmed there is nothing left to wait for - a restart costs ~10s of `start-period` and loses nothing, since the db is WAL and the history is already written - and 13 minutes of a frozen dashboard is not meaningfully more self-healing than 4. `test/watchdog.test.js` asserts the sum stays under 5 minutes, because this is the kind of constant that drifts upward one cautious commit at a time. (4) _Leave a trace, especially of a stall._ This was learned the expensive way: a real 220s outage left **nothing whatsoever** in the log between the two sides of it, and was only provable afterwards by finding the matching gap in `host_metrics`. So `index.js` emits **`app.vitals` on a fixed interval** (`VITALS_INTERVAL_MS`, 60s, 0 to disable) and most of its value is that it's periodic - a gap in the heartbeats is itself the evidence, and the lines either side show the state going in and coming back out. It carries only live counters that nothing else reports: `rssMb`/`heapMb`, the watchdog's `lagMs`, `pollLastMs`/`pollMaxMs`/`pollSlow` from `metricsCollector.takePollStats()` (`maxMs` resets on each read, so a rising floor across consecutive lines is the collector degrading, not one bad poll hours ago pinning the number forever), `dockerActive`/`dockerQueued` from `docker.poolStats()`, `statsLive` from `statsWatcher.liveCount()` (read against `hosts`: below it, some host's stats stream is down and that host is paying 1.3-2.0s for the one-shot `docker stats` on every 5s poll - the stream's own restart lines say so as it happens, this is what says it is _still_ happening an hour later), and `logStreams`/`sseClients` - the open/close pairs elsewhere each describe one stream, and "how many are held right now" is not something you can replay from them while the UI is hung. **`dbLastMs`/`dbMaxMs` sit next to `lagMs` on that line for a reason**: better-sqlite3 is synchronous, so every write is event-loop time, and lag plus a long worst-write in the same window means the storage was the cause, while lag without one means it was something else - equally worth knowing, and previously unanswerable. `db.js`'s `timed()` wraps only the two writes big enough to matter (the per-poll transaction and the hourly prune, which is a full table scan); timing every single-row statement would cost more than it tells you. Around it sit narrower signals, each chosen so it fires on a real problem and not on normal work: `db.write.slow` (`SLOW_DB_WRITE_MS`, 250ms); `metrics.poll.slow` (`SLOW_POLL_MS`, 15s) is what precedes watchdog staleness, since the watchdog only speaks once the loop has stopped entirely; `request.slow` (`SLOW_REQUEST_MS`, 5s) uses **per-route thresholds** via `slowThresholdFor`, because a `docker stop` waiting out SIGTERM routinely takes ten-plus seconds while working exactly as designed and `docker system df` was measured at 40-75s cold - those are held to their own timeouts instead; and `docker.queue.saturated`/`docker.queue.drained` bracket an _episode_ of concurrency-limit saturation rather than logging per queued call. Four more close gaps where the app already knew something and threw it away: **`host.unreachable` carries the reason** — reachability is a boolean, so "became unreachable" arrived with no cause at all, and timed-out / host-key-verification-failed / permission-denied / daemon-not-running call for completely different responses; `docker.js` keeps the last failure per host in `lastCheckErrors`, written by `noteHostFailure` from both the probe and the ordinary poll calls (the latter is now the usual source, since a reachable host is never probed), and `markUnreachable` reads it on the reachable→unreachable transition only, never per poll. **`auth.rate_limited`** exists because the limiter tripping is the one event that _silences_ the log: once it trips, requests stop reaching `verifyLogin`, so `auth.failure` stops too and a sustained brute-force reads as though the attacker gave up. **`app.shutdown.complete`** reports `endedBy: 'drained'` vs `'timeout'` — the 5s forced path means streams were still held, which is the connection-budget problem surfacing at the one moment it is easy to observe. **`alert.webhook.backlog`** gives the retry queue a depth, since the per-alert retry lines each describe one alert and never say they are the same growing queue. `eventWatcher.takeIngestCount()` feeds `events` on the vitals line for the same reason the queue aggregates: a container in a restart loop is a real source of synchronous writes, and logging the flood would _be_ the flood.

**`POST /api/client-error` is the one route deliberately exempt from the admin gate, and the exemption is enforced rather than assumed.** The frontend compiles its Vue templates in the browser, so a broken render is a blank page with a completely healthy server log — "the site is broken" and "the server is fine" both true, with nothing reconciling them unless someone opens devtools. `app.js`'s three global handlers (`window.onerror`, `unhandledrejection`, `app.config.errorHandler`) and `mounted()`'s `bootError` path mirror to this route so client failures land in `docker logs` with everything else. It has to work for a **viewer** — a viewer's browser breaks exactly like an admin's — so `test/index.test.js`'s structural admin-gating check carries an `ADMIN_EXEMPT` map whose entries record their justification and, crucially, fail if the route they name no longer exists, so a removed route can't leave its exemption behind to silently cover whatever later takes that path. Two properties qualify a route for it: no state change, and a real reason a non-admin must reach it. **The client-side caps are the load-bearing part, not the server's rate limiter.** A render error inside a watcher fires every frame, and each report would take one of the browser's ~6 per-origin connections — the same budget the poll loop and log streams live on — so an unbounded beacon would cause the exact hang it exists to diagnose. `reportOnce` dedups on kind+message+source+line and stops entirely after `MAX_CLIENT_ERROR_REPORTS` (5) per page load, **checking the cap before touching the dedup set** so a loop throwing distinct messages can't grow that set forever after reporting has stopped. That cap also bounds recursion by construction. `api.js`'s `reportClientError` is deliberately not `apiFetch`: it must never redirect on 401, never throw (anything thrown lands back in the handler that called it), and never retry; `keepalive: true` lets a boot-failure report survive the navigation that often follows it. Verified in a real browser — clean boot reports nothing, two identical errors report once, twelve distinct ones stop at five. **Aggregate a sustained condition, don't log an event per occurrence** - that rule now covers the queue, `watchdog.lag_summary`, and `disk_usage.poll.failed`'s failure count, and the reason is that a few hundred identical lines bury the one thing that was worth reading. Note `active` is deliberately absent from the queue lines: reaching that path means every slot is held, and `release()` hands a slot straight to a waiter rather than decrementing, so it is `MAX_CONCURRENT` by construction.

**`clientError` and `server.timeout` are both traps, and `index.js` documents them in place.** Taking over `clientError` means taking over the _response_, and it is not always a 400: `headersTimeout` and `requestTimeout` (both set) surface there as `ERR_HTTP_REQUEST_TIMEOUT`, which Node's own default answers **408** - measured, not assumed. `clientErrorStatus` is exported and unit-tested precisely because the handler itself lives inside the `require.main === module` block and can't be. The handler also declines to write when `!socket.writable || socket.bytesWritten > 0`, matching the default: otherwise `socket.end()` is a silent no-op that reads like a reply was sent, or corrupts a partly-written one. **There is deliberately no `server.on('timeout')` listener and no `server.timeout`** - it defaults to 0 in Node ≥13 so a listener alone can never fire, and merely attaching one _suppresses_ Node's default socket destruction, so enabling it to "fix" that would leak every timed-out socket unless the handler destroyed them itself. It also can't be enabled safely here at all: `server.timeout` is whole-socket inactivity and this app's SSE streams are idle by design between 30s heartbeats.

**The watchdog reads two clocks, and the difference between them is load-bearing.** `now` (wall) measures staleness, since `lastPollCompletedTs` is a `Date.now()`; `monotonic` (`process.hrtime`) measures event-loop lag and the resume grace. They are separate because a suspended host - laptop sleep, a paused WSL2/Docker Desktop VM, this app's usual home - stops the poll loop for hours with nothing whatsoever wrong with it, and `CLOCK_MONOTONIC` does not advance across a suspend while the wall clock does. A tick whose wall delta exceeds its monotonic delta by `SUSPEND_JUMP_MS` is therefore a resume, not a stall: lag is recorded as zero, `staleSince` is cleared, and `RESUME_GRACE_MS` of quiet follows so the collector's own timer can turn over before staleness counts again (`status()` honours that grace too, or waking the machine would flap the container unhealthy for a few seconds every time). A genuinely starved VM advances both clocks together and is still caught normally. Getting this wrong is expensive in both directions, and more so now that the exit grace is two minutes rather than ten.

**Event-loop lag has two thresholds because one number can't do both jobs.** It never triggers the exit on its own (a one-off spike during the hourly prune is normal); it exists because better-sqlite3 is synchronous, so a slow bind-mounted volume can block the event loop long enough to stall the HTTP server. A single stall past `LAG_WARN_MS` (2s) gets its own line. Everything past `LAG_NOTICE_MS` (250ms) is accumulated instead and flushed once a minute as `watchdog.lag_summary` (`stalls`/`maxMs`/`totalMs`/`blockedPct`), with the window opening on the first stall worth noticing so a healthy host logs nothing at all. The summary exists because the single 5s threshold it replaced recorded **nothing** on a host that was losing 90-220s an hour to stalls that were each individually under it - the only visible symptom was `metricsCollector`'s hourly `setInterval` firing three minutes late, which is not something anyone goes looking for. If a report starts "it freezes sometimes", `watchdog.lag_summary` is the first thing to read. `uncaughtException` exits for the same reason; `unhandledRejection` only logs, since one failed docker call or db write shouldn't take monitoring down for every host.

**`alerts.js`** is the rule engine plus webhook delivery. Every alert setting (webhook URL/format, CPU/mem/disk thresholds) follows the same pattern: an `.env` default, overridable from the DB via the admin Settings UI (`PUT /api/settings/...`), with the DB value always winning when present — even an explicit empty/0 to deliberately disable something `.env` configured. See the README's Alerts section for the full rule table and webhook URL-scheme routing. **Per-container overrides** live in the `container_alert_rules` table (`server/db.js`): an ordered, first-match-wins list matched by container name (case-insensitive substring) or an exact compose project, optionally scoped to one host. `resolveContainerConfig({hostId, containerName, composeProject}, ctx)` walks it — the matched rule's non-null fields override the global threshold config for that call, with anything it leaves null still inheriting the global value, and its `mutedRules` naming which of `container_crashed`/`crash_loop`/`unhealthy` are suppressed for that container. No match at all (the common case) returns the global config untouched. **The reads it needs are hoisted to one per poll, not one per container**, via `alertContext()` (`{global, rules}`): `metricsCollector.pollHost` builds one and passes it to every `handleSample` in that poll, the same collect-then-act shape the metrics transaction above already uses. Per-container was measured at ~30µs a call with 10 rules configured — 6ms of synchronous event-loop time every 5s at 200 containers, four times what batching the metrics write saved, and growing with rules × containers × hosts. It's built lazily (skipped entirely when every container on the host is label-disabled) and `ctx` is optional, so the event path and the tests still resolve per call. On the event side that's the right granularity anyway: `mutedByRule` runs only on a `handleEvent` call actually about to fire, never once per `docker events` line, and it **logs an `alert.muted` line when it suppresses one** — `fire()` always leaves an `alert.fired` trace, so without that a muted alert would be the one outcome with no record at all to answer "why didn't this alert?". This is deliberately separate from the `opendockwatch.alerts=off` Docker label, which stays exactly as narrow as before — checked first, unconditionally, before any rule lookup, and still only gates `handleSample`'s threshold rules; muting an event rule per container goes through the rules table instead of widening what the label means. `composeProject` reaches both call sites cheaply: `docker.js`'s label parsing already put it on every container object (forwarded into `handleSample` via `metricsCollector.js`'s `alertSamples.push`), and `docker events`' `Actor.Attributes` carries the same label set (`eventWatcher.js`'s `parseEventLine` reads it alongside `name`/`exitCode`), so neither needs an extra docker call.

**The `alerts` table is also the cooldown store, which is why the Activity tab's alerts-column Clear button is a soft delete.** `shouldFire` suppresses a repeat for `COOLDOWN_MS` (10 min) by reading `db.getLastAlertFireTs`, which is nothing more than the newest matching row in `alerts` — so a hard `DELETE` there does not clear a list, it **re-arms every rule on that host**. The breach state that decides whether a threshold rule wants to fire lives in a different table (`alert_breaches`) and is untouched by a clear, and `checkSustained` returns true on _every_ sample once a breach is past `sustainMinutes`, so the cooldown is the only thing standing between an ongoing breach and an alert every 5 seconds. Clearing a still-breaching host therefore re-inserted the alert on the next poll and **re-sent its webhook**, with the list repopulating in front of the user who just emptied it; `docker_disk` was worse in kind, since its comment records that it has no sustain window and relies on the cooldown alone. `db.clearAlerts` instead stamps `cleared_at` and **every other alerts query filters on `cleared_at IS NULL`** — list, open counts, per-container counts, ack/ack-all, and the webhook retry sweep, so the clear is invisible everywhere a hard delete was — with `lastAlertFire` as the single deliberate exception. Rows leave for real on `pruneAlerts`' ordinary retention sweep. If a new query against `alerts` is added, it needs that filter unless it is answering "when did this last fire?".

**The events column's Clear is a soft delete for the same reason, and its blast radius was wider.** `events` is not just the Activity feed: `countRestartsSince` backs the `crash_loop` rule (3 restarts in `CRASH_LOOP_WINDOW_MS`) and `getRestartCountsByContainer` backs both the List view's `restartCount1h` and `prometheus.js`'s restart gauge. A hard delete therefore emptied a list _and_ silently reset crash-loop detection — a container actually in a restart loop needed three fresh restarts before it could be caught again — walked the restart column back to 0 for an hour, and made a Prometheus counter go backwards, which breaks `rate()` in whatever is graphing it. So `db.clearEvents` stamps `cleared_at` and **only `getEvents` filters on it**; the two restart counters deliberately do not, because they answer what a container did rather than what the tab is showing. The same rule as above applies to a new query against `events`: filter, unless the question is about the container's actual history. **Both clears also write an `audit_log` row** (`auditClear` in `index.js`, action `clear_alerts`/`clear_events`, no container): `cleared_at` records when a clear happened, and the audit log is the only place that records _who_ — it is also the one table a clear doesn't touch. Those rows carry a `container_id` of NULL and an action outside `('stop','start','restart')`, which is what keeps them out of `countManualStopsSince`/`countManualStartsSince`, where a stray match would suppress a real `crash_loop` or `container_crashed` alert. Note that nothing in `public/js` reads `GET /api/audit` — the audit log is an API-and-database record, not a screen. **The two clears scope their host differently and now answer an unknown one the same way**: events takes a path segment and gets `requireHost`, alerts takes `?hostId=` and gets `requireHostQuery`, which repeats the same 400-then-404 pair for a query param (and sets no `req.odwHost`, since these routes hand the id to sqlite and never to the docker CLI). Without it a typo'd host id came back `200 {count: 0}` — "cleared nothing" and "no such host" are not the same answer. `POST /alerts/ack-all` still takes the unvalidated form and is the remaining candidate for that middleware. Labels follow the same symmetry: the buttons are **Clear alerts** and **Clear events**, not "Clear activity" — the tab itself is Activity, so that name read as though it emptied both columns. **Its index needed the same care**: right after a Clear every retained row is cleared, so the plain `(host_id, ts)` walk that `getEvents` was given an index for in the first place would traverse the host's entire history to return an empty page — hence the third, partial `idx_events_host_ts_active ON events (host_id, ts) WHERE cleared_at IS NULL`, which `test/db.test.js` pins with an `EXPLAIN QUERY PLAN` assertion. That index is created **after** the `ALTER TABLE` block rather than inside the schema block, and that placement is load-bearing: on an upgrading database the schema block runs against a table that does not have `cleared_at` yet, so a `CREATE INDEX` naming it there throws at module load and takes the app down on the first start after the upgrade.

**The Settings panel** (`public/js/components/`) is a tab-strip shell (`SettingsPanel.js`) over five independent sections — `SettingsGeneral.js`, `SettingsWebhook.js`, `SettingsThresholds.js`, `SettingsContainerRules.js`, `SettingsHosts.js` — each owning its own fetch/save/error/status state rather than one file juggling five prefixed copies of the same shape (the pre-split version's `webhookSaving`/`thresholdsSaving`/`hostsSaving` etc.). Tabs swap via `v-if`, not `v-show`: each child is a cheap admin-only GET-config panel with no stream to preserve across a switch, so remounting fresh on every click keeps data always-current (add a host, flip to Container Rules, its host dropdown already has it) at the cost of one harmless refetch. The repeated saving/error/status try/catch/finally across all five lives once in `public/js/lib/settingsSection.js`'s `withStatus(vm, savingField, fn)` — not pure (it mutates the passed component), so it sits alongside `logStream.js` as a shared-but-not-unit-tested helper rather than in the pure-logic part of `lib/`. `SettingsGeneral.js` is the odd one out among the five: its one setting (the default landing tab, `DEFAULT_VIEW`/`server/index.js`'s `getDefaultView()`) has no secrets and applies to every role, so unlike the other four its `GET /settings/default-view` route is still `requireAdmin` for symmetry with the panel it lives in (only admins ever open Settings), but the _value_ itself reaches every logged-in user for free as a `defaultView` field on `GET /api/session` - `app.js`'s `mounted()` calls `setView(session.defaultView || 'list')` once hosts are loaded (not a bare assignment, so a configured `'flow'` default also fires `fetchTopology()` immediately, the same as clicking the tab by hand). **`getDefaultView()` validates the stored value on the way out, not only the submitted one on the way in.** `PUT` already 400s on anything outside `VALID_VIEWS`, but a hand-edited settings row — or one written by a release that still had a view this one has since dropped — would otherwise be handed straight to the client, and an unrecognised view is a **blank page**: List/Flow are `v-show` and Logs/Activity `v-if`, so nothing renders and no tab reads as active. `dbDefaultView()` therefore returns `null` for an unusable row, which also keeps `overridden` honest — it reports the override actually in effect rather than the mere presence of a row. The `.env` side is resolved once at module load into `ENV_DEFAULT_VIEW` rather than per call, since `getDefaultView()` runs on every `/session`: a misspelt `DEFAULT_VIEW` should log `config.default_view.invalid` once at boot, the same shape as the `SESSION_SECRET` warning, not on every login.

**The disk poll is the one schedule derived from measurement rather than declared, because `docker system df`'s cost is a property of the host's storage and nothing else.** It deduplicates shared image layers by walking the whole overlay2 tree: sub-second on native Linux, but measured at **40-75s cold on a WSL2/Docker Desktop host** with the same 32 images, where the layers sit on a virtual disk behind a 9p/virtiofs hop and every `stat` pays for it. Warm it drops back to ~2.6s, so the cost is dominated by page-cache state and the run-to-run spread on one machine is more than an order of magnitude. Three things follow, and they're all in `nextDiskDelay` / `pollDiskUsage`. (1) `DISK_USAGE_TIMEOUT_MS` is 120s, not a value chosen near the typical cost - the old 30s was picked on Linux and meant the call could **never once succeed** on WSL2, so the Disk panel was permanently empty while a heavyweight process was spawned and SIGKILLed every 60s forever. (2) The next run is scheduled at least `DISK_DUTY_FACTOR` × the last duration away, so a 75s call gets a ~5 minute gap instead of a 60s one - a call that takes longer than its own interval is effectively continuous, and holds one of `docker.js`'s 12 concurrency slots the whole time. On a fast host this floors at the plain 60s and nothing changes. (3) Consecutive failures back off exponentially to a 1h cap and reset on the first success. Be aware the backoff and the cache interact the wrong way round - polling less often means a colder cache means a slower call - which is why the timeout is set well clear of the cold cost rather than relying on backoff to find a workable rhythm. **A failed poll is surfaced, not swallowed**: `snapshot.diskUsageError` reaches the client via `{rows, error}` from `/hosts/:hostId/disk-usage` (a bare array couldn't distinguish "measurement failed" from "nothing on disk", so `HostCard` rendered no panel at all), last known rows are kept and shown alongside it, and the log line is a `warn` carrying the consecutive-failure count, since a call that is impossible on a given host is one fact about that host rather than several hundred incidents. Relatedly, `docker.js`'s `dockerCommandError` exists because `execFile` reports a timeout kill as a generic `Command failed: docker ...` with **empty** stderr - nothing is ever written to it - which reads like a daemon fault and is precisely why this went unnoticed for weeks.

**`server/db.js`** is a single `better-sqlite3` database (`data/opendockwatch.db`) holding metrics history, events, audit log, alerts, settings overrides, and doubles as the express-session store. Every query is prepared once into the `stmts` map at module load rather than per call - put new ones there too. **Everything a poll writes goes through one `db.transaction()`, not a loop of individual `.run()` calls and not a transaction plus a loose insert** - that's `insertMetrics(samples, hostSample)`, which carries every running container's row _and_ the host row. Per-row `.run()`s measured on an SSD at 2.65ms → 0.70ms for 50 containers and 10.58ms → 1.45ms for 200; folding the host row in on top of that saves a further 0.04-0.06ms per host per poll (44% of the write at 2 containers, 9% at 200). Since better-sqlite3 is synchronous the saving comes off the event loop directly - the same one `watchdog.js` watches for lag.

**Be careful about _why_ that is worth doing, because this file used to state it wrongly.** It claimed WAL "still runs at SQLite's default `synchronous=FULL`, so a per-row `.run()` is a full commit and an fsync each". It does not: setting `journal_mode = WAL` also drops `synchronous` to **NORMAL** (`SQLITE_DEFAULT_WAL_SYNCHRONOUS`), verified with `PRAGMA synchronous` on both a fresh database and the real `data/opendockwatch.db` - both report `1`. Under WAL+NORMAL a commit appends to the WAL and does **not** fsync; the fsyncs are at checkpoints. So the cost being saved is commit machinery, not disk sync, and it is tens of microseconds rather than milliseconds. The measurements above are real and the batching is still right - it is the mechanism that was mis-stated, and it matters because "every commit is an fsync" would justify contortions this codebase should not make. If a write path ever genuinely needs durability-per-commit, that is a deliberate `PRAGMA synchronous = FULL`, not something to assume is already in force. Atomicity comes along for free and is worth keeping: a malformed sample rolls the whole poll back rather than writing half an instant into the history charts (`test/db.test.js`). The ordering in `metricsCollector.pollHost` is deliberate - collect every sample **and build the host row**, write them all in one transaction, _then_ run `alerts.handleSample`/`handleHostSample` over them. The host row is built before the write purely so it can join that transaction; its alerting stays after, for the same reason the container alerting does. Alerting per container inside that loop would have put the rule engine's own `alert_breaches` writes, and `fire()`'s fire-and-forget async webhook, inside the metrics transaction; better-sqlite3 transactions are synchronous and must not have an `await` suspend inside them. The two history queries downsample into `@bucketMs`-wide windows using `BUCKET_EXPR` from `server/metricsHistory.js`, which is written as `ts - (ts % @bucketMs)` for a reason that will bite anyone who "simplifies" it back: better-sqlite3 binds every JavaScript number as REAL, SQLite's `/` is float division the moment an operand is REAL, and so the obvious `(ts / @bucketMs) * @bucketMs` returns `ts` unchanged and the GROUP BY groups nothing at all. `%` coerces to INTEGER regardless of binding. The same module's `withIoRates` then turns each bucket's `MAX(net_rx_bytes)` and friends into per-second rates by differencing consecutive buckets over their real elapsed time (the columns hold cumulative counters, so they're meaningless plotted raw), reusing `docker.js`'s `computeRate` so a container restart's counter reset comes back as `null` rather than a negative rate. The history queries themselves use `MAX`, not `AVG`, for those same I/O columns - a container that restarts mid-bucket makes `MAX` that bucket's pre-restart peak, so the following delta goes negative and is reported as `null`, the correct read on a counter reset. Both are pure and unit-tested in `test/metricsHistory.test.js`. Old rows are pruned on the retention windows (`METRICS_RETENTION_DAYS`/`EVENTS_RETENTION_DAYS`) by `metricsCollector.start()`, once at boot and hourly after that; the boot run matters because an instance that restarts more often than the interval would never reach the first tick. Indexes are chosen against the query's whole shape, `ORDER BY` included, not just its `WHERE` columns: `events` carries `(host_id, container_id, ts)` for the per-container restart counts and `(host_id, ts)` for `getEvents` (plus the partial third one covered above), because the first can only use its leading column when `container_id` isn't in the predicate, leaving SQLite to sort the host's entire retained history through a temp B-tree to answer a `LIMIT 200` — 14.1ms against 300k rows, versus 0.181ms once the second index turns it into a walk that stops at the limit. `EXPLAIN QUERY PLAN` naming a `USE TEMP B-TREE FOR ORDER BY` is the tell. No migration framework — schema is a set of `CREATE TABLE IF NOT EXISTS` statements run at startup; add new tables the same way, and new indexes too (unlike `ALTER TABLE ADD COLUMN`, `CREATE INDEX IF NOT EXISTS` in that block does reach an existing database on upgrade) — with one exception: an index over a column the `ALTER TABLE` block is adding has to be created after that block, since in the schema block it would run against a table that does not have the column yet (see `idx_events_host_ts_active`). A new _column_ on an existing table needs both: add it to the `CREATE TABLE` (for a fresh database) and a `try { db.exec('ALTER TABLE ... ADD COLUMN ...') } catch {}` right after the schema block (for an existing one upgrading — `IF NOT EXISTS` only skips the whole statement, it doesn't retroactively add columns to a table that already exists without them).

**Auth (`server/auth.js`)** is cookie-session based with two roles: admin (full control) and an optional read-only viewer (`VIEWER_USER`/`VIEWER_PASS_HASH`). Role enforcement is server-side (`requireAdmin` middleware on every mutating route) — the viewer role hides buttons in the UI too, but a request forged around the UI still gets a 403 from the server. `test/index.test.js` enforces that structurally rather than by a hand-maintained list: it walks the api router's own stack and fails if any non-GET route lacks `requireAdmin`, so a mutating route added later can't quietly ship without it. Read-only is not the same as "may read everything", though, and one route needs the distinction spelled out: `GET /containers/:id/inspect` returns `docker inspect`'s `Config.Env`, which is where DB passwords and API keys actually live, so a non-admin session gets it through `maskEnvValues` (`docker.js`) — variable names kept, values replaced, `envMasked: true` on the response so `ContainerDetail` can say why rather than look like every value is blank. `maskEnvValues` splits on the _first_ `=` only, or a secret containing one (base64 padding, a connection string with `?ssl=true`) would leak its tail; a genuinely empty value stays visibly empty instead of being dressed up as a hidden one. Login calls `req.session.regenerate()` before marking the session authenticated — `saveUninitialized: false` means there's rarely a pre-auth session to fixate, but that's a property of the current config rather than a guarantee, and the guarantee should come from the login itself.

**Two endpoints sit outside the `requireAuth` router and are gated differently.** `/healthz` is deliberately open and deliberately narrow (see the Dockerfile's HEALTHCHECK). `/metrics` can't use cookie auth because Prometheus can't, so it takes a shared secret in `METRICS_TOKEN` — and an unset token means the endpoint **404s**, not that it serves without auth. That response enumerates every container name, compose project, usage figure and restart count across every host, which is inventory disclosure to anything that can reach the port, so the unconfigured state has to fail closed; a scraper sets the variable, nobody else needs the endpoint at all. The comparison goes through `crypto.timingSafeEqual` (length checked first, so only the token's length is observable) since this is the one credential that travels in a URL.

**Static assets are mounted twice, and the HTML is rewritten on the way out.** There is no build step, so a page load is ~43 separate sub-resources: 35 ES modules, 7 vendor scripts, the stylesheet and the logo. `express.static`'s defaults gave every one an ETag and no `max-age`, so every revisit and every reload was 43 conditional round trips — all answering 304, all still spending a turn of the browser's ~6-connection budget on the same origin whose SSE streams already hold some of it open. Measured before and after in a real browser: **43 network requests on revisit → 0, and on reload → 0** (cold load is unchanged at ~1.4MB, as it must be). The fix is a version-pinned prefix, `/assets/v<package.json version>`, mounted `immutable, maxAge: '365d'`. Pinning by path rather than by `?v=` query is the load-bearing choice: a relative `import './format.js'` resolves against the **importing module's own URL**, so pointing `index.html` at `/assets/v2.5.1/js/app.js` pulls the entire 35-module graph under the same prefix for free, where a query string would not be carried by those imports and 34 of the 35 would silently fall back to the uncached mount. The bare `/assets` mount stays, on a 5-minute `max-age`: `app.js`'s template references `/assets/logo.svg` directly, and a browser still holding the previous release's `index.html` has to keep working rather than 404 its way to a blank page. **The HTML itself is `Cache-Control: no-cache`, always** — it is the pointer to everything above, so caching it means the browser keeps loading the previous release's assets out of its own cache indefinitely and invisibly. `sendPage()` reads the file per request (two small files, once per navigation, against 43 saved requests) so `npm run dev` still picks up edits, and rewrites `/assets/` to the pinned prefix rather than the HTML carrying a placeholder — that keeps both files valid as plain static HTML.

**Security headers** are five fixed values set by one middleware in `index.js`, ahead of everything including the static mounts, rather than a helmet dependency. CSP is the load-bearing one, and the directive doing the work is the _absence_ of `'unsafe-inline'` from `script-src`: container log output reaches the DOM through `v-html` in three components, and since `innerHTML` never executes a `<script>` tag anyway, the real injection vector there is an inline handler like `<img onerror=…>` — which is exactly what that omission blocks. This is why `public/login.html`'s submit handler lives in `public/js/login.js` instead of an inline `<script>`, and why a test asserts both that it stays external and that `script-src` never gains `'unsafe-inline'`. If a future inline block "needs" it, put the script in a file instead.

`script-src` does carry **`'unsafe-eval'`, and removing it blanks the entire app** — verified in a real browser, not assumed. There's no build step (a deliberate constraint, see the frontend section), so every component ships a `template` string that Vue compiles in the browser via `Function(code)()` at `vue.global.prod.js`'s single `Function(` call site; under a CSP without `'unsafe-eval'` that throws and every component renders empty, silently, with nothing useful in the console. The only ways off it are precompiling templates (a build step) or hand-writing `render()` functions — both are much larger changes than the header, and `'unsafe-eval'` doesn't re-enable inline scripts or event handlers, so it costs little against the threat this CSP was added for. `style-src` carries `'unsafe-inline'` for the same no-build-step reason and can't avoid it — `format.js`'s ANSI colour spans and `graph.js`'s cytoscape HTML labels both emit `style="…"` into parsed HTML — and `img-src` allows `data:`/`blob:` for the graph's inline SVG icons and the PNG export. Not set: HSTS, which does nothing over the plain HTTP many deployments use behind a proxy and belongs on the proxy terminating TLS.

**`requireHost` attaches the resolved host as `req.odwHost`, and the name is load-bearing.** Express defines `req.host` as a **getter-only** property returning the Host header, so `req.host = hostObject` silently no-ops in sloppy mode and every handler downstream reads back a string like `"localhost:3000"` instead. Nothing throws and nothing looks wrong locally: `hostArgs()` is `host && host.dockerHost ? ['-H', host.dockerHost] : []`, and a string has no `.dockerHost`, so it falls through to the empty-args case — the **local socket**. A single-local-host install therefore behaves perfectly while every remote host's containers, logs, stats, inspect and start/stop/restart routes quietly run against the wrong daemon. `test/index.test.js` drives a probe route through the real `requireHost` and asserts the handler receives an object, plus asserts express's own `req.host` is still unwritable so the day that changes is visible rather than assumed. Never name request-scoped state after something express already owns.

**Route input handling (`server/index.js`)** — nothing from the URL reaches sqlite or the docker CLI raw. `intParam` defaults and clamps numeric query params (`Number('abc')` is `NaN`, which better-sqlite3 rejects outright with "datatype mismatch" instead of treating as absent, so an unvalidated `?limit=`/`?since=` 500s the request rather than falling back), `tailParam` allows a positive integer or docker's literal `all` (the log viewer's "All lines" option), and `requireContainerId` rejects anything that doesn't look like a container id - nothing runs through a shell, but an id starting with `-` would be read by docker as a flag rather than a container. Anything a route throws that it doesn't handle itself lands in the terminal error handler registered after the router, which logs it and returns the message alone; without it express's default handler answers, and that one puts the whole stack trace in the response body unless `NODE_ENV=production`.

**Frontend is Vue 3 (Options API)**, no SFCs/build step — `public/js/**` is loaded as native ES modules via `<script type="module">`. `app.js` is the root component (~400 lines): session/role bootstrap, host list/selection, the 5s polling loop, containers/stats/alerts state, view switching, and `doAction`. Everything view-specific lives in `public/js/components/`: `SparkTile`/`HostCard` (the host-usage tiles), `ContainerList`/`ContainerDetail` (the List view and its detail panel), `MiniSpark`/`ContainerMetricsModal` (the per-container sparkline in each row and the full-history view it opens), `LogViewer` (the full-size log panel), `ActivityView` (the alerts/events tab), `SettingsPanel` (webhook/threshold/host config), and `FlowView` (the Cytoscape graph/tree view). `SparkTile` is the shared chart for both the host tiles and the modal, which is why its second series is `secondarySamples`/`secondaryLabel` rather than anything host-named - it carries the host total behind Docker's own usage on the host card, and the tx half of an rx/tx pair on the modal's I/O charts - and why `slotCount` is a prop: the host card's live window and the 1h/24h/7d ranges hold different numbers of buckets. **The hovered values are a rendered readout (`.spark-readout`), never a `title` attribute**, and that distinction was a real usability bug: a native tooltip needs the pointer held on the element itself for about a second and vanishes the moment that element moves — and the hover dots are 6px and move on every 5s poll, so reading one meant chasing a target that walked away. `onHover` already derives the slot index from horizontal position alone, so the readout rides the crosshair and stays up for as long as the pointer is anywhere over the chart. It is pinned to the top of the chart rather than following the dot vertically, deliberately: tracking the value would make it jitter on every redraw, which is the same complaint in a different form. It flips to the near side of the crosshair past the halfway mark instead of being clamped at the edge (clamping would park it on the line it annotates), and carries `pointer-events: none` because the `mousemove` positioning it belongs to the chart underneath — a readout that swallowed that event would freeze itself the instant it appeared. Hovering the still-empty padded region of a partly-filled chart correctly shows nothing at all, since `hoverPoints` returns null when neither series has a value there. **`HostCard` has the same 1h/24h/7d range strip as `ContainerMetricsModal`, plus a fourth `live` option, and the strip only renders in fullscreen** — a tile sharing a row has no space for it. `live` is the default and reads the root's `metricsHistory` prop (the rolling window the root already refetches every poll), so the card costs no extra request until someone actually widens the window; the other three re-read sqlite over the same `GET /metrics/history` the modal uses, minus its `containerId`. Every series reads one `activeHistory` computed rather than the prop directly, so a range switch moves both tiles together and they can't end up drawing different windows. Same two guards as the modal, plus one: a landing response is dropped if either the range **or the host** has changed since it was issued, and only `1h` keeps a refresh timer (24h/7d buckets are 5 and 30 minutes wide, so a 5s refetch would redraw an identical chart). Leaving fullscreen resets to `live` — the strip is the only way back, so a non-live range would otherwise be stranded with its timer still running behind a tile that can't show it. The `system_*` columns behind the "host total" overlay are `AVG`d by the same query at every bucket width, so that series works at 7d exactly as it does live. `MiniSpark` is deliberately not a variant of it; sharing that component for a table cell would mean `v-if`-ing away five of its six parts. Panels that are meaningfully transient (`LogViewer`, `ContainerDetail`, `ActivityView`, `SettingsPanel`) mount via `v-if`, each time fresh, so their own `mounted()`/`beforeUnmount()` own their stream or fetch lifecycle instead of the root orchestrating it (e.g. `ContainerDetail` watches its own `container.id` prop to reset/refetch on a same-mount container switch, since watching the whole `container` object would refire on every 5s poll — the root replaces its `containers` array wholesale each poll, so the object reference changes even when the id doesn't). `ContainerList` and `FlowView` instead stay mounted via `v-show` across List/Flow tab switches, since there's nothing external to tear down and rebuilding a Cytoscape graph from scratch on every switch would be wasteful for a host with many compose projects — they watch their own props (`topology`, `hostId`, `stateFilter`) to re-render instead of remounting. State that's genuinely shared across views (`selectedContainerId`, `selectedHostId`, `alerts`) stays in the root and flows down as props, with children emitting events back up (`select`, `action`, `close`, `open-log-viewer`, ...) rather than reaching into siblings; `fullscreen` on both `LogViewer` and `FlowView` is the one exception worth calling out — it's a real `v-model` (not fully internal) because the root's own layout needs to know about it directly, to hide the host card and other panels. Two sources feed the container charts and they are not interchangeable: the List row's `MiniSpark` reads the root's live in-memory buffer (`recordMetricsSample`, ~2 minutes, empty after a reload), while the modal reads the persisted sqlite history over `GET /metrics/history?containerId=`. Samples are right-aligned into the chart's slots by `padSlots`, so a series shorter than the window - a container created ten minutes ago, or a buffer still filling - draws in the right-hand part of the chart and grows leftward, rather than stretching to fit. `public/js/lib/` holds pure, unit-tested logic shared across components: `spark.js` (sparkline coordinate math, used by `SparkTile` and `MiniSpark`), `logSync.js` (the binary search behind the Logs tab's multi-pane scroll sync), `logLines.js` (per-line log decoration/filtering — see below), `format.js`'s `eventSeverity` maps docker event actions onto the same `critical`/`warning`/`ok` vocabulary the alert rows use, so one colour language covers both Activity columns — it drives both the event rows' left accent and their badges. Unlisted actions (`exec_create`, `attach`, `commit`, `resize`, …) stay deliberately neutral: colouring routine noise would drown the handful of rows worth spotting. `health_status:` is special-cased and tests the **negative first**, since `"unhealthy".includes("healthy")` is true and the obvious order gets the two exactly backwards. Severity is attached once per event at ingest (both `loadEvents` and the SSE `onmessage`), never derived in the template, for the same reason `logLines.js` exists — a method call from a `v-for` re-runs on every render. The row accent is an `inset` box-shadow on the first cell rather than a `border-left`, because the events table is `border-collapse` and a per-cell border fights the collapsed grid. `activityCounts.js` (`groupCounts`, behind the Activity tab's per-kind header badges — alerts by rule, events by action; counted off the _text-searched_ lists so the badges describe the rows the search box left — but deliberately not off the badge-filtered ones, see `activityFilter.js` below — sorted by count with a `localeCompare` tie-break that is the load-bearing part, since without it two kinds on the same count swap places as rows stream in and a badge row that reshuffles while you read it is worse than none, then capped with the remainder returned as a `+N more` badge), **`activityFilter.js`** (`filterAlerts`/`filterEvents`, the two filters each Activity column applies — see below for why they are two and not one), `logBuffer.js` (`pushCapped`, the append-and-trim shared by the visible line array, a paused pane's held buffer, and the drain of one into the other — pure and unit-tested precisely because the invariant that matters spans all three: `test/logBuffer.test.js` asserts that pausing and resuming lands on the same buffer as never pausing, cap included), and `logStream.js` (the EventSource/buffering factory both `LogViewer` and `ContainerDetail`'s log preview build on; the one module that isn't purely pure, since it also owns the hidden-tab suspension, which is why `doc`/`EventSourceImpl`/`schedule` are all injectable). `logLines.js` exists because per-line work has to happen **once at append**, not per render: `decorateLine` derives a line's level, timestamp and no-filter HTML when it arrives, and `selectLines` reuses that cached `baseHtml` unless a filter is actually active. Deriving it per recompute cost ~4.4ms for a 3000-line pane (~17.7ms across four, past a 60fps frame's 16.7ms); caching brings a pane to ~0.16ms. `ContainerDetail` had a worse variant — it called `highlightLine` from a template _method_, so the work re-ran on every render including the 5s stats poll — and its preview is capped at `PREVIEW_TAIL`, not `MAX_LOG_LINES`. The same module also owns the Log Viewer's search cursor (`hitIndexFor`/`stepHitId`), and the rule there is that **the cursor is a line id, never a position**: `appendLines` trims the buffer from the front once a pane passes `MAX_LOG_LINES`, so every appended line shifts each index down by one and a positional cursor quietly comes to name a different line — the highlight walks the hit list on its own, with no user action, while the "26 / 30" counter keeps reporting the position it started from. It's invisible in a short pane and constant in a busy tailing one, which is why it shipped. `hitIndexFor` resolves the id back to a position on every render (a computed, so once per render pass and not once per line) and falls back to the first hit when the parked-on line has aged out or been filtered away; `LogViewer` clears the cursor in `startStream`/`onReset` because `logStream` restarts its ids from 0 for a new source, so a cursor held across a reconnect would otherwise point at whatever unrelated line inherits that id. Clicking a hit line sets `revealAll` rather than clearing the filter: `selectLines` gets a `hideNonMatching` option, and with it off, `filteredLines` renders every line (context included, matches still highlighted, non-matches reusing cached `baseHtml` so this isn't the O(n) `highlightLine` cost again) while `matchLines` - always computed with `hideNonMatching: true` - keeps the hits box counting and stepping through matches only, since the two arrays diverge once revealAll is on. Typing a further filter character (or toggling regex mode) drops `revealAll` back to false, since a new search term means "narrow down again"; clearing the filter to empty just turns `searchActive` off, which is what actually hides the box and the highlighting. Supporting modules: `api.js` (the only place `fetch` is called, wraps 401→redirect-to-login and JSON/error handling), `format.js` (pure display formatting: ANSI-to-HTML for colored logs, byte/timestamp formatting, log-level detection, badge/icon lookups), `constants.js` (poll intervals, history lengths), `graph.js` (all Cytoscape.js flow-view logic: layout via dagre, edge/node styling, compose-group collapse/expand via cytoscape-expand-collapse, and `localStorage`-backed persistence of dragged node positions + camera zoom/pan + collapsed group ids, keyed per host so a reload doesn't reset your arrangement — owned by `FlowView`, which is the only component that imports it). The Flow view has two render modes sharing the same topology data: graph mode (`buildElements`, compose-group boxes, network/depends-on/manual edges) and tree mode (`buildTreeElements`, an ArgoCD-style `project → container → network/mount` DAG with no compound groups, network/volume pills deduped globally so shared infrastructure gets one node with multiple incoming edges). A tapped tree-mode pill (`proj:`/`net:`/`mount:` id) is filtered out inside `FlowView` before it ever reaches the root — routing it into `selectedContainerId` would trip `ContainerDetail`'s watcher into fetching `docker inspect` for a fake id — so it's kept as `FlowView`-local state (`pillSelection`), used only for fading and the tap-info bar. Container nodes are shared between both modes via `containerNodeEl`. Positions/camera are keyed per host _and_ per mode (`odw:flow:positions:<mode>:<hostId>`, etc.) since a dagre layout from one mode is meaningless in the other; the mode choice itself is also saved per host. Vendor libraries (Vue, Cytoscape, dagre, html2canvas-pro, cytoscape-expand-collapse) are checked into `public/vendor/` and loaded as global `<script>` tags, not npm/bundled — `eslint.config.js` declares them as browser globals for that reason. html2canvas-pro exists specifically because `cy.png()` only rasterizes cytoscape's own `<canvas>`, not the `cytoscape-node-html-label` DOM overlay that actually renders node content (name, icons, CPU/RAM bars, badges) — Flow view's "Export PNG" screenshots the real on-screen DOM instead (this means it has a fixed pixel resolution to manage - see `EXPORT_SCALE` and the container-resize dance in `exportPng`: html2canvas just copies cytoscape's existing CSS-pixel-resolution canvas bitmap, so a higher `scale` merely stretches an already-low-res source, which is why `exportPng` instead temporarily renders into a container `EXPORT_SCALE` times larger - scaling container size, zoom, and pan by the same factor is a uniform scale-up of `renderedX = graphX * zoom + pan.x`, so it frames the exact same crop with `EXPORT_SCALE` times as many real pixels to draw into). "Export SVG" sidesteps that entirely: `extractSvgGeometry` (impure, reads the live `cy` instance's positions/classes/data) feeds `renderSvg` (pure, geometry → an `<svg>` string, unit-tested the same way `buildElements` is) which hand-draws the same node/edge visual design `CY_STYLE` and the HTML templates already encode - no dependency on the DOM overlay or a rasterization step, so there's no resolution ceiling to manage for a host with a lot of compose projects. expand-collapse physically removes a collapsed group's children from the graph, so `updateGraph`'s poll-driven diff skips them entirely while hidden rather than touching them (an earlier version briefly expanded/re-collapsed every poll to keep their data fresh, but that visibly flickered the collapsed box every 5s) — `expandcollapse.afterexpand` re-syncs a group's children from the latest poll's data the moment it's actually opened instead. Below `COMPACT_ZOOM_THRESHOLD` (graph.js), nodes render a compact HTML label (state/icon/name only, no metric bars) and shrink to match via a per-element style function on node height keyed off a `compact` data flag - flipped synchronously on every `viewport` event (immediate, unlike the debounced viewport-position save alongside it) so it reads as a direct consequence of zooming. **A container leaf's state class must come from `elements.js`'s `CONTAINER_STATE_CLASSES`, and every selector that means "any container" must be built from it** - `layout.js`'s `OVERLAP_NODE_SELECTOR` and `updateCompactFlag`, `graph.js`'s `nodeHtmlLabel` query, `svgExport.js`'s `svgNodeKind`. Nothing throws when one of the four misses a state; the node just quietly stops participating in whatever that selector drives, which is how `created` shipped absent from `layout.js`'s two: it never received a `compact` flag, so `node.created`'s height mapper always took the full-height branch and the node stayed full size (rendering the non-compact label) while every neighbour shrank on zoom-out, and it was neither an obstacle for nor a subject of overlap resolution, so it could sit on top of another node. `test/graph.test.js` sweeps every docker state through `buildElements` and asserts the class it emits is in that list, which catches a new branch added to `containerStateClass` without the list, but not a selector that forgot to derive itself - so derive, don't spell out.

**`ConfirmButton` is the app's only confirmation, and it is a two-step button rather than a dialog.** The Activity tab's two Clear buttons act on every alert or event on the host from a single click, which is the one place in the UI where a slip is worth a second of friction. It arms on the first click (label swaps to `Sure?`, fills red via `.confirm-btn.armed`) and runs on the second; the `ARM_MS` timeout, a blur, or unmounting all disarm it — the unmount case matters because the Activity tab is `v-if`, so switching tabs mid-arm would otherwise leave a timer firing against a component that no longer exists. Deliberately not `window.confirm`: it blocks the event loop this app spends a lot of effort keeping free, and a native dialog is the same kind of borrowed browser affordance as the `title` tooltip the sparkline readout replaced. Registered locally by `ActivityView` (`components: { ConfirmButton }`), the same way `SettingsPanel` registers its five tabs — root registration in `app.js` is local to the root, not global, so a nested component has to be declared by its parent. **Be aware the two Clear buttons are currently the only things using it**: `SettingsHosts`' "Remove" (which deletes a monitored host) and `SettingsContainerRules`' "Remove" are both still one click, and are the obvious candidates if this is meant to be the house pattern rather than one screen's.

**The Activity columns filter on two independent things, and collapsing them into one didn't work.** Each column has a free-text search box (substring, across a few fields) and a row of count badges that double as filter toggles. The badges first shipped by writing their key into the search box, which reused the filtering that already existed but was wrong in two ways that a badge filter cannot afford. It **over-matched**, because the search is a substring across several fields: clicking the events column's `start` badge also matched every `restart` row, and clicking an alert rule badge also matched any alert whose _message_ merely mentioned that rule — so the badge said 1 and the list showed 3. And because `groupCounts` runs off the searched list (deliberately, so the badges describe what's on screen), setting the search **collapsed the badge row to the one badge you just clicked**, leaving no way to switch from one filter to another without un-toggling first. `activityFilter.js`'s `filterAlerts`/`filterEvents` therefore return **`{ searched, shown }`**: `searched` is the text box alone and is what the badges are counted off, so every badge stays visible and clickable while one is active; `shown` is that narrowed by an exact match on the field the badges group by (`rule`/`action`), and is what the list renders. The two filters compose, and `alertRuleFilter`/`eventActionFilter` are their own component state rather than the search string — the "Clear filters" button clears both, which matters because a badge can drop out of the visible row (past `groupCounts`' limit) while its filter is still applied.

**Container state and health are two axes and both are rendered.** `stateEmoji(state, health)` colours a running container's dot by health (green/amber `starting`/red `unhealthy`) instead of a flat green, and `created` gets its own dashed accent icon rather than falling into the generic stopped branch. `HEALTH_COLOR` is declared at the **top** of `format.js`, not next to `healthColor()` where it reads more naturally, purely because the icon constants are built from it at module load and a `const` is in its TDZ until its own initializer runs - keep it there rather than re-introducing the three hex literals it used to be duplicated into. The Flow view mirrors the same two axes as classes (`created`, `starting`) with `CY_STYLE` ordered `created → starting → unhealthy → selected` so the more urgent fact wins the border colour, and `svgExport.js` repeats that precedence by hand in `svgContainerNode` - the SVG exporter hand-draws what `CY_STYLE` encodes, so a new state or health colour has to be added in both or the export silently disagrees with the screen.

**The Logs tab's multi-pane scroll sync** (`LogsView.js`/`LogViewer.js`): a `viewMode` toggle at the top of the side list picks between `'single'` (one pane; clicking a row swaps its container, clicking the open row closes it - `openIds` never exceeds length 1) and `'multi'` (clicking a row toggles it open/closed, `openIds` capped at `MAX_OPEN_LOG_PANES`) rather than always replacing a single selection, so up to four `<log-viewer embedded>` panes can render side by side. Switching `'multi'` → `'single'` with more than one pane open collapses `openIds` down to the main pane if one was set, else whichever was opened most recently, and clears `disabledSyncIds`/`mainId`/`joinTsMsById` along with it - none of those apply to a lone pane. `setViewMode` is a no-op when nothing needs to collapse (0 or 1 panes open, or already in that mode). Each pane's `onScroll` emits `scroll-sync` with `{containerId, tsMs}` - the epoch-ms timestamp of whichever line is now at the top of its viewport - only when the _user_ scrolled it (`_programmatic` guards the case where `scrollToTimestamp` itself moved the pane, so a sync-driven scroll doesn't re-broadcast and ping-pong forever). `LogsView`'s `broadcastFrom` is the single place a sync event actually moves other panes: peer-to-peer by default (whoever scrolls drives the rest), but designating one pane `mainId` switches the group to leader-follower (only the main's scrolling drives anyone - `broadcastFrom`'s first check enforces this even though every pane's events keep arriving). `disabledSyncIds` lets a pane opt out entirely, in both directions (it doesn't broadcast and isn't moved). `toggleSync`/`setMain` broadcast the affected pane's _current_ position immediately when re-enabling sync or marking main, rather than waiting for its next scroll event - that's what lets you scroll a pane to a spot of interest while desynced, then have the rest jump to match it the moment you flip sync back on. `lastSyncTsMs` is kept so a pane opened after the group has already scrolled somewhere joins at that same timeframe instead of live-tailing at the bottom while its siblings look at history. `LogViewer`'s `embedded`/`multiPane`/`wrap` props split standalone mode (root overlay, `fullscreen` v-model, its own wrap toggle) from embedded mode (a `LogsView` pane: no fullscreen, `wrap` fed from one tab-level toggle instead of repeating it per pane) - `multiPane` is independent of `embedded` and only turns on once 2+ panes are open, since a single embedded pane has no close/sync/main controls to show (picking a different row is the close equivalent).

**The log panel header is two rows, and its breakpoints are measured rather than guessed.** The container name owns the top row alone — `white-space: nowrap` with an ellipsis and the full name on `title`, since compose-prefixed names run long and used to wrap to two lines in a side-by-side pane. Row two is the status badge pinned left with the control strip pushed right by `margin-left: auto`. The badge is **always present** and reads `▶ active` / `⏸ paused` / `⏸ suspended` from one `statusBadge` computed: "active" is only legible as a state because it sits exactly where "paused" would, so a streaming pane says so rather than saying nothing. Manual pause outranks suspension, because if the user paused it that's the answer to "why isn't this moving". Three `@container log-panel` tiers, each set from a measured natural width (the strip needs 993px in a multi-pane header and 1140px in a standalone one, which also carries Matches/Fullscreen/Wrap/Close): **≤1150px** drops the button labels and narrows the search box to 150px — this is the one that matters, since two panes on a 1080p screen land at ~985px each and were wrapping; **≤900px** swaps the four level buttons for the `☰ Levels` dropdown, for the 2×2 grid at ~865px; **≤760px** finally collapses the search box to an icon that expands on focus. That last one is deliberately still 760 rather than folded into the tier above — between 760 and 900 the level dropdown alone buys back enough, and seeing what you filtered on is worth more than the 120px. Below ~800px it does wrap to two control rows; that's accepted degradation, not a target. Re-measure rather than eyeball if controls are added: one more button moves every boundary.

**Pause and the match strip (`LogViewer.js`).** Space toggles a manual pause on the log body. It deliberately does **not** stop the stream: the EventSource stays connected and incoming lines go into a non-reactive `_pendingLines` buffer capped at the same `MAX_LOG_LINES`, so resuming shows what actually arrived instead of paying for a reconnect and a re-tail (and a container left paused for an hour can't grow the buffer without bound). The keydown listener is on `document`, so it's live without the pane needing focus first — guarded against firing while typing (`INPUT`/`TEXTAREA`/`SELECT`/`BUTTON`/`contenteditable`), against any modifier, and with `preventDefault` so space doesn't also scroll the page. Every open pane carries that listener, so in multi-pane the **hovered** pane takes the keypress or one space would pause all four; a lone pane needs no hover. It's distinct from `suspended` (the background-tab connection handback) and badged differently, since "I paused this" and "the tab did" are different states — and `onReset` force-unpauses, because that path has just wiped the buffer and staying paused would leave an empty pane that never fills, which reads as broken rather than paused. **The match strip** is a filtered-results pane, the long-standing log-viewer pattern of listing the hits separately and clicking one to jump to it: `matchLines` (which already exists for the hits counter) rendered as a short scrollable list under the log body, each row clicking through to `selectMatch` — the same reveal-in-context path clicking a hit line in the body takes. Single-pane only (`matchPaneVisible` is `showMatchPane && !multiPane`): a quarter-width cell in the 4-up grid has no vertical room to give up. **While it's open the log body stops narrowing to matches** — `showAllLines` is `revealAll || matchPaneVisible`, so the strip makes reveal-mode the default rather than something you get only after clicking a hit. Filtering both would be redundant, and worse than redundant: the strip's whole purpose is jumping into surrounding context, which a filtered body doesn't have. The level toggles still apply — those aren't search. Rows never wrap, since a wrapped row would eat two or three of the handful the strip shows at once. The standalone pane sizes its body against the viewport, so `.has-match-pane` takes the strip's height back out of that calc; the embedded pane is already a flex column and needs no such adjustment. **The strip resizes by dragging its own header bar (`.log-match-pane-header`), deliberately not by `resize: vertical`.** The native handle is wrong here in three separate ways, worth keeping written down because it is the obvious thing to reach for again: it lives on the bottom-right corner, which on a pane anchored to the _bottom_ of the panel is diagonally opposite the only edge that moves; dragging it down grows the strip downward off the end of a fixed-height panel rather than into the log; and it is invisible until stumbled upon. A dedicated hairline grip was the first replacement and was still a thing to hunt for — the header is better because it already exists, already _is_ the boundary between log and strip, and is a full-width 34px bar you can grab without aiming. A centred `::after` pill brightens on hover/focus (a bare `cursor: ns-resize` is only discoverable by sweeping the mouse across it), and `tabindex="0"` plus ↑/↓ handling resizes it without a pointer at all. **`startMatchResize` bails on `ev.target.closest('button')`**: the ✕ lives inside the handle, and without that guard pressing it starts a zero-distance drag whose `preventDefault` eats the click. **The drag maths inverts the delta** (`startH - (e.clientY - startY)`), because the handle is the top edge and dragging up has to make it taller. Listeners go on `window`, not the handle: a fast drag outruns the element under the cursor, and the pointer routinely ends up over the log body or outside the panel entirely. **The bound is measured, not declared** — `matchMaxHeight()` is the current height plus whatever the log body can give up above `MIN_LOG_BODY_PX`, read live off `logView.offsetHeight`. CSS can't express that: the log body is `flex: 1; min-height: 0` in both flex-column panels and so yields all the way to zero, and the panel's own height differs by mode (fullscreen is a viewport calc, embedded is measured by `LogsView.updateWrapHeight`), so a px cap eats the whole log on a short window while a `vh` cap can only ever be right for one of the two modes. The height itself lives in `LogViewer.js`'s `matchListHeight` rather than as an inline style the drag writes directly, because the element sits behind two `v-if`s (the pane toggle, then `searchActive`) and would otherwise lose it the moment the strip is hidden or the filter cleared.

**Live updates use Server-Sent Events**, not WebSockets: container logs (`GET /api/hosts/:id/containers/:id/logs`, `docker logs -f --timestamps`) and the container event feed (`GET /api/hosts/:id/events/stream`, via `eventWatcher`'s `Broadcaster` in `server/sse.js`) are both one-way SSE streams the frontend consumes with `EventSource`.

**The image** (`Dockerfile`) installs with `npm ci` from the committed lockfile, so it gets the dependency tree CI linted and tested against rather than whatever resolves on build day, and sets `NODE_ENV=production`. The Docker CLI is copied from Docker's own `docker:29-cli` image rather than installed from Alpine's `docker-cli` package: the CLI is a Go binary, so scanners attribute every Go standard-library CVE to it, and Alpine's build lags Docker's - v3.24/community sat on 29.5.3 built with go1.26.3 (carrying three stdlib CVEs fixed in go1.26.4) while Docker's image shipped 29.6.2 on go1.26.5. No amount of rebuilding fixed that; only Alpine rebuilding the package would have. The binary is self-contained, runs as-is on the musl base, and a newer CLI talks to older daemons fine (verified against a 27.5.1 daemon). `openssh-client` still comes from apk, since `docker -H ssh://` shells out to the system `ssh`. `.dockerignore` keeps `data/` out of the build context - without it, a `docker compose up --build` on any machine that has already run OpenDockWatch bakes that machine's sqlite database into the image, session store and the settings row holding the webhook URL (token and all) included.

**Chart colors** are the four `--seq-*`/`--accent` custom properties in `style.css`, validated as a categorical set (lightness band, chroma, contrast, and colorblind separation on every pair) against the tile surface rather than picked by eye - the header comment above them records what passed and what failed, including the obvious purple that turns out to be indistinguishable from `--accent` for deutan viewers. Re-validate rather than eyeball if they ever change; the `dataviz` skill carries the validator.

**Two eslint environments** (`eslint.config.js`): `server/**`, `scripts/**`, `test/**` are CommonJS/Node; `public/js/**` is an ES module/browser environment. Keep new files in the right bucket.
