# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

OpenDockWatch is a small self-hosted Docker monitoring dashboard: container list/start/stop/restart, live log tailing, a topology ("Flow") graph, and an alerts/events feed. It watches the local Docker daemon and any number of remote hosts over SSH. See `README.md` for the full feature list and `CONTRIBUTING.md` for the release process.

## Commands

```
npm install                                 # deps
cp .env.example .env                        # then fill in AUTH_USER/AUTH_PASS_HASH/SESSION_SECRET
cp config/hosts.example.json config/hosts.json
npm run hash-password -- "your-password"    # generates a bcrypt hash for .env's AUTH_PASS_HASH

npm run dev                                  # node --watch server/index.js, http://localhost:3000
npm start                                    # plain node server/index.js

npm test                                     # syntax-check every server/public-js/scripts file, then node --test
node --test test/docker.test.js              # run a single test file
node --test --test-name-pattern="parseByteString" test/docker.test.js   # run one test by name

npm run lint                                 # eslint .
npm run format                               # prettier --write .
npm run format:check                         # prettier --check .  (what CI runs)

docker compose up -d --build                 # run OpenDockWatch itself in a container
```

CI (`.github/workflows/ci.yml`) runs `npm run lint && npm run format:check && npm test`, then a plain `docker build`. Always run the same three before considering a change done.

## Code comments

A comment block attached to a function/method (or a magic number/config constant next to one) is capped at 3 lines. If the full rationale doesn't fit, keep the 3-line version terse and load-bearing, and put the rest here in CLAUDE.md under the relevant module instead of letting it spread across the codebase - this file is already the canonical home for the "why" behind most non-obvious decisions in this repo, so a comment can point here rather than repeat it.

There is no build step for the frontend — `public/js/*.js` is served as-is via native ES modules (`<script type="module">` in `public/index.html`). Most of it (`app.js`, `public/js/components/**`) is only syntax-checked, not unit-tested, since it's Vue/Cytoscape UI code with no meaningful behavior outside a browser - but pure logic with no DOM/cytoscape dependency has no such excuse: `format.js` (ANSI parsing, level detection, byte/rate formatting), `graph.js`'s `buildElements`/`aggregateGroups` (graph-building), and `public/js/lib/spark.js`/`lib/logStream.js` (sparkline coordinate math and the EventSource/buffering factory shared by `LogViewer`/`ContainerDetail`'s log streams - `EventSourceImpl` and the flush `schedule` are injectable specifically so this is testable under `node --test` with a stub source, without a browser) are all unit-tested. `test/format.test.js`, `test/graph.test.js`, `test/spark.test.js`, and `test/logStream.test.js` `import()` their module directly (dynamic import, since `require()` can't load an ES module - `node:test`'s `before()` hook loads each once and shares it across that file's tests). When pulling more logic out of a component in `public/js/components/`, prefer landing it in `public/js/lib/` if it's pure - that's the difference between it being tested and not.

## Architecture

**The server shells out to the `docker` CLI** (`server/docker.js`, via `child_process.execFile`/`spawn`) rather than talking to the Engine API or a Docker SDK. Every function takes a `host` object and prefixes its args with `-H <dockerHost>` when set (`hostArgs()`); a `null`/absent `dockerHost` means the local socket. This is _why_ remote hosts work at all: `-H ssh://user@host` is resolved by the Docker CLI itself using normal SSH key/config, so there's no separate tunneling code to maintain. Hosts are defined in `config/hosts.json` (gitignored, copy from `hosts.example.json`), each with an optional `edges: [{from,to,label}]` list for relationships Docker itself can't see. Hosts can also be added/edited/removed live from the Settings panel (admin-only, `/api/settings/hosts`) — `server/hosts.js`'s `saveHosts()` rewrites the file and the route calls `metricsCollector.addHost/removeHost` and `eventWatcher.addHost/removeHost` for just that one host, so a new SSH host starts being monitored immediately with no process restart (edits are a `removeHost` + `addHost` pair rather than an in-place update, since reconnecting is simpler than diffing what changed). The image's `/etc/ssh/ssh_config.d/opendockwatch.conf` (written by the `Dockerfile`) turns on SSH connection multiplexing (`ControlMaster`/`ControlPersist 10m`) globally, so the several `docker` calls each remote host gets per 5s poll ride one persistent SSH connection instead of opening their own — pure infra, no code involved, since the CLI just shells out to system `ssh`. `checkHost`/`testHostConnection` (the latter backing Settings' "Test connection" button, surfacing real `ssh`/`docker` stderr instead of a boolean) get a longer timeout for SSH hosts than the local-socket default (`checkTimeoutMs()`), since that's the one call that has to pay a slow link's connection-setup cost before multiplexing makes everything after it cheap.

**`server/logger.js`** writes structured single-line audit/debug events (`[opendockwatch] [LEVEL] event key=value ...`) to stdout/stderr - picked up by `docker logs` automatically and by the app's own Log Viewer level filters. Nothing in the server writes to `console` directly except `logger.banner()`, the ASCII boot banner (art, not an event - it's the visual marker for where a restart begins when scrolling back through `docker logs`, and `app.started` carries the same data as a real event immediately after). A failure that only reaches `console.error` is invisible to the Log Viewer's level filters, which is the entire reason this module exists, so new error paths go through it. Never log secrets: `alerts.webhookScheme()` is the only sanctioned way to put a webhook URL in a log line (`discord://…`), shared by `alerts.js` and `index.js`'s settings route so the redaction can't drift between them.

**What gets logged, and the rule for adding more.** The log's job is to let someone reconstruct what the app did without attaching a debugger, so it covers **state transitions and discrete operations, never per-poll steady state** - a line every 5s per host would bury the ones that matter. Currently: lifecycle (`app.started`/`app.shutdown`), auth success/failure, every container action as a **pair** (`container.<action>.requested` before the CLI call, `container.<action>` with `tookMs` after - `docker stop` can sit through its full 10s SIGTERM grace, and logging only on completion left a pressed button invisible until it finished), log-stream and event-stream open/close with `heldSec` (each one holds a `docker logs -f` child and one of the browser's ~6 connections - see the connection budget above), `logs.download` (container logs carry secrets, so exporting them is audit material), host watch start/stop, `docker events` stream start/restart-backoff/stop, host reachability in **both** directions (`host_unreachable` fires an alert, `host.reachable` only logs - nobody wants a webhook for good news, but "did it come back?" has to be answerable), webhook delivery success as well as failure, `alert.muted` for a suppressed alert, `db.pruned` with per-table row counts when the hourly prune actually deletes something, and every failure path. Steady-state polling stays silent by design.

**Pure parsing/graph-building functions are exported from `server/docker.js`** (`parseByteString`, `parseLabels`, `parseHealth`, `networkEdges`, `dependsOnEdges`, …) specifically so `test/*.test.js` can unit-test them directly without mocking `child_process`. When adding docker-CLI-output parsing, keep the parsing pure and separate from the function that actually shells out, and export it.

**Two long-running background jobs, started in `server/index.js` on boot:**

- `eventWatcher.js` — one persistent `docker events` process per host (auto-restarts with exponential backoff on exit/error, capped at 30s). The pending restart is tracked on the watcher's state so `removeHost` can cancel it, and the restart itself re-checks that the map still holds _that same state object_ before reviving anything: an edit through Settings is a `removeHost` + `addHost` pair, so a backoff elapsing after one would otherwise restart the old watcher against the new entry and leave two streams running for one host - every event inserted, published and alerted on twice, with the newer child orphaned where no `removeHost`/`stop` can reach it. Each parsed event line fans out to three places through `ingestEvent`: `db.insertEvent` (persistence), `broadcaster.publish` (live SSE push to the Activity tab), and `alerts.handleEvent` (rule engine). This is the single ingestion point for all event-driven alerts (`container_crashed`, `crash_loop`, `unhealthy`). **`ingestEvent` must never throw**, and that is the reason it exists as its own function rather than as the body of the loop: it runs inside the child process's stdout `'data'` handler, an exception out of an EventEmitter listener is an `uncaughtException`, and `index.js` calls `process.exit(1)` on those — so one `SQLITE_BUSY` on one event line would end monitoring for every host, which is precisely the trade `unhandledRejection` is deliberately not making three paragraphs up. The `try`/`catch` is per event so a bad line doesn't cost the rest of the chunk it arrived in either, and it's exported purely so `test/eventWatcher.test.js` can assert the swallow-and-log contract by mocking `db.insertEvent`/`alerts.handleEvent` to throw, without spawning a real `docker events`. Note that this is about _thrown_ errors only: writing to an SSE response whose client has gone is not one of them — `res.write` on an ended or destroyed `ServerResponse` returns `false` and drops the data rather than throwing or emitting, verified on Node 22 for socket-destroy, write-after-`end`, and a client RST mid-burst, so `sse.js` needs no guard around its write.
- `metricsCollector.js` — polls every host every `POLL_MS` (5s) for containers/stats/info, plus disk usage every 60s; keeps an in-memory snapshot per host (`getSnapshot(hostId)`, used e.g. to avoid an extra docker call just for a container's name in audit logging) and writes samples to sqlite for history charts. Also feeds the threshold-based alerts (`container_cpu`/`container_mem`/`host_cpu`/`host_mem`/`docker_disk`, `handleSample`/`handleHostSample`/`handleDiskUsage` in `alerts.js`).

**Staying responsive is a design constraint, not an optimization** — the failure this app has to avoid is the one where it's still running but unusable, since that's the one a container restart is the only cure for. Three rules follow from it, and new code has to keep them. (1) _Never leave a request unanswered._ A browser allows ~6 connections per origin over HTTP/1.1 and this app permanently holds some of them open for its SSE streams, so a request that hangs is a connection slot lost — enough of them and the tab can't issue any request at all, including the ones a reload needs, and that state outlives the server recovering. `requestTimeout` in `index.js` answers 504 rather than hanging (SSE routes exempt, matched by path suffix; a late real response is dropped rather than thrown, since a second send would otherwise destroy an already-answered connection), `api.js` puts an `AbortSignal.timeout` on every `fetch`, and `docker.js`'s `run()` escalates SIGTERM→SIGKILL so a CLI blocked on a wedged daemon socket can't leave its promise unsettled forever. (2) _Don't multiply work per viewer._ The collector already has containers/stats/reachability/hostname in its snapshot; routes serve from it rather than shelling out per request (`?fresh=1` on `/containers` is the one opt-out, for the refetch right after a start/stop where up-to-`POLL_MS` staleness is visible), `getTopology` caches its three label/mount `docker ps` calls against the container-id set (they can't change without the container being recreated under a new id), and `run()` caps concurrent CLI processes. Client-side, the poll loop is a chained `setTimeout` and never `setInterval` — a cycle awaits five or six requests, so on a slow host an interval starts a second cycle before the first finishes and they stack — plus a backoff on failure and a full stop while the tab is hidden. Anything long-lived that reconnects needs a budget too: `logStream.js` gives up after repeated disconnects with no line in between, since EventSource retries forever and each retry spawns a `docker logs` server-side. **The ~6 connections are a budget to be spent deliberately, and log streams are what spend it** — the Logs tab alone can hold four. So a stream only runs in the views its component is actually part of: `app.js`'s `detailPanelVisible` gates the detail panel (and `setView` closes the bottom Log Viewer) to List and Flow, the Logs tab owns its panes, Activity owns its event stream — worst case four, never six, leaving two for the poll loop. Streams also suspend themselves after `HIDDEN_SUSPEND_GRACE_MS` in a backgrounded tab (`logStream.js`), returning both the connection and the server-side `docker logs -f` child; the grace exists because resuming re-tails and therefore resets the pane, which is wrong for a two-second tab switch and right after a real absence. Raising `MAX_OPEN_LOG_PANES` spends that margin directly. (3) _Recover without a human._ `watchdog.js` measures how long since `metricsCollector` last _completed_ a poll — deliberately a property of the loop, not of Docker, since an unreachable host still completes its poll — and reports unhealthy on `/healthz` then exits after a grace period. The exit is the part that matters: Docker never restarts a container for being unhealthy, and `restart: unless-stopped` only reacts to the process exiting, so self-exit is the only path back. It's injectable (clock, `exit`, timer) and unit-tested in `test/watchdog.test.js`. A second, purely diagnostic signal - event-loop lag, how far the fixed-interval check timer drifts - never triggers the exit on its own (a one-off spike during the hourly prune is normal); it exists because better-sqlite3 is synchronous, so a slow bind-mounted volume can block the event loop long enough to stall the HTTP server, and it's worth knowing about even though it isn't the exit condition. `uncaughtException` exits for the same reason; `unhandledRejection` only logs, since one failed docker call or db write shouldn't take monitoring down for every host.

**`alerts.js`** is the rule engine plus webhook delivery. Every alert setting (webhook URL/format, CPU/mem/disk thresholds) follows the same pattern: an `.env` default, overridable from the DB via the admin Settings UI (`PUT /api/settings/...`), with the DB value always winning when present — even an explicit empty/0 to deliberately disable something `.env` configured. See the README's Alerts section for the full rule table and webhook URL-scheme routing. **Per-container overrides** live in the `container_alert_rules` table (`server/db.js`): an ordered, first-match-wins list matched by container name (case-insensitive substring) or an exact compose project, optionally scoped to one host. `resolveContainerConfig({hostId, containerName, composeProject}, ctx)` walks it — the matched rule's non-null fields override the global threshold config for that call, with anything it leaves null still inheriting the global value, and its `mutedRules` naming which of `container_crashed`/`crash_loop`/`unhealthy` are suppressed for that container. No match at all (the common case) returns the global config untouched. **The reads it needs are hoisted to one per poll, not one per container**, via `alertContext()` (`{global, rules}`): `metricsCollector.pollHost` builds one and passes it to every `handleSample` in that poll, the same collect-then-act shape the metrics transaction above already uses. Per-container was measured at ~30µs a call with 10 rules configured — 6ms of synchronous event-loop time every 5s at 200 containers, four times what batching the metrics write saved, and growing with rules × containers × hosts. It's built lazily (skipped entirely when every container on the host is label-disabled) and `ctx` is optional, so the event path and the tests still resolve per call. On the event side that's the right granularity anyway: `mutedByRule` runs only on a `handleEvent` call actually about to fire, never once per `docker events` line, and it **logs an `alert.muted` line when it suppresses one** — `fire()` always leaves an `alert.fired` trace, so without that a muted alert would be the one outcome with no record at all to answer "why didn't this alert?". This is deliberately separate from the `opendockwatch.alerts=off` Docker label, which stays exactly as narrow as before — checked first, unconditionally, before any rule lookup, and still only gates `handleSample`'s threshold rules; muting an event rule per container goes through the rules table instead of widening what the label means. `composeProject` reaches both call sites cheaply: `docker.js`'s label parsing already put it on every container object (forwarded into `handleSample` via `metricsCollector.js`'s `alertSamples.push`), and `docker events`' `Actor.Attributes` carries the same label set (`eventWatcher.js`'s `parseEventLine` reads it alongside `name`/`exitCode`), so neither needs an extra docker call.

**The Settings panel** (`public/js/components/`) is a tab-strip shell (`SettingsPanel.js`) over five independent sections — `SettingsGeneral.js`, `SettingsWebhook.js`, `SettingsThresholds.js`, `SettingsContainerRules.js`, `SettingsHosts.js` — each owning its own fetch/save/error/status state rather than one file juggling five prefixed copies of the same shape (the pre-split version's `webhookSaving`/`thresholdsSaving`/`hostsSaving` etc.). Tabs swap via `v-if`, not `v-show`: each child is a cheap admin-only GET-config panel with no stream to preserve across a switch, so remounting fresh on every click keeps data always-current (add a host, flip to Container Rules, its host dropdown already has it) at the cost of one harmless refetch. The repeated saving/error/status try/catch/finally across all five lives once in `public/js/lib/settingsSection.js`'s `withStatus(vm, savingField, fn)` — not pure (it mutates the passed component), so it sits alongside `logStream.js` as a shared-but-not-unit-tested helper rather than in the pure-logic part of `lib/`. `SettingsGeneral.js` is the odd one out among the five: its one setting (the default landing tab, `DEFAULT_VIEW`/`server/index.js`'s `getDefaultView()`) has no secrets and applies to every role, so unlike the other four its `GET /settings/default-view` route is still `requireAdmin` for symmetry with the panel it lives in (only admins ever open Settings), but the _value_ itself reaches every logged-in user for free as a `defaultView` field on `GET /api/session` - `app.js`'s `mounted()` calls `setView(session.defaultView || 'list')` once hosts are loaded (not a bare assignment, so a configured `'flow'` default also fires `fetchTopology()` immediately, the same as clicking the tab by hand).

**`server/db.js`** is a single `better-sqlite3` database (`data/opendockwatch.db`) holding metrics history, events, audit log, alerts, settings overrides, and doubles as the express-session store. Every query is prepared once into the `stmts` map at module load rather than per call - put new ones there too. **Anything written once per container per poll goes through a `db.transaction()`, not a loop of individual `.run()` calls** - that's `insertContainerMetrics`, the one write on that path. WAL mode still runs at SQLite's default `synchronous=FULL`, so a per-row `.run()` is a full commit and an fsync each: measured on an SSD that's 2.65ms → 0.70ms for 50 containers and 10.58ms → 1.45ms for 200, and since better-sqlite3 is synchronous the saving comes off the event loop directly - the same event loop `watchdog.js` watches for lag, and the same lag a slow bind-mounted volume already makes worse. Atomicity comes along for free and is worth keeping: a malformed sample rolls the whole poll back rather than writing half an instant into the history charts (`test/db.test.js`). The ordering in `metricsCollector.pollHost` is deliberate - collect every sample, write them in one transaction, _then_ run `alerts.handleSample` over them. Alerting per container inside that loop would have put the rule engine's own `alert_breaches` writes, and `fire()`'s fire-and-forget async webhook, inside the metrics transaction; better-sqlite3 transactions are synchronous and must not have an `await` suspend inside them. The two history queries downsample into `@bucketMs`-wide windows using `BUCKET_EXPR` from `server/metricsHistory.js`, which is written as `ts - (ts % @bucketMs)` for a reason that will bite anyone who "simplifies" it back: better-sqlite3 binds every JavaScript number as REAL, SQLite's `/` is float division the moment an operand is REAL, and so the obvious `(ts / @bucketMs) * @bucketMs` returns `ts` unchanged and the GROUP BY groups nothing at all. `%` coerces to INTEGER regardless of binding. The same module's `withIoRates` then turns each bucket's `MAX(net_rx_bytes)` and friends into per-second rates by differencing consecutive buckets over their real elapsed time (the columns hold cumulative counters, so they're meaningless plotted raw), reusing `docker.js`'s `computeRate` so a container restart's counter reset comes back as `null` rather than a negative rate. The history queries themselves use `MAX`, not `AVG`, for those same I/O columns - a container that restarts mid-bucket makes `MAX` that bucket's pre-restart peak, so the following delta goes negative and is reported as `null`, the correct read on a counter reset. Both are pure and unit-tested in `test/metricsHistory.test.js`. Old rows are pruned on the retention windows (`METRICS_RETENTION_DAYS`/`EVENTS_RETENTION_DAYS`) by `metricsCollector.start()`, once at boot and hourly after that; the boot run matters because an instance that restarts more often than the interval would never reach the first tick. Indexes are chosen against the query's whole shape, `ORDER BY` included, not just its `WHERE` columns: `events` carries both `(host_id, container_id, ts)` for the per-container restart counts and `(host_id, ts)` for `getEvents`, because the first can only use its leading column when `container_id` isn't in the predicate, leaving SQLite to sort the host's entire retained history through a temp B-tree to answer a `LIMIT 200` — 14.1ms against 300k rows, versus 0.181ms once the second index turns it into a walk that stops at the limit. `EXPLAIN QUERY PLAN` naming a `USE TEMP B-TREE FOR ORDER BY` is the tell. No migration framework — schema is a set of `CREATE TABLE IF NOT EXISTS` statements run at startup; add new tables the same way, and new indexes too (unlike `ALTER TABLE ADD COLUMN`, `CREATE INDEX IF NOT EXISTS` in that block does reach an existing database on upgrade). A new _column_ on an existing table needs both: add it to the `CREATE TABLE` (for a fresh database) and a `try { db.exec('ALTER TABLE ... ADD COLUMN ...') } catch {}` right after the schema block (for an existing one upgrading — `IF NOT EXISTS` only skips the whole statement, it doesn't retroactively add columns to a table that already exists without them).

**Auth (`server/auth.js`)** is cookie-session based with two roles: admin (full control) and an optional read-only viewer (`VIEWER_USER`/`VIEWER_PASS_HASH`). Role enforcement is server-side (`requireAdmin` middleware on every mutating route) — the viewer role hides buttons in the UI too, but a request forged around the UI still gets a 403 from the server. `test/index.test.js` enforces that structurally rather than by a hand-maintained list: it walks the api router's own stack and fails if any non-GET route lacks `requireAdmin`, so a mutating route added later can't quietly ship without it. Read-only is not the same as "may read everything", though, and one route needs the distinction spelled out: `GET /containers/:id/inspect` returns `docker inspect`'s `Config.Env`, which is where DB passwords and API keys actually live, so a non-admin session gets it through `maskEnvValues` (`docker.js`) — variable names kept, values replaced, `envMasked: true` on the response so `ContainerDetail` can say why rather than look like every value is blank. `maskEnvValues` splits on the _first_ `=` only, or a secret containing one (base64 padding, a connection string with `?ssl=true`) would leak its tail; a genuinely empty value stays visibly empty instead of being dressed up as a hidden one. Login calls `req.session.regenerate()` before marking the session authenticated — `saveUninitialized: false` means there's rarely a pre-auth session to fixate, but that's a property of the current config rather than a guarantee, and the guarantee should come from the login itself.

**Two endpoints sit outside the `requireAuth` router and are gated differently.** `/healthz` is deliberately open and deliberately narrow (see the Dockerfile's HEALTHCHECK). `/metrics` can't use cookie auth because Prometheus can't, so it takes a shared secret in `METRICS_TOKEN` — and an unset token means the endpoint **404s**, not that it serves without auth. That response enumerates every container name, compose project, usage figure and restart count across every host, which is inventory disclosure to anything that can reach the port, so the unconfigured state has to fail closed; a scraper sets the variable, nobody else needs the endpoint at all. The comparison goes through `crypto.timingSafeEqual` (length checked first, so only the token's length is observable) since this is the one credential that travels in a URL.

**Security headers** are five fixed values set by one middleware in `index.js`, ahead of everything including the static mount, rather than a helmet dependency. CSP is the load-bearing one, and the directive doing the work is the _absence_ of `'unsafe-inline'` from `script-src`: container log output reaches the DOM through `v-html` in three components, and since `innerHTML` never executes a `<script>` tag anyway, the real injection vector there is an inline handler like `<img onerror=…>` — which is exactly what that omission blocks. This is why `public/login.html`'s submit handler lives in `public/js/login.js` instead of an inline `<script>`, and why a test asserts both that it stays external and that `script-src` never gains `'unsafe-inline'`. If a future inline block "needs" it, put the script in a file instead.

`script-src` does carry **`'unsafe-eval'`, and removing it blanks the entire app** — verified in a real browser, not assumed. There's no build step (a deliberate constraint, see the frontend section), so every component ships a `template` string that Vue compiles in the browser via `Function(code)()` at `vue.global.prod.js`'s single `Function(` call site; under a CSP without `'unsafe-eval'` that throws and every component renders empty, silently, with nothing useful in the console. The only ways off it are precompiling templates (a build step) or hand-writing `render()` functions — both are much larger changes than the header, and `'unsafe-eval'` doesn't re-enable inline scripts or event handlers, so it costs little against the threat this CSP was added for. `style-src` carries `'unsafe-inline'` for the same no-build-step reason and can't avoid it — `format.js`'s ANSI colour spans and `graph.js`'s cytoscape HTML labels both emit `style="…"` into parsed HTML — and `img-src` allows `data:`/`blob:` for the graph's inline SVG icons and the PNG export. Not set: HSTS, which does nothing over the plain HTTP many deployments use behind a proxy and belongs on the proxy terminating TLS.

**`requireHost` attaches the resolved host as `req.odwHost`, and the name is load-bearing.** Express defines `req.host` as a **getter-only** property returning the Host header, so `req.host = hostObject` silently no-ops in sloppy mode and every handler downstream reads back a string like `"localhost:3000"` instead. Nothing throws and nothing looks wrong locally: `hostArgs()` is `host && host.dockerHost ? ['-H', host.dockerHost] : []`, and a string has no `.dockerHost`, so it falls through to the empty-args case — the **local socket**. A single-local-host install therefore behaves perfectly while every remote host's containers, logs, stats, inspect and start/stop/restart routes quietly run against the wrong daemon. `test/index.test.js` drives a probe route through the real `requireHost` and asserts the handler receives an object, plus asserts express's own `req.host` is still unwritable so the day that changes is visible rather than assumed. Never name request-scoped state after something express already owns.

**Route input handling (`server/index.js`)** — nothing from the URL reaches sqlite or the docker CLI raw. `intParam` defaults and clamps numeric query params (`Number('abc')` is `NaN`, which better-sqlite3 rejects outright with "datatype mismatch" instead of treating as absent, so an unvalidated `?limit=`/`?since=` 500s the request rather than falling back), `tailParam` allows a positive integer or docker's literal `all` (the log viewer's "All lines" option), and `requireContainerId` rejects anything that doesn't look like a container id - nothing runs through a shell, but an id starting with `-` would be read by docker as a flag rather than a container. Anything a route throws that it doesn't handle itself lands in the terminal error handler registered after the router, which logs it and returns the message alone; without it express's default handler answers, and that one puts the whole stack trace in the response body unless `NODE_ENV=production`.

**Frontend is Vue 3 (Options API)**, no SFCs/build step — `public/js/**` is loaded as native ES modules via `<script type="module">`. `app.js` is the root component (~400 lines): session/role bootstrap, host list/selection, the 5s polling loop, containers/stats/alerts state, view switching, and `doAction`. Everything view-specific lives in `public/js/components/`: `SparkTile`/`HostCard` (the host-usage tiles), `ContainerList`/`ContainerDetail` (the List view and its detail panel), `MiniSpark`/`ContainerMetricsModal` (the per-container sparkline in each row and the full-history view it opens), `LogViewer` (the full-size log panel), `ActivityView` (the alerts/events tab), `SettingsPanel` (webhook/threshold/host config), and `FlowView` (the Cytoscape graph/tree view). `SparkTile` is the shared chart for both the host tiles and the modal, which is why its second series is `secondarySamples`/`secondaryLabel` rather than anything host-named - it carries the host total behind Docker's own usage on the host card, and the tx half of an rx/tx pair on the modal's I/O charts - and why `slotCount` is a prop: the host card's live window and the 1h/24h/7d ranges hold different numbers of buckets. **`HostCard` has the same 1h/24h/7d range strip as `ContainerMetricsModal`, plus a fourth `live` option, and the strip only renders in fullscreen** — a tile sharing a row has no space for it. `live` is the default and reads the root's `metricsHistory` prop (the rolling window the root already refetches every poll), so the card costs no extra request until someone actually widens the window; the other three re-read sqlite over the same `GET /metrics/history` the modal uses, minus its `containerId`. Every series reads one `activeHistory` computed rather than the prop directly, so a range switch moves both tiles together and they can't end up drawing different windows. Same two guards as the modal, plus one: a landing response is dropped if either the range **or the host** has changed since it was issued, and only `1h` keeps a refresh timer (24h/7d buckets are 5 and 30 minutes wide, so a 5s refetch would redraw an identical chart). Leaving fullscreen resets to `live` — the strip is the only way back, so a non-live range would otherwise be stranded with its timer still running behind a tile that can't show it. The `system_*` columns behind the "host total" overlay are `AVG`d by the same query at every bucket width, so that series works at 7d exactly as it does live. `MiniSpark` is deliberately not a variant of it; sharing that component for a table cell would mean `v-if`-ing away five of its six parts. Panels that are meaningfully transient (`LogViewer`, `ContainerDetail`, `ActivityView`, `SettingsPanel`) mount via `v-if`, each time fresh, so their own `mounted()`/`beforeUnmount()` own their stream or fetch lifecycle instead of the root orchestrating it (e.g. `ContainerDetail` watches its own `container.id` prop to reset/refetch on a same-mount container switch, since watching the whole `container` object would refire on every 5s poll — the root replaces its `containers` array wholesale each poll, so the object reference changes even when the id doesn't). `ContainerList` and `FlowView` instead stay mounted via `v-show` across List/Flow tab switches, since there's nothing external to tear down and rebuilding a Cytoscape graph from scratch on every switch would be wasteful for a host with many compose projects — they watch their own props (`topology`, `hostId`, `stateFilter`) to re-render instead of remounting. State that's genuinely shared across views (`selectedContainerId`, `selectedHostId`, `alerts`) stays in the root and flows down as props, with children emitting events back up (`select`, `action`, `close`, `open-log-viewer`, ...) rather than reaching into siblings; `fullscreen` on both `LogViewer` and `FlowView` is the one exception worth calling out — it's a real `v-model` (not fully internal) because the root's own layout needs to know about it directly, to hide the host card and other panels. Two sources feed the container charts and they are not interchangeable: the List row's `MiniSpark` reads the root's live in-memory buffer (`recordMetricsSample`, ~2 minutes, empty after a reload), while the modal reads the persisted sqlite history over `GET /metrics/history?containerId=`. Samples are right-aligned into the chart's slots by `padSlots`, so a series shorter than the window - a container created ten minutes ago, or a buffer still filling - draws in the right-hand part of the chart and grows leftward, rather than stretching to fit. `public/js/lib/` holds pure, unit-tested logic shared across components: `spark.js` (sparkline coordinate math, used by `SparkTile` and `MiniSpark`), `logSync.js` (the binary search behind the Logs tab's multi-pane scroll sync), `logLines.js` (per-line log decoration/filtering — see below), `format.js`'s `eventSeverity` maps docker event actions onto the same `critical`/`warning`/`ok` vocabulary the alert rows use, so one colour language covers both Activity columns — it drives both the event rows' left accent and their badges. Unlisted actions (`exec_create`, `attach`, `commit`, `resize`, …) stay deliberately neutral: colouring routine noise would drown the handful of rows worth spotting. `health_status:` is special-cased and tests the **negative first**, since `"unhealthy".includes("healthy")` is true and the obvious order gets the two exactly backwards. Severity is attached once per event at ingest (both `loadEvents` and the SSE `onmessage`), never derived in the template, for the same reason `logLines.js` exists — a method call from a `v-for` re-runs on every render. The row accent is an `inset` box-shadow on the first cell rather than a `border-left`, because the events table is `border-collapse` and a per-cell border fights the collapsed grid. `activityCounts.js` (`groupCounts`, behind the Activity tab's per-kind header badges — alerts by rule, events by action; counted off the _searched_ lists so the badges always describe the rows on screen, sorted by count with a `localeCompare` tie-break that is the load-bearing part, since without it two kinds on the same count swap places as rows stream in and a badge row that reshuffles while you read it is worse than none, then capped with the remainder returned as a `+N more` badge), `logBuffer.js` (`pushCapped`, the append-and-trim shared by the visible line array, a paused pane's held buffer, and the drain of one into the other — pure and unit-tested precisely because the invariant that matters spans all three: `test/logBuffer.test.js` asserts that pausing and resuming lands on the same buffer as never pausing, cap included), and `logStream.js` (the EventSource/buffering factory both `LogViewer` and `ContainerDetail`'s log preview build on; the one module that isn't purely pure, since it also owns the hidden-tab suspension, which is why `doc`/`EventSourceImpl`/`schedule` are all injectable). `logLines.js` exists because per-line work has to happen **once at append**, not per render: `decorateLine` derives a line's level, timestamp and no-filter HTML when it arrives, and `selectLines` reuses that cached `baseHtml` unless a filter is actually active. Deriving it per recompute cost ~4.4ms for a 3000-line pane (~17.7ms across four, past a 60fps frame's 16.7ms); caching brings a pane to ~0.16ms. `ContainerDetail` had a worse variant — it called `highlightLine` from a template _method_, so the work re-ran on every render including the 5s stats poll — and its preview is capped at `PREVIEW_TAIL`, not `MAX_LOG_LINES`. The same module also owns the Log Viewer's search cursor (`hitIndexFor`/`stepHitId`), and the rule there is that **the cursor is a line id, never a position**: `appendLines` trims the buffer from the front once a pane passes `MAX_LOG_LINES`, so every appended line shifts each index down by one and a positional cursor quietly comes to name a different line — the highlight walks the hit list on its own, with no user action, while the "26 / 30" counter keeps reporting the position it started from. It's invisible in a short pane and constant in a busy tailing one, which is why it shipped. `hitIndexFor` resolves the id back to a position on every render (a computed, so once per render pass and not once per line) and falls back to the first hit when the parked-on line has aged out or been filtered away; `LogViewer` clears the cursor in `startStream`/`onReset` because `logStream` restarts its ids from 0 for a new source, so a cursor held across a reconnect would otherwise point at whatever unrelated line inherits that id. Clicking a hit line sets `revealAll` rather than clearing the filter: `selectLines` gets a `hideNonMatching` option, and with it off, `filteredLines` renders every line (context included, matches still highlighted, non-matches reusing cached `baseHtml` so this isn't the O(n) `highlightLine` cost again) while `matchLines` - always computed with `hideNonMatching: true` - keeps the hits box counting and stepping through matches only, since the two arrays diverge once revealAll is on. Typing a further filter character (or toggling regex mode) drops `revealAll` back to false, since a new search term means "narrow down again"; clearing the filter to empty just turns `searchActive` off, which is what actually hides the box and the highlighting. Supporting modules: `api.js` (the only place `fetch` is called, wraps 401→redirect-to-login and JSON/error handling), `format.js` (pure display formatting: ANSI-to-HTML for colored logs, byte/timestamp formatting, log-level detection, badge/icon lookups), `constants.js` (poll intervals, history lengths), `graph.js` (all Cytoscape.js flow-view logic: layout via dagre, edge/node styling, compose-group collapse/expand via cytoscape-expand-collapse, and `localStorage`-backed persistence of dragged node positions + camera zoom/pan + collapsed group ids, keyed per host so a reload doesn't reset your arrangement — owned by `FlowView`, which is the only component that imports it). The Flow view has two render modes sharing the same topology data: graph mode (`buildElements`, compose-group boxes, network/depends-on/manual edges) and tree mode (`buildTreeElements`, an ArgoCD-style `project → container → network/mount` DAG with no compound groups, network/volume pills deduped globally so shared infrastructure gets one node with multiple incoming edges). A tapped tree-mode pill (`proj:`/`net:`/`mount:` id) is filtered out inside `FlowView` before it ever reaches the root — routing it into `selectedContainerId` would trip `ContainerDetail`'s watcher into fetching `docker inspect` for a fake id — so it's kept as `FlowView`-local state (`pillSelection`), used only for fading and the tap-info bar. Container nodes are shared between both modes via `containerNodeEl`. Positions/camera are keyed per host _and_ per mode (`odw:flow:positions:<mode>:<hostId>`, etc.) since a dagre layout from one mode is meaningless in the other; the mode choice itself is also saved per host. Vendor libraries (Vue, Cytoscape, dagre, html2canvas-pro, cytoscape-expand-collapse) are checked into `public/vendor/` and loaded as global `<script>` tags, not npm/bundled — `eslint.config.js` declares them as browser globals for that reason. html2canvas-pro exists specifically because `cy.png()` only rasterizes cytoscape's own `<canvas>`, not the `cytoscape-node-html-label` DOM overlay that actually renders node content (name, icons, CPU/RAM bars, badges) — Flow view's "Export PNG" screenshots the real on-screen DOM instead (this means it has a fixed pixel resolution to manage - see `EXPORT_SCALE` and the container-resize dance in `exportPng`: html2canvas just copies cytoscape's existing CSS-pixel-resolution canvas bitmap, so a higher `scale` merely stretches an already-low-res source, which is why `exportPng` instead temporarily renders into a container `EXPORT_SCALE` times larger - scaling container size, zoom, and pan by the same factor is a uniform scale-up of `renderedX = graphX * zoom + pan.x`, so it frames the exact same crop with `EXPORT_SCALE` times as many real pixels to draw into). "Export SVG" sidesteps that entirely: `extractSvgGeometry` (impure, reads the live `cy` instance's positions/classes/data) feeds `renderSvg` (pure, geometry → an `<svg>` string, unit-tested the same way `buildElements` is) which hand-draws the same node/edge visual design `CY_STYLE` and the HTML templates already encode - no dependency on the DOM overlay or a rasterization step, so there's no resolution ceiling to manage for a host with a lot of compose projects. expand-collapse physically removes a collapsed group's children from the graph, so `updateGraph`'s poll-driven diff skips them entirely while hidden rather than touching them (an earlier version briefly expanded/re-collapsed every poll to keep their data fresh, but that visibly flickered the collapsed box every 5s) — `expandcollapse.afterexpand` re-syncs a group's children from the latest poll's data the moment it's actually opened instead. Below `COMPACT_ZOOM_THRESHOLD` (graph.js), nodes render a compact HTML label (state/icon/name only, no metric bars) and shrink to match via a per-element style function on node height keyed off a `compact` data flag - flipped synchronously on every `viewport` event (immediate, unlike the debounced viewport-position save alongside it) so it reads as a direct consequence of zooming.

**The Logs tab's multi-pane scroll sync** (`LogsView.js`/`LogViewer.js`): a `viewMode` toggle at the top of the side list picks between `'single'` (one pane; clicking a row swaps its container, clicking the open row closes it - `openIds` never exceeds length 1) and `'multi'` (clicking a row toggles it open/closed, `openIds` capped at `MAX_OPEN_LOG_PANES`) rather than always replacing a single selection, so up to four `<log-viewer embedded>` panes can render side by side. Switching `'multi'` → `'single'` with more than one pane open collapses `openIds` down to the main pane if one was set, else whichever was opened most recently, and clears `disabledSyncIds`/`mainId`/`joinTsMsById` along with it - none of those apply to a lone pane. `setViewMode` is a no-op when nothing needs to collapse (0 or 1 panes open, or already in that mode). Each pane's `onScroll` emits `scroll-sync` with `{containerId, tsMs}` - the epoch-ms timestamp of whichever line is now at the top of its viewport - only when the _user_ scrolled it (`_programmatic` guards the case where `scrollToTimestamp` itself moved the pane, so a sync-driven scroll doesn't re-broadcast and ping-pong forever). `LogsView`'s `broadcastFrom` is the single place a sync event actually moves other panes: peer-to-peer by default (whoever scrolls drives the rest), but designating one pane `mainId` switches the group to leader-follower (only the main's scrolling drives anyone - `broadcastFrom`'s first check enforces this even though every pane's events keep arriving). `disabledSyncIds` lets a pane opt out entirely, in both directions (it doesn't broadcast and isn't moved). `toggleSync`/`setMain` broadcast the affected pane's _current_ position immediately when re-enabling sync or marking main, rather than waiting for its next scroll event - that's what lets you scroll a pane to a spot of interest while desynced, then have the rest jump to match it the moment you flip sync back on. `lastSyncTsMs` is kept so a pane opened after the group has already scrolled somewhere joins at that same timeframe instead of live-tailing at the bottom while its siblings look at history. `LogViewer`'s `embedded`/`multiPane`/`wrap` props split standalone mode (root overlay, `fullscreen` v-model, its own wrap toggle) from embedded mode (a `LogsView` pane: no fullscreen, `wrap` fed from one tab-level toggle instead of repeating it per pane) - `multiPane` is independent of `embedded` and only turns on once 2+ panes are open, since a single embedded pane has no close/sync/main controls to show (picking a different row is the close equivalent).

**The log panel header is two rows, and its breakpoints are measured rather than guessed.** The container name owns the top row alone — `white-space: nowrap` with an ellipsis and the full name on `title`, since compose-prefixed names run long and used to wrap to two lines in a side-by-side pane. Row two is the status badge pinned left with the control strip pushed right by `margin-left: auto`. The badge is **always present** and reads `▶ active` / `⏸ paused` / `⏸ suspended` from one `statusBadge` computed: "active" is only legible as a state because it sits exactly where "paused" would, so a streaming pane says so rather than saying nothing. Manual pause outranks suspension, because if the user paused it that's the answer to "why isn't this moving". Three `@container log-panel` tiers, each set from a measured natural width (the strip needs 993px in a multi-pane header and 1140px in a standalone one, which also carries Matches/Fullscreen/Wrap/Close): **≤1150px** drops the button labels and narrows the search box to 150px — this is the one that matters, since two panes on a 1080p screen land at ~985px each and were wrapping; **≤900px** swaps the four level buttons for the `☰ Levels` dropdown, for the 2×2 grid at ~865px; **≤760px** finally collapses the search box to an icon that expands on focus. That last one is deliberately still 760 rather than folded into the tier above — between 760 and 900 the level dropdown alone buys back enough, and seeing what you filtered on is worth more than the 120px. Below ~800px it does wrap to two control rows; that's accepted degradation, not a target. Re-measure rather than eyeball if controls are added: one more button moves every boundary.

**Pause and the match strip (`LogViewer.js`).** Space toggles a manual pause on the log body. It deliberately does **not** stop the stream: the EventSource stays connected and incoming lines go into a non-reactive `_pendingLines` buffer capped at the same `MAX_LOG_LINES`, so resuming shows what actually arrived instead of paying for a reconnect and a re-tail (and a container left paused for an hour can't grow the buffer without bound). The keydown listener is on `document`, so it's live without the pane needing focus first — guarded against firing while typing (`INPUT`/`TEXTAREA`/`SELECT`/`BUTTON`/`contenteditable`), against any modifier, and with `preventDefault` so space doesn't also scroll the page. Every open pane carries that listener, so in multi-pane the **hovered** pane takes the keypress or one space would pause all four; a lone pane needs no hover. It's distinct from `suspended` (the background-tab connection handback) and badged differently, since "I paused this" and "the tab did" are different states — and `onReset` force-unpauses, because that path has just wiped the buffer and staying paused would leave an empty pane that never fills, which reads as broken rather than paused. **The match strip** is a filtered-results pane, the long-standing log-viewer pattern of listing the hits separately and clicking one to jump to it: `matchLines` (which already exists for the hits counter) rendered as a short scrollable list under the log body, each row clicking through to `selectMatch` — the same reveal-in-context path clicking a hit line in the body takes. Single-pane only (`matchPaneVisible` is `showMatchPane && !multiPane`): a quarter-width cell in the 4-up grid has no vertical room to give up. **While it's open the log body stops narrowing to matches** — `showAllLines` is `revealAll || matchPaneVisible`, so the strip makes reveal-mode the default rather than something you get only after clicking a hit. Filtering both would be redundant, and worse than redundant: the strip's whole purpose is jumping into surrounding context, which a filtered body doesn't have. The level toggles still apply — those aren't search. Rows never wrap, since a wrapped row would eat two or three of the handful the strip shows at once. The standalone pane sizes its body against the viewport, so `.has-match-pane` takes the strip's height back out of that calc; the embedded pane is already a flex column and needs no such adjustment.

**Live updates use Server-Sent Events**, not WebSockets: container logs (`GET /api/hosts/:id/containers/:id/logs`, `docker logs -f --timestamps`) and the container event feed (`GET /api/hosts/:id/events/stream`, via `eventWatcher`'s `Broadcaster` in `server/sse.js`) are both one-way SSE streams the frontend consumes with `EventSource`.

**The image** (`Dockerfile`) installs with `npm ci` from the committed lockfile, so it gets the dependency tree CI linted and tested against rather than whatever resolves on build day, and sets `NODE_ENV=production`. The Docker CLI is copied from Docker's own `docker:29-cli` image rather than installed from Alpine's `docker-cli` package: the CLI is a Go binary, so scanners attribute every Go standard-library CVE to it, and Alpine's build lags Docker's - v3.24/community sat on 29.5.3 built with go1.26.3 (carrying three stdlib CVEs fixed in go1.26.4) while Docker's image shipped 29.6.2 on go1.26.5. No amount of rebuilding fixed that; only Alpine rebuilding the package would have. The binary is self-contained, runs as-is on the musl base, and a newer CLI talks to older daemons fine (verified against a 27.5.1 daemon). `openssh-client` still comes from apk, since `docker -H ssh://` shells out to the system `ssh`. `.dockerignore` keeps `data/` out of the build context - without it, a `docker compose up --build` on any machine that has already run OpenDockWatch bakes that machine's sqlite database into the image, session store and the settings row holding the webhook URL (token and all) included.

**Chart colors** are the four `--seq-*`/`--accent` custom properties in `style.css`, validated as a categorical set (lightness band, chroma, contrast, and colorblind separation on every pair) against the tile surface rather than picked by eye - the header comment above them records what passed and what failed, including the obvious purple that turns out to be indistinguishable from `--accent` for deutan viewers. Re-validate rather than eyeball if they ever change; the `dataviz` skill carries the validator.

**Two eslint environments** (`eslint.config.js`): `server/**`, `scripts/**`, `test/**` are CommonJS/Node; `public/js/**` is an ES module/browser environment. Keep new files in the right bucket.
