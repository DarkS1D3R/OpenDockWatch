# CLAUDE.md — server/

Backend architecture notes for OpenDockWatch's `server/**`. See the [root CLAUDE.md](../CLAUDE.md) for commands and repo-wide conventions, and [public/CLAUDE.md](../public/CLAUDE.md) for the frontend half of anything that spans both.

**The server shells out to the `docker` CLI** (`server/docker.js`, via `child_process.execFile`/`spawn`) rather than talking to the Engine API or a Docker SDK. Every function takes a `host` object and prefixes its args with `-H <dockerHost>` when set (`hostArgs()`); a `null`/absent `dockerHost` means the local socket. This is _why_ remote hosts work at all: `-H ssh://user@host` is resolved by the Docker CLI itself using normal SSH key/config, so there's no separate tunneling code to maintain. Hosts are defined in `config/hosts.json` (gitignored, copy from `hosts.example.json`), each with an optional `edges: [{from,to,label}]` list for relationships Docker itself can't see. Hosts can also be added/edited/removed live from the Settings panel (admin-only, `/api/settings/hosts`) — `server/hosts.js`'s `saveHosts()` rewrites the file and the route calls `metricsCollector.addHost/removeHost` and `eventWatcher.addHost/removeHost` for just that one host, so a new SSH host starts being monitored immediately with no process restart (edits are a `removeHost` + `addHost` pair rather than an in-place update, since reconnecting is simpler than diffing what changed). The image's `/etc/ssh/ssh_config.d/opendockwatch.conf` (written by the `Dockerfile`) turns on SSH connection multiplexing (`ControlMaster`/`ControlPersist 10m`) globally, so the several `docker` calls each remote host gets per 5s poll ride one persistent SSH connection instead of opening their own — pure infra, no code involved, since the CLI just shells out to system `ssh`. `checkHost`/`testHostConnection` (the latter backing Settings' "Test connection" button, surfacing real `ssh`/`docker` stderr instead of a boolean) get a longer timeout for SSH hosts than the local-socket default (`checkTimeoutMs()`), since that's the one call that has to pay a slow link's connection-setup cost before multiplexing makes everything after it cheap.

**`server/logger.js`** writes structured single-line audit/debug events (`[opendockwatch] [LEVEL] event key=value ...`) to stdout/stderr - picked up by `docker logs` automatically and by the app's own Log Viewer level filters. Nothing in the server writes to `console` directly except `logger.banner()`, the ASCII boot banner (art, not an event - it's the visual marker for where a restart begins when scrolling back through `docker logs`, and `app.started` carries the same data as a real event immediately after). A failure that only reaches `console.error` is invisible to the Log Viewer's level filters, which is the entire reason this module exists, so new error paths go through it. Never log secrets: `alerts.webhookScheme()` is the only sanctioned way to put a webhook URL in a log line (`discord://…`), shared by `alerts.js` and `index.js`'s settings route so the redaction can't drift between them. Both halves of that are enforced, not just stated: `test/logger.test.js` scans every `server/*.js` for a direct `console.` call and fails any file but `logger.js` itself, and `test/alerts.test.js` drives all six webhook log paths (first delivery, failure, timeout, retry sweep, retry failure, and the thrown `sendTestAlert` message) with a canary token in the URL and asserts it reaches no line at any level. The scrubbing that makes that hold is `redactWebhookUrls`, in `deliverWebhook`'s catch: a thrown message is the _runtime's_, and undici's "fetch failed" is no contract, so both URL forms and the raw one's credential path are swapped for their scheme before anything can log or answer with it — in two passes, whole URLs before paths, since a `discord://` token reappears inside the discord.com endpoint and interleaving would chew a hole in a URL the later pass still had to match. An error with nothing redacted is rethrown as-is rather than re-wrapped, so its name and stack survive.

**What gets logged, and the rule for adding more.** The log's job is to let someone reconstruct what the app did without attaching a debugger, so it covers **state transitions and discrete operations, never per-poll steady state** - a line every 5s per host would bury the ones that matter. Currently: lifecycle (`app.started`/`app.shutdown`), auth success/failure, every container action as a **pair** (`container.<action>.requested` before the CLI call, `container.<action>` with `tookMs` after - `docker stop` can sit through its full 10s SIGTERM grace, and logging only on completion left a pressed button invisible until it finished), log-stream and event-stream open/close with `heldSec` (each one holds a `docker logs -f` child and one of the browser's ~6 connections - see the connection budget in `public/CLAUDE.md`), `logs.download` (container logs carry secrets, so exporting them is audit material), host watch start/stop, `docker events` stream start/restart-backoff/stop, host reachability in **both** directions (`host_unreachable` fires an alert, `host.reachable` only logs - nobody wants a webhook for good news, but "did it come back?" has to be answerable), webhook delivery success as well as failure, `alert.muted` for a suppressed alert, `db.pruned` with per-table row counts when the hourly prune actually deletes something, and every failure path. Steady-state polling stays silent by design.

**Pure parsing/graph-building functions are exported from `server/docker.js`** (`parseByteString`, `parseLabels`, `parseHealth`, `networkEdges`, `dependsOnEdges`, …) specifically so `test/*.test.js` can unit-test them directly without mocking `child_process`. When adding docker-CLI-output parsing, keep the parsing pure and separate from the function that actually shells out, and export it. `parseIdValueLines` is the shared shape behind three of them (`dependsOnEdges`/`customDependsOnEdges`/`parseMountsList`): a `docker ps --format '{{.ID}}\t{{...}}'` blob is one id/value pair per line, split on the _first_ tab only so a value that happens to contain one (a mounts list, a depends_on triple list) stays whole. `getTopologyMeta` fetches all three in **one** `docker ps --no-trunc` call instead of three - each used to be its own SSH round trip - and slices the pulled-in full-length id back to 12 chars for the two depends-on lines to match `listContainers`' truncated `container.id`, the same way `parseMountsList` already did for the mounts line. That split is itself `splitCombinedTopologyPs`, pulled out of `getTopologyMeta` and exported for the same reason as the rest of this paragraph - the shell-out and the parsing of what it returns are two different things to get wrong.

**Three long-running background jobs.** The first two are started by `server/index.js` on boot; the third is started per host by `metricsCollector` itself, since it exists only to feed it.

- `eventWatcher.js` — one persistent `docker events` process per host (auto-restarts with exponential backoff, capped at 30s). **The restart/backoff/teardown lifecycle itself lives in `server/restartingWatcher.js`**, shared with `statsWatcher.js` below - the two ran ~80 lines of it verbatim before that split, and `createRestartingWatcher` takes what actually differs (how to spawn the child, how to parse its stdout, what if anything must happen right before a restart) as options rather than duplicating the spawn/backoff/identity-check/teardown shell around them. **The restart hangs off `'close'`, never `'exit'`, and that is not interchangeable**: Node emits `'exit'` only for a child that actually ran, so a child that never spawned at all — `docker` off PATH, or an `EAGAIN`/`ENOMEM` fork failure under process pressure — emits `'error'` then `'close'` and no `'exit'` whatsoever (verified on Node 22). Keyed on `'exit'`, that left the host with **no event stream for the life of the process**: no `container_crashed`, `crash_loop` or `unhealthy` alerts, one `events.stream.failed` line, and nothing to bring it back. Nothing else catches it either — `watchdog.js` measures the poll loop, and a host with a dead event stream polls perfectly normally. `'close'` fires in both cases and always follows `'exit'`, so it needs no second handler. `test/eventWatcher.test.js`'s `endChild(child, {spawned})` helper exists to keep tests ending children the way Node actually ends them; asserting on a bare `emit('exit')` is what let this ship. The pending restart is tracked on the watcher's state so `removeHost` can cancel it, and the restart itself re-checks that the map still holds _that same state object_ before reviving anything: an edit through Settings is a `removeHost` + `addHost` pair, so a backoff elapsing after one would otherwise restart the old watcher against the new entry and leave two streams running for one host - every event inserted, published and alerted on twice, with the newer child orphaned where no `removeHost`/`stop` can reach it. Each parsed event line fans out to three places through `ingestEvent`: `db.insertEvent` (persistence), `broadcaster.publish` (live SSE push to the Activity tab), and `alerts.handleEvent` (rule engine). This is the single ingestion point for all event-driven alerts (`container_crashed`, `crash_loop`, `unhealthy`). **`ingestEvent` must never throw**, and that is the reason it exists as its own function rather than as the body of the loop: it runs inside the child process's stdout `'data'` handler, an exception out of an EventEmitter listener is an `uncaughtException`, and `index.js` calls `process.exit(1)` on those — so one `SQLITE_BUSY` on one event line would end monitoring for every host, which is precisely the trade `unhandledRejection` is deliberately not making three paragraphs up. The `try`/`catch` is per event so a bad line doesn't cost the rest of the chunk it arrived in either, and it's exported purely so `test/eventWatcher.test.js` can assert the swallow-and-log contract by mocking `db.insertEvent`/`alerts.handleEvent` to throw, without spawning a real `docker events`. Note that this is about _thrown_ errors only: writing to an SSE response whose client has gone is not one of them — `res.write` on an ended or destroyed `ServerResponse` returns `false` and drops the data rather than throwing or emitting, verified on Node 22 for socket-destroy, write-after-`end`, and a client RST mid-burst, so `sse.js` needs no guard around its write.
- `metricsCollector.js` — polls every host every `POLL_MS` (5s) for containers/info (stats come from the stream below), plus disk usage on a **derived** interval (`nextDiskDelay`, floor 60s); keeps an in-memory snapshot per host (`getSnapshot(hostId)`, used e.g. to avoid an extra docker call just for a container's name in audit logging) and writes samples to sqlite for history charts. Also feeds the threshold-based alerts (`container_cpu`/`container_mem`/`host_cpu`/`host_mem`/`docker_disk`, `handleSample`/`handleHostSample`/`handleDiskUsage` in `alerts.js`). **Reachability is derived from the poll's own calls, not probed separately** — `checkHost` (`docker version`) used to be `await`ed serially in front of every poll, which is a whole extra round trip on an SSH host to re-answer a question the three calls behind it answer for free. It now runs only as a **gate for a host already believed down**, and that asymmetry is the entire design: against a host that is up the probe is pure overhead, while against one that is down a single process failing fast beats three each waiting out their own timeout, so a host stuck offline never advances past the gate. The three calls go through `Promise.allSettled`, not `Promise.all`, because reachability now depends on them and _"one of the three failed" is not the same fact as "the daemon is gone"_: only all three failing marks the host unreachable, and anything less is a failed poll on a host that is demonstrably still answering — firing `host_unreachable` for that would be a worse answer than the probe used to give. A partial failure therefore leaves the snapshot on the previous poll's values exactly as the old single `try`/`catch` around all three did, since half a poll would diff this poll's stats against themselves and write an instant of history that never happened. `markUnreachable` exists because that outcome has three call sites and the alert has to fire exactly once per poll; `docker.js` gained `noteHostFailure`/`noteHostReachable` so `lastCheckError` keeps answering "why is this host down?" whichever path decided it was. `pollHost` is exported purely so `test/metricsCollector.test.js` can drive those branches, and the docker calls it makes go through the module object rather than destructured bindings so they can be stubbed. **Only the calls that actually reached the daemon count towards reachability**, which is why `pollHost` tracks that rather than just reading the settle results: two of the three are routinely answered from memory — stats from `statsWatcher`'s stream, info from `docker.js`'s `HOST_INFO_TTL_MS` cache — and a value served from a buffer proves nothing about the host still being there. Counting one would leave a dead host looking reachable for as long as they stayed warm. `listContainers` is always live, so the live set is never empty. **`docker info` is cached for the same reason it was worth caching at all**: CPU count, total memory, server version and hostname are fixed for a daemon's lifetime, and the two container counts — the only fields that move between polls — are recomputed each poll by `containerCounts` from the `docker ps` output already in hand, so caching costs no freshness. A TTL rather than "once, forever" so a VM resize or a daemon upgrade still lands. Note this shows up as **spawn count, not latency**: the three calls run in parallel, so `pollLastMs` is unchanged — measured at 9 `docker info` processes in 40s before and 2 after.
- `statsWatcher.js` — one persistent `docker stats` process per host, replacing the `docker stats --no-stream` call the poll used to make. **That one call was the poll cycle**: measured at 1.3-2.0s against a _two-container_ daemon, because the CLI has to collect a whole sample cycle before it can print a CPU percentage and only then exits — a third of the poll interval, and one of `run()`'s 12 concurrency slots held for all of it. Built on the same `restartingWatcher.js` as `eventWatcher` above, with two things of its own: `beforeRestart` clears the sample map right before a restart is scheduled (see (2) below for why), and `initState` seeds it fresh per host. Same never-throw contract on the stdout handler. End to end on one machine, same daemon and same `hosts.json`, `app.vitals`' `pollLastMs` went from a steady **2081ms to 80ms**. Four things about it are load-bearing. (1) **`docker stats` draws a table with cursor-control escapes even when its output is a pipe** — each refresh is `ESC[J ESC[H <rows> ESC[H <rows> ESC[K`, verified byte-for-byte — so a row arrives with an escape glued to the front of the JSON that `JSON.parse` rejects outright. `parseStatsLine` strips them and is pure/exported so that survives without a daemon. It does not try to reconstruct redraw _frames_: nothing here needs to know where one ends. (2) **`getSamples` returns a copy, never the live map.** `pollHost` mutates what it gets (`Object.assign(s, computeIoRates(...))`) and diffs it against the object it kept from the previous poll — aliasing would make those the same object, so every cumulative counter would equal itself and every I/O rate would silently be zero. (3) **It returns `null`, not `{}`, when it has nothing usable** — no rows yet, or no row for `STALE_SAMPLES_MS` (30s) — and `pollHost` falls back to the one-shot call. A stream that is up but no longer printing would otherwise freeze the dashboard on numbers that never advance, which is worse than paying for the slow call; the same reason `exit` clears the samples rather than keeping them warm across a restart. (4) **`docker stats` only reports running containers**, so `retainContainers` prunes against the running set from the same poll's `docker ps` — exactly like `alerts.retainContainers` beside it — or a host that cycles containers accumulates an entry per id it has ever seen. `statsLive` on the vitals line is the count of hosts actually being served from a stream: below `hosts`, someone is paying the one-shot cost on every poll.

**Staying responsive is a design constraint, not an optimization** — the failure this app has to avoid is the one where it's still running but unusable, since that's the one a container restart is the only cure for. Three rules follow from it, and new code has to keep them. (1) _Never leave a request unanswered._ A browser allows ~6 connections per origin over HTTP/1.1 and this app permanently holds some of them open for its SSE streams, so a request that hangs is a connection slot lost — enough of them and the tab can't issue any request at all, including the ones a reload needs, and that state outlives the server recovering. `requestTimeout` in `index.js` answers 504 rather than hanging (SSE routes exempt, matched by path suffix; a late real response is dropped rather than thrown, since a second send would otherwise destroy an already-answered connection), `api.js` puts an `AbortSignal.timeout` on every `fetch`, and `docker.js`'s `run()` escalates SIGTERM→SIGKILL so a CLI blocked on a wedged daemon socket can't leave its promise unsettled forever. (2) _Don't multiply work per viewer._ The collector already has containers/stats/info/reachability/hostname in its snapshot; routes serve from it rather than shelling out per request — `/containers`, `/stats` and `/info` all do (`?fresh=1` on `/containers` is the one opt-out, for the refetch right after a start/stop where up-to-`POLL_MS` staleness is visible) — and **the poll loop asks for all of it in one request, not four**: `GET /hosts/:id/dashboard` returns `{containers, stats, metricsHistory, alerts}`, which is exactly what `app.js`'s cycle used to `await` one after another, at a cost of four round trips, four session-store lookups and four turns of the ~6-connection budget per open tab every `POLL_MS`. Measured in a real browser over ~4 cycles: **18 `/api` requests → 4 in List view, 25 → 10 in Flow**. The four fields are built by `containersFor`/`statsFor`/`hostHistoryFor` plus `db.getAlerts`, and those exist as functions specifically so the bundle cannot drift from the individual routes it duplicates — `test/index.test.js` asserts field-by-field parity against each one. **Those parity assertions need seeded rows to mean anything**, which is why the test inserts host metrics spanning the 1h boundary and alerts across two hosts: against an empty database `metricsHistory` and `alerts` are both `[]` no matter what the bundle asked for, and mutation-testing confirmed that pointing the bundle at the 24h range and dropping its host scope both survived the entire suite until those rows existed. **Topology is deliberately not in the bundle** even though the poll fetches it too in Flow view: it is the one part that can still shell out (its label/mount metadata is cached against the container-id set, which recreating a container invalidates), so folding it in would put a docker call behind four fields that are otherwise pure memory and make the whole response only as reliable as its slowest part. It stays its own route and `refresh()` runs the two through `Promise.all` instead of in series, so Flow view costs two requests and one round trip rather than five and five., `getTopology` caches its three label/mount `docker ps` calls against the container-id set (they can't change without the container being recreated under a new id), and `run()` caps concurrent CLI processes. **Two of those four fields are cached across requests, not just computed once per poll cycle**: `restartCountsCache`/`dashboardExtrasCache` (`index.js`) key on the collector's own `statsTs` rather than a separate wall-clock timer, so the restart-count `GROUP BY`, the 1h history bucketing and the alerts query each run once per poll tick regardless of how many tabs are open on that host, not once per request. `containersFor`'s `fresh` bypasses `restartCountsCache` the same way it bypasses the snapshot above it, or a post-action refetch could pair a live container list with a stale restart count. Because the bundle answers from cache, anything that mutates the alerts it serves has to invalidate it explicitly: `forgetDashboardCaches(hostId)` is called by the host add/edit/delete routes and by the alert ack/ack-all/clear routes alike, or a clear or ack lands invisibly until the next `statsTs` tick and `app.js`'s wholesale `this.alerts = data.alerts` overwrites the client's own optimistic update with the stale list. The single-alert ack route has no `hostId` in its URL, so `db.getAlertHostId(id)` looks it up first - `null` (not found, or already cleared) correctly means nothing to invalidate. The client side of this rule — the poll loop's own chained-request discipline and the ~6-connection budget it shares with log streams — is in `public/CLAUDE.md`. (3) _Recover without a human._ `watchdog.js` measures how long since `metricsCollector` last _completed_ a poll — deliberately a property of the loop, not of Docker, since an unreachable host still completes its poll — and reports unhealthy on `/healthz` then exits after a grace period. The exit is the part that matters: Docker never restarts a container for being unhealthy, and `restart: unless-stopped` only reacts to the process exiting, so self-exit is the only path back. It's injectable (both clocks, `exit`, timer) and unit-tested in `test/watchdog.test.js`. **Recovery time is `STALE_MS + EXIT_AFTER_MS` and a user experiences it as one number**, so treat it as one: detection stays conservative at 120s (24 missed polls, ~3x the worst legitimate cycle of a timing-out SSH host at 20s + the 5s SIGKILL grace + a full 15s semaphore queue wait), but the grace after that is 120s rather than the 600s it started at. Once staleness is confirmed there is nothing left to wait for - a restart costs ~10s of `start-period` and loses nothing, since the db is WAL and the history is already written - and 13 minutes of a frozen dashboard is not meaningfully more self-healing than 4. `test/watchdog.test.js` asserts the sum stays under 5 minutes, because this is the kind of constant that drifts upward one cautious commit at a time. (4) _Leave a trace, especially of a stall._ This was learned the expensive way: a real 220s outage left **nothing whatsoever** in the log between the two sides of it, and was only provable afterwards by finding the matching gap in `host_metrics`. So `index.js` emits **`app.vitals` on a fixed interval** (`VITALS_INTERVAL_MS`, 60s, 0 to disable) and most of its value is that it's periodic - a gap in the heartbeats is itself the evidence, and the lines either side show the state going in and coming back out. It carries only live counters that nothing else reports: `rssMb`/`heapMb`, the watchdog's `lagMs`, `pollLastMs`/`pollMaxMs`/`pollSlow` from `metricsCollector.takePollStats()` (`maxMs` resets on each read, so a rising floor across consecutive lines is the collector degrading, not one bad poll hours ago pinning the number forever), `dockerActive`/`dockerQueued` from `docker.poolStats()`, `statsLive` from `statsWatcher.liveCount()` (read against `hosts`: below it, some host's stats stream is down and that host is paying 1.3-2.0s for the one-shot `docker stats` on every 5s poll - the stream's own restart lines say so as it happens, this is what says it is _still_ happening an hour later), and `logStreams`/`sseClients` - the open/close pairs elsewhere each describe one stream, and "how many are held right now" is not something you can replay from them while the UI is hung. **`dbLastMs`/`dbMaxMs` sit next to `lagMs` on that line for a reason**: better-sqlite3 is synchronous, so every write is event-loop time, and lag plus a long worst-write in the same window means the storage was the cause, while lag without one means it was something else - equally worth knowing, and previously unanswerable. `db.js`'s `timed()` wraps only the two writes big enough to matter (the per-poll transaction and the hourly prune, which is a full table scan); timing every single-row statement would cost more than it tells you. Around it sit narrower signals, each chosen so it fires on a real problem and not on normal work: `db.write.slow` (`SLOW_DB_WRITE_MS`, 250ms); `metrics.poll.slow` (`SLOW_POLL_MS`, 15s) is what precedes watchdog staleness, since the watchdog only speaks once the loop has stopped entirely; `request.slow` (`SLOW_REQUEST_MS`, 5s) uses **per-route thresholds** via `slowThresholdFor`, because a `docker stop` waiting out SIGTERM routinely takes ten-plus seconds while working exactly as designed and `docker system df` was measured at 40-75s cold - those are held to their own timeouts instead; and `docker.queue.saturated`/`docker.queue.drained` bracket an _episode_ of concurrency-limit saturation rather than logging per queued call. Four more close gaps where the app already knew something and threw it away: **`host.unreachable` carries the reason** — reachability is a boolean, so "became unreachable" arrived with no cause at all, and timed-out / host-key-verification-failed / permission-denied / daemon-not-running call for completely different responses; `docker.js` keeps the last failure per host in `lastCheckErrors`, written by `noteHostFailure` from both the probe and the ordinary poll calls (the latter is now the usual source, since a reachable host is never probed), and `markUnreachable` reads it on the reachable→unreachable transition only, never per poll. **`auth.rate_limited`** exists because the limiter tripping is the one event that _silences_ the log: once it trips, requests stop reaching `verifyLogin`, so `auth.failure` stops too and a sustained brute-force reads as though the attacker gave up. **`app.shutdown.complete`** reports `endedBy: 'drained'` vs `'timeout'` — the 5s forced path means streams were still held, which is the connection-budget problem surfacing at the one moment it is easy to observe. **`alert.webhook.backlog`** gives the retry queue a depth, since the per-alert retry lines each describe one alert and never say they are the same growing queue. `eventWatcher.takeIngestCount()` feeds `events` on the vitals line for the same reason the queue aggregates: a container in a restart loop is a real source of synchronous writes, and logging the flood would _be_ the flood.

**`POST /api/client-error` is the one route deliberately exempt from the admin gate, and the exemption is enforced rather than assumed.** The frontend compiles its Vue templates in the browser, so a broken render is a blank page with a completely healthy server log — "the site is broken" and "the server is fine" both true, with nothing reconciling them unless someone opens devtools. `app.js`'s three global handlers (`window.onerror`, `unhandledrejection`, `app.config.errorHandler`) and `mounted()`'s `bootError` path mirror to this route so client failures land in `docker logs` with everything else. It has to work for a **viewer** — a viewer's browser breaks exactly like an admin's — so `test/index.test.js`'s structural admin-gating check carries an `ADMIN_EXEMPT` map whose entries record their justification and, crucially, fail if the route they name no longer exists, so a removed route can't leave its exemption behind to silently cover whatever later takes that path. Two properties qualify a route for it: no state change, and a real reason a non-admin must reach it. **The client-side caps are the load-bearing part, not the server's rate limiter.** A render error inside a watcher fires every frame, and each report would take one of the browser's ~6 per-origin connections — the same budget the poll loop and log streams live on — so an unbounded beacon would cause the exact hang it exists to diagnose. `reportOnce` dedups on kind+message+source+line and stops entirely after `MAX_CLIENT_ERROR_REPORTS` (5) per page load, **checking the cap before touching the dedup set** so a loop throwing distinct messages can't grow that set forever after reporting has stopped. That cap also bounds recursion by construction. `api.js`'s `reportClientError` is deliberately not `apiFetch`: it must never redirect on 401, never throw (anything thrown lands back in the handler that called it), and never retry; `keepalive: true` lets a boot-failure report survive the navigation that often follows it. Verified in a real browser — clean boot reports nothing, two identical errors report once, twelve distinct ones stop at five. **Aggregate a sustained condition, don't log an event per occurrence** - that rule now covers the queue, `watchdog.lag_summary`, and `disk_usage.poll.failed`'s failure count, and the reason is that a few hundred identical lines bury the one thing that was worth reading. Note `active` is deliberately absent from the queue lines: reaching that path means every slot is held, and `release()` hands a slot straight to a waiter rather than decrementing, so it is `MAX_CONCURRENT` by construction. `test/api.test.js` pins the rest of its contract - no 401 redirect, no throw on a synchronous or asynchronous fetch failure, exactly one request, `keepalive: true`, and no `AbortSignal`, the last being the structural proof it did not go through `apiFetch` (which always attaches one, asserted alongside so the proof cannot go vacuous).

**`clientError` and `server.timeout` are both traps, and `index.js` documents them in place.** Taking over `clientError` means taking over the _response_, and it is not always a 400: `headersTimeout` and `requestTimeout` (both set) surface there as `ERR_HTTP_REQUEST_TIMEOUT`, which Node's own default answers **408** - measured, not assumed. `clientErrorStatus` is exported and unit-tested precisely because the handler itself lives inside the `require.main === module` block and can't be. The handler also declines to write when `!socket.writable || socket.bytesWritten > 0`, matching the default: otherwise `socket.end()` is a silent no-op that reads like a reply was sent, or corrupts a partly-written one. **There is deliberately no `server.on('timeout')` listener and no `server.timeout`** - it defaults to 0 in Node ≥13 so a listener alone can never fire, and merely attaching one _suppresses_ Node's default socket destruction, so enabling it to "fix" that would leak every timed-out socket unless the handler destroyed them itself. It also can't be enabled safely here at all: `server.timeout` is whole-socket inactivity and this app's SSE streams are idle by design between 30s heartbeats.

**The watchdog reads two clocks, and the difference between them is load-bearing.** `now` (wall) measures staleness, since `lastPollCompletedTs` is a `Date.now()`; `monotonic` (`process.hrtime`) measures event-loop lag and the resume grace. They are separate because a suspended host - laptop sleep, a paused WSL2/Docker Desktop VM, this app's usual home - stops the poll loop for hours with nothing whatsoever wrong with it, and `CLOCK_MONOTONIC` does not advance across a suspend while the wall clock does. A tick whose wall delta exceeds its monotonic delta by `SUSPEND_JUMP_MS` is therefore a resume, not a stall: lag is recorded as zero, `staleSince` is cleared, and `RESUME_GRACE_MS` of quiet follows so the collector's own timer can turn over before staleness counts again (`status()` honours that grace too, or waking the machine would flap the container unhealthy for a few seconds every time). A genuinely starved VM advances both clocks together and is still caught normally. Getting this wrong is expensive in both directions, and more so now that the exit grace is two minutes rather than ten.

**Event-loop lag has two thresholds because one number can't do both jobs.** It never triggers the exit on its own (a one-off spike during the hourly prune is normal); it exists because better-sqlite3 is synchronous, so a slow bind-mounted volume can block the event loop long enough to stall the HTTP server. A single stall past `LAG_WARN_MS` (2s) gets its own line. Everything past `LAG_NOTICE_MS` (250ms) is accumulated instead and flushed once a minute as `watchdog.lag_summary` (`stalls`/`maxMs`/`totalMs`/`blockedPct`), with the window opening on the first stall worth noticing so a healthy host logs nothing at all. The summary exists because the single 5s threshold it replaced recorded **nothing** on a host that was losing 90-220s an hour to stalls that were each individually under it - the only visible symptom was `metricsCollector`'s hourly `setInterval` firing three minutes late, which is not something anyone goes looking for. If a report starts "it freezes sometimes", `watchdog.lag_summary` is the first thing to read. `uncaughtException` exits for the same reason; `unhandledRejection` only logs, since one failed docker call or db write shouldn't take monitoring down for every host.

**`alerts.js`** is the rule engine plus webhook delivery. Every alert setting (webhook URL/format, CPU/mem/disk thresholds) follows the same pattern: an `.env` default, overridable from the DB via the admin Settings UI (`PUT /api/settings/...`), with the DB value always winning when present — even an explicit empty/0 to deliberately disable something `.env` configured. See the README's Alerts section for the full rule table and webhook URL-scheme routing. **Per-container overrides** live in the `container_alert_rules` table (`server/db.js`): an ordered, first-match-wins list matched by container name (case-insensitive substring) or an exact compose project, optionally scoped to one host. `resolveContainerConfig({hostId, containerName, composeProject}, ctx)` walks it — the matched rule's non-null fields override the global threshold config for that call, with anything it leaves null still inheriting the global value, and its `mutedRules` naming which of `container_crashed`/`crash_loop`/`unhealthy` are suppressed for that container. No match at all (the common case) returns the global config untouched. **The reads it needs are hoisted to one per poll, not one per container**, via `alertContext()` (`{global, rules}`): `metricsCollector.pollHost` builds one and passes it to every `handleSample` in that poll, the same collect-then-act shape the metrics transaction above already uses. `handleHostSample` takes the same `ctx` and reuses its `global` half when `pollHost` already built one that poll, rather than reading the threshold config a second time; `handleDiskUsage` accepts one too for symmetry, though its disk poll runs on its own ~60s timer independent of `pollHost`'s cycle, so in practice it usually has none to reuse and falls back to reading its own. Per-container was measured at ~30µs a call with 10 rules configured — 6ms of synchronous event-loop time every 5s at 200 containers, four times what batching the metrics write saved, and growing with rules × containers × hosts. It's built lazily (skipped entirely when every container on the host is label-disabled) and `ctx` is optional, so the event path and the tests still resolve per call. On the event side that's the right granularity anyway: `mutedByRule` runs only on a `handleEvent` call actually about to fire, never once per `docker events` line, and it **logs an `alert.muted` line when it suppresses one** — `fire()` always leaves an `alert.fired` trace, so without that a muted alert would be the one outcome with no record at all to answer "why didn't this alert?". This is deliberately separate from the `opendockwatch.alerts=off` Docker label, which stays exactly as narrow as before — checked first, unconditionally, before any rule lookup, and still only gates `handleSample`'s threshold rules; muting an event rule per container goes through the rules table instead of widening what the label means. `composeProject` reaches both call sites cheaply: `docker.js`'s label parsing already put it on every container object (forwarded into `handleSample` via `metricsCollector.js`'s `alertSamples.push`), and `docker events`' `Actor.Attributes` carries the same label set (`eventWatcher.js`'s `parseEventLine` reads it alongside `name`/`exitCode`), so neither needs an extra docker call.

**The `alerts` table is also the cooldown store, which is why the Activity tab's alerts-column Clear button is a soft delete.** `shouldFire` suppresses a repeat for `COOLDOWN_MS` (10 min) by reading `db.getLastAlertFireTs`, which is nothing more than the newest matching row in `alerts` — so a hard `DELETE` there does not clear a list, it **re-arms every rule on that host**. The breach state that decides whether a threshold rule wants to fire lives in a different table (`alert_breaches`) and is untouched by a clear, and `checkSustained` returns true on _every_ sample once a breach is past `sustainMinutes`, so the cooldown is the only thing standing between an ongoing breach and an alert every 5 seconds. Clearing a still-breaching host therefore re-inserted the alert on the next poll and **re-sent its webhook**, with the list repopulating in front of the user who just emptied it; `docker_disk` was worse in kind, since its comment records that it has no sustain window and relies on the cooldown alone. `db.clearAlerts` instead stamps `cleared_at` and **every other alerts query filters on `cleared_at IS NULL`** — list, open counts, per-container counts, ack/ack-all, and the webhook retry sweep, so the clear is invisible everywhere a hard delete was — with `lastAlertFire` as the single deliberate exception. Rows leave for real on `pruneAlerts`' ordinary retention sweep. If a new query against `alerts` is added, it needs that filter unless it is answering "when did this last fire?".

**The events column's Clear is a soft delete for the same reason, and its blast radius was wider.** `events` is not just the Activity feed: `countRestartsSince` backs the `crash_loop` rule (3 restarts in `CRASH_LOOP_WINDOW_MS`) and `getRestartCountsByContainer` backs both the List view's `restartCount1h` and `prometheus.js`'s restart gauge. A hard delete therefore emptied a list _and_ silently reset crash-loop detection — a container actually in a restart loop needed three fresh restarts before it could be caught again — walked the restart column back to 0 for an hour, and made a Prometheus counter go backwards, which breaks `rate()` in whatever is graphing it. So `db.clearEvents` stamps `cleared_at` and **only `getEvents` filters on it**; the two restart counters deliberately do not, because they answer what a container did rather than what the tab is showing. The same rule as above applies to a new query against `events`: filter, unless the question is about the container's actual history. **Both clears also write an `audit_log` row** (`auditClear` in `index.js`, action `clear_alerts`/`clear_events`, no container): `cleared_at` records when a clear happened, and the audit log is the only place that records _who_ — it is also the one table a clear doesn't touch. Those rows carry a `container_id` of NULL and an action outside `('stop','start','restart')`, which is what keeps them out of `countManualStopsSince`/`countManualStartsSince`, where a stray match would suppress a real `crash_loop` or `container_crashed` alert. Note that nothing in `public/js` reads `GET /api/audit` — the audit log is an API-and-database record, not a screen — and that route is **`requireAdmin`**, unlike the alerts list beside it. It is who ran what, and its `error` column carries raw docker/ssh stderr (host names, paths, `Permission denied (publickey)`), so it belongs behind the same call that masks `Config.Env` for a viewer. Being a GET, the structural walk at the top of `test/index.test.js` cannot cover it — that one only inspects mutating methods — so it has an explicit viewer-403/admin-200 pair instead. A privileged **read** added later needs the same by hand; the walk will not catch it. **The two clears scope their host differently and now answer an unknown one the same way**: events takes a path segment and gets `requireHost`, alerts takes `?hostId=` and gets `requireHostQuery`, which repeats the same 400-then-404 pair for a query param (and sets no `req.odwHost`, since these routes hand the id to sqlite and never to the docker CLI). Without it a typo'd host id came back `200 {count: 0}` — "cleared nothing" and "no such host" are not the same answer. `POST /alerts/ack-all` now takes it too, replacing its hand-rolled `if (!hostId)` — it was the last route scoping by `?hostId=` without it, and answered a typo'd id `200 {count: 0}`. Labels follow the same symmetry: the buttons are **Clear alerts** and **Clear events**, not "Clear activity" — the tab itself is Activity, so that name read as though it emptied both columns. **Its index needed the same care**: right after a Clear every retained row is cleared, so the plain `(host_id, ts)` walk that `getEvents` was given an index for in the first place would traverse the host's entire history to return an empty page — hence the third, partial `idx_events_host_ts_active ON events (host_id, ts) WHERE cleared_at IS NULL`, which `test/db.test.js` pins with an `EXPLAIN QUERY PLAN` assertion. That index is created **after** the `ALTER TABLE` block rather than inside the schema block, and that placement is load-bearing: on an upgrading database the schema block runs against a table that does not have `cleared_at` yet, so a `CREATE INDEX` naming it there throws at module load and takes the app down on the first start after the upgrade.

**"Filter `cleared_at`" is enforced, not just written down here.** `test/db.test.js` scans `server/db.js` for every `name: db.prepare(`…`)` pair and fails any statement reading or updating `alerts`/`events` without a `cleared_at` filter. Inserts are exempt structurally; the seven real exceptions (the two cooldown/restart-count reads above, the two by-primary-key webhook updates, and the two age-based prunes) are named in `CLEARED_AT_EXEMPT` with a reason each, and an entry that no longer matches a live statement fails too, so a rename can't quietly hand an exemption to whatever takes the name next. A companion assertion pins the statement count, so a query written in a shape the scan doesn't match fails loudly instead of going unchecked.

**`getDefaultView()` validates the stored value on the way out, not only the submitted one on the way in.** (See `public/CLAUDE.md` for the Settings panel component this backs.) `PUT` already 400s on anything outside `VALID_VIEWS`, but a hand-edited settings row — or one written by a release that still had a view this one has since dropped — would otherwise be handed straight to the client, and an unrecognised view is a **blank page**: List/Flow are `v-show` and Logs/Activity `v-if`, so nothing renders and no tab reads as active. `dbDefaultView()` therefore returns `null` for an unusable row, which also keeps `overridden` honest — it reports the override actually in effect rather than the mere presence of a row. The `.env` side is resolved once at module load into `ENV_DEFAULT_VIEW` rather than per call, since `getDefaultView()` runs on every `/session`: a misspelt `DEFAULT_VIEW` should log `config.default_view.invalid` once at boot, the same shape as the `SESSION_SECRET` warning, not on every login.

**The disk poll is the one schedule derived from measurement rather than declared, because `docker system df`'s cost is a property of the host's storage and nothing else.** It deduplicates shared image layers by walking the whole overlay2 tree: sub-second on native Linux, but measured at **40-75s cold on a WSL2/Docker Desktop host** with the same 32 images, where the layers sit on a virtual disk behind a 9p/virtiofs hop and every `stat` pays for it. Warm it drops back to ~2.6s, so the cost is dominated by page-cache state and the run-to-run spread on one machine is more than an order of magnitude. Three things follow, and they're all in `nextDiskDelay` / `pollDiskUsage`. (1) `DISK_USAGE_TIMEOUT_MS` is 120s, not a value chosen near the typical cost - the old 30s was picked on Linux and meant the call could **never once succeed** on WSL2, so the Disk panel was permanently empty while a heavyweight process was spawned and SIGKILLed every 60s forever. (2) The next run is scheduled at least `DISK_DUTY_FACTOR` × the last duration away, so a 75s call gets a ~5 minute gap instead of a 60s one - a call that takes longer than its own interval is effectively continuous, and holds one of `docker.js`'s 12 concurrency slots the whole time. On a fast host this floors at the plain 60s and nothing changes. (3) Consecutive failures back off exponentially to a 1h cap and reset on the first success. Be aware the backoff and the cache interact the wrong way round - polling less often means a colder cache means a slower call - which is why the timeout is set well clear of the cold cost rather than relying on backoff to find a workable rhythm. **A failed poll is surfaced, not swallowed**: `snapshot.diskUsageError` reaches the client via `{rows, error}` from `/hosts/:hostId/disk-usage` (a bare array couldn't distinguish "measurement failed" from "nothing on disk", so `HostCard` rendered no panel at all), last known rows are kept and shown alongside it, and the log line is a `warn` carrying the consecutive-failure count, since a call that is impossible on a given host is one fact about that host rather than several hundred incidents. Relatedly, `docker.js`'s `dockerCommandError` exists because `execFile` reports a timeout kill as a generic `Command failed: docker ...` with **empty** stderr - nothing is ever written to it - which reads like a daemon fault and is precisely why this went unnoticed for weeks.

**`server/db.js`** is a single `better-sqlite3` database (`data/opendockwatch.db`) holding metrics history, events, audit log, alerts, settings overrides, and doubles as the express-session store. Every query is prepared once into the `stmts` map at module load rather than per call - put new ones there too. **Everything a poll writes goes through one `db.transaction()`, not a loop of individual `.run()` calls and not a transaction plus a loose insert** - that's `insertMetrics(samples, hostSample)`, which carries every running container's row _and_ the host row. Per-row `.run()`s measured on an SSD at 2.65ms → 0.70ms for 50 containers and 10.58ms → 1.45ms for 200; folding the host row in on top of that saves a further 0.04-0.06ms per host per poll (44% of the write at 2 containers, 9% at 200). Since better-sqlite3 is synchronous the saving comes off the event loop directly - the same one `watchdog.js` watches for lag.

**Be careful about _why_ that is worth doing, because this file used to state it wrongly.** It claimed WAL "still runs at SQLite's default `synchronous=FULL`, so a per-row `.run()` is a full commit and an fsync each". It does not: setting `journal_mode = WAL` also drops `synchronous` to **NORMAL** (`SQLITE_DEFAULT_WAL_SYNCHRONOUS`), verified with `PRAGMA synchronous` on both a fresh database and the real `data/opendockwatch.db` - both report `1`. Under WAL+NORMAL a commit appends to the WAL and does **not** fsync; the fsyncs are at checkpoints. So the cost being saved is commit machinery, not disk sync, and it is tens of microseconds rather than milliseconds. The measurements above are real and the batching is still right - it is the mechanism that was mis-stated, and it matters because "every commit is an fsync" would justify contortions this codebase should not make. If a write path ever genuinely needs durability-per-commit, that is a deliberate `PRAGMA synchronous = FULL`, not something to assume is already in force. Atomicity comes along for free and is worth keeping: a malformed sample rolls the whole poll back rather than writing half an instant into the history charts (`test/db.test.js`). The ordering in `metricsCollector.pollHost` is deliberate - collect every sample **and build the host row**, write them all in one transaction, _then_ run `alerts.handleSample`/`handleHostSample` over them. The host row is built before the write purely so it can join that transaction; its alerting stays after, for the same reason the container alerting does. Alerting per container inside that loop would have put the rule engine's own `alert_breaches` writes, and `fire()`'s fire-and-forget async webhook, inside the metrics transaction; better-sqlite3 transactions are synchronous and must not have an `await` suspend inside them. The two history queries downsample into `@bucketMs`-wide windows using `BUCKET_EXPR` from `server/metricsHistory.js`, which is written as `ts - (ts % @bucketMs)` for a reason that will bite anyone who "simplifies" it back: better-sqlite3 binds every JavaScript number as REAL, SQLite's `/` is float division the moment an operand is REAL, and so the obvious `(ts / @bucketMs) * @bucketMs` returns `ts` unchanged and the GROUP BY groups nothing at all. `%` coerces to INTEGER regardless of binding. The same module's `withIoRates` then turns each bucket's `MAX(net_rx_bytes)` and friends into per-second rates by differencing consecutive buckets over their real elapsed time (the columns hold cumulative counters, so they're meaningless plotted raw), reusing `docker.js`'s `computeRate` so a container restart's counter reset comes back as `null` rather than a negative rate. The history queries themselves use `MAX`, not `AVG`, for those same I/O columns - a container that restarts mid-bucket makes `MAX` that bucket's pre-restart peak, so the following delta goes negative and is reported as `null`, the correct read on a counter reset. Both are pure and unit-tested in `test/metricsHistory.test.js`. Old rows are pruned on the retention windows (`METRICS_RETENTION_DAYS`/`EVENTS_RETENTION_DAYS`) by `metricsCollector.start()`, once at boot and hourly after that; the boot run matters because an instance that restarts more often than the interval would never reach the first tick. Indexes are chosen against the query's whole shape, `ORDER BY` included, not just its `WHERE` columns: `events` carries `(host_id, container_id, ts)` for the per-container restart counts and `(host_id, ts)` for `getEvents` (plus the partial third one covered above), because the first can only use its leading column when `container_id` isn't in the predicate, leaving SQLite to sort the host's entire retained history through a temp B-tree to answer a `LIMIT 200` — 14.1ms against 300k rows, versus 0.181ms once the second index turns it into a walk that stops at the limit. `EXPLAIN QUERY PLAN` naming a `USE TEMP B-TREE FOR ORDER BY` is the tell. No migration framework — schema is a set of `CREATE TABLE IF NOT EXISTS` statements run at startup; add new tables the same way, and new indexes too (unlike `ALTER TABLE ADD COLUMN`, `CREATE INDEX IF NOT EXISTS` in that block does reach an existing database on upgrade) — with one exception: an index over a column the `ALTER TABLE` block is adding has to be created after that block, since in the schema block it would run against a table that does not have the column yet (see `idx_events_host_ts_active`). A new _column_ on an existing table needs both: add it to the `CREATE TABLE` (for a fresh database) and a `try { db.exec('ALTER TABLE ... ADD COLUMN ...') } catch {}` right after the schema block (for an existing one upgrading — `IF NOT EXISTS` only skips the whole statement, it doesn't retroactively add columns to a table that already exists without them).

**Auth (`server/auth.js`)** is cookie-session based with two roles: admin (full control) and an optional read-only viewer (`VIEWER_USER`/`VIEWER_PASS_HASH`). Role enforcement is server-side (`requireAdmin` middleware on every mutating route) — the viewer role hides buttons in the UI too, but a request forged around the UI still gets a 403 from the server. `test/index.test.js` enforces that structurally rather than by a hand-maintained list: it walks the api router's own stack and fails if any non-GET route lacks `requireAdmin`, so a mutating route added later can't quietly ship without it. Read-only is not the same as "may read everything", though, and one route needs the distinction spelled out: `GET /containers/:id/inspect` returns `docker inspect`'s `Config.Env`, which is where DB passwords and API keys actually live, so a non-admin session gets it through `maskEnvValues` (`docker.js`) — variable names kept, values replaced, `envMasked: true` on the response so `ContainerDetail` can say why rather than look like every value is blank. `maskEnvValues` splits on the _first_ `=` only, or a secret containing one (base64 padding, a connection string with `?ssl=true`) would leak its tail; a genuinely empty value stays visibly empty instead of being dressed up as a hidden one. Login calls `req.session.regenerate()` before marking the session authenticated — `saveUninitialized: false` means there's rarely a pre-auth session to fixate, but that's a property of the current config rather than a guarantee, and the guarantee should come from the login itself.

**Two endpoints sit outside the `requireAuth` router and are gated differently.** `/healthz` is deliberately open and deliberately narrow (see the Dockerfile's HEALTHCHECK). `/metrics` can't use cookie auth because Prometheus can't, so it takes a shared secret in `METRICS_TOKEN` — and an unset token means the endpoint **404s**, not that it serves without auth. That response enumerates every container name, compose project, usage figure and restart count across every host, which is inventory disclosure to anything that can reach the port, so the unconfigured state has to fail closed; a scraper sets the variable, nobody else needs the endpoint at all. The comparison goes through `crypto.timingSafeEqual` (length checked first, so only the token's length is observable) since this is the one credential that travels in a URL.

**`server/prometheus.js` renders that body by hand, and `test/prometheus.test.js` exists because nobody reads it by eye.** A scraper does, so every failure mode here is silent: a malformed line doesn't look broken, it stops a dashboard updating. The tests cover the exposition rules a hand-built body can break (HELP/TYPE before samples, one family's samples staying contiguous — which is why `render()` accumulates five arrays instead of emitting per host — a trailing newline, and a valid body when there are no hosts at all), the value fallbacks that keep a `NaN` off the wire (a container with no stats row yet, a missing restart count, a host with no `hostInfo`), and above all **`esc()`**. Container names are user-controlled by whoever ran `docker run --name`, and a raw newline in one does not corrupt a label, it corrupts the whole scrape by splitting the sample into two lines — so the escaping cases are the point of the file. Everything is driven through `metricsCollector.getAllSnapshots`/`db` mocks, so it needs no daemon, no poll and no seeded table. **The suite was mutation-checked**, nine deliberate defects against `render()`, and that was worth doing: the rounding assertion originally used `1.5MiB`, which is already a whole number of bytes and therefore passed with or without the `Math.round` it claimed to pin. If you add a case here, break the thing it covers and watch it fail first.

**Static assets are mounted twice, and the HTML is rewritten on the way out.** There is no build step, so a page load is ~43 separate sub-resources: 35 ES modules, 7 vendor scripts, the stylesheet and the logo. `express.static`'s defaults gave every one an ETag and no `max-age`, so every revisit and every reload was 43 conditional round trips — all answering 304, all still spending a turn of the browser's ~6-connection budget on the same origin whose SSE streams already hold some of it open. Measured before and after in a real browser: **43 network requests on revisit → 0, and on reload → 0** (cold load is unchanged at ~1.4MB, as it must be). The fix is a version-pinned prefix, `/assets/v<package.json version>`, mounted `immutable, maxAge: '365d'`. Pinning by path rather than by `?v=` query is the load-bearing choice: a relative `import './format.js'` resolves against the **importing module's own URL**, so pointing `index.html` at `/assets/v2.5.1/js/app.js` pulls the entire 35-module graph under the same prefix for free, where a query string would not be carried by those imports and 34 of the 35 would silently fall back to the uncached mount. The bare `/assets` mount stays, on a 5-minute `max-age`: `app.js`'s template references `/assets/logo.svg` directly, and a browser still holding the previous release's `index.html` has to keep working rather than 404 its way to a blank page. **The HTML itself is `Cache-Control: no-cache`, always** — it is the pointer to everything above, so caching it means the browser keeps loading the previous release's assets out of its own cache indefinitely and invisibly. `sendPage()` reads the file per request (two small files, once per navigation, against 43 saved requests) so `npm run dev` still picks up edits, and rewrites `/assets/` to the pinned prefix rather than the HTML carrying a placeholder — that keeps both files valid as plain static HTML.

**Security headers** are five fixed values set by one middleware in `index.js`, ahead of everything including the static mounts, rather than a helmet dependency. CSP is the load-bearing one, and the directive doing the work is the _absence_ of `'unsafe-inline'` from `script-src`: container log output reaches the DOM through `v-html` in three components, and since `innerHTML` never executes a `<script>` tag anyway, the real injection vector there is an inline handler like `<img onerror=…>` — which is exactly what that omission blocks. This is why `public/login.html`'s submit handler lives in `public/js/login.js` instead of an inline `<script>`, and why a test asserts both that it stays external and that `script-src` never gains `'unsafe-inline'`. If a future inline block "needs" it, put the script in a file instead.

`script-src` does carry **`'unsafe-eval'`, and removing it blanks the entire app** — verified in a real browser, not assumed. There's no build step (a deliberate constraint, see `public/CLAUDE.md`), so every component ships a `template` string that Vue compiles in the browser via `Function(code)()` at `vue.global.prod.js`'s single `Function(` call site; under a CSP without `'unsafe-eval'` that throws and every component renders empty, silently, with nothing useful in the console. The only ways off it are precompiling templates (a build step) or hand-writing `render()` functions — both are much larger changes than the header, and `'unsafe-eval'` doesn't re-enable inline scripts or event handlers, so it costs little against the threat this CSP was added for. `style-src` carries `'unsafe-inline'` for the same no-build-step reason and can't avoid it — `format.js`'s ANSI colour spans and `graph.js`'s cytoscape HTML labels both emit `style="…"` into parsed HTML — and `img-src` allows `data:`/`blob:` for the graph's inline SVG icons and the PNG export. Not set: HSTS, which does nothing over the plain HTTP many deployments use behind a proxy and belongs on the proxy terminating TLS.

**`requireHost` attaches the resolved host as `req.odwHost`, and the name is load-bearing.** Express defines `req.host` as a **getter-only** property returning the Host header, so `req.host = hostObject` silently no-ops in sloppy mode and every handler downstream reads back a string like `"localhost:3000"` instead. Nothing throws and nothing looks wrong locally: `hostArgs()` is `host && host.dockerHost ? ['-H', host.dockerHost] : []`, and a string has no `.dockerHost`, so it falls through to the empty-args case — the **local socket**. A single-local-host install therefore behaves perfectly while every remote host's containers, logs, stats, inspect and start/stop/restart routes quietly run against the wrong daemon. `test/index.test.js` drives a probe route through the real `requireHost` and asserts the handler receives an object, plus asserts express's own `req.host` is still unwritable so the day that changes is visible rather than assumed. Never name request-scoped state after something express already owns.

**Route input handling (`server/index.js`)** — nothing from the URL reaches sqlite or the docker CLI raw. `intParam` defaults and clamps numeric query params (`Number('abc')` is `NaN`, which better-sqlite3 rejects outright with "datatype mismatch" instead of treating as absent, so an unvalidated `?limit=`/`?since=` 500s the request rather than falling back), `tailParam` allows a positive integer or docker's literal `all` (the log viewer's "All lines" option), and `requireContainerId` rejects anything that doesn't look like a container id - nothing runs through a shell, but an id starting with `-` would be read by docker as a flag rather than a container. **`requireContainerAction` guards `:action` for a different reason, and the ordering is the whole point**: `containerAction` already refuses anything outside `start`/`stop`/`restart`, but by the time it does, the route has written an `audit_log` row and emitted `container.<action>.requested` — so an unchecked value left a phantom audit row for an action that never ran, and answered **502** where 400 was right. Worse, express URL-decodes path params and `logger.js` escapes field _values_ but not the **event name**, so `…/containers/<id>/stop%0A%5Bopendockwatch%5D%20%5BINFO%5D%20auth.success…` forged a second, perfectly well-formed line in `docker logs` and in the app's own Log Viewer. It is admin-only, so this is log and audit _integrity_, not access — which is exactly why it is easy to leave unfixed and worth the middleware. The set is imported from `docker.js` rather than retyped, so the route gate and the CLI guard cannot drift. Anything a route throws that it doesn't handle itself lands in the terminal error handler registered after the router, which logs it and returns the message alone; without it express's default handler answers, and that one puts the whole stack trace in the response body unless `NODE_ENV=production`.

**Live updates use Server-Sent Events**, not WebSockets: container logs (`GET /api/hosts/:id/containers/:id/logs`, `docker logs -f --timestamps`) and the container event feed (`GET /api/hosts/:id/events/stream`) are both served via `eventWatcher`'s `Broadcaster` in `server/sse.js`. See `public/CLAUDE.md` for how the frontend consumes them.

**The image** (`Dockerfile`) installs with `npm ci` from the committed lockfile, so it gets the dependency tree CI linted and tested against rather than whatever resolves on build day, and sets `NODE_ENV=production`. The Docker CLI is copied from Docker's own `docker:29-cli` image rather than installed from Alpine's `docker-cli` package: the CLI is a Go binary, so scanners attribute every Go standard-library CVE to it, and Alpine's build lags Docker's - v3.24/community sat on 29.5.3 built with go1.26.3 (carrying three stdlib CVEs fixed in go1.26.4) while Docker's image shipped 29.6.2 on go1.26.5. No amount of rebuilding fixed that; only Alpine rebuilding the package would have. The binary is self-contained, runs as-is on the musl base, and a newer CLI talks to older daemons fine (verified against a 27.5.1 daemon). `openssh-client` still comes from apk, since `docker -H ssh://` shells out to the system `ssh`. `.dockerignore` keeps `data/` out of the build context - without it, a `docker compose up --build` on any machine that has already run OpenDockWatch bakes that machine's sqlite database into the image, session store and the settings row holding the webhook URL (token and all) included.
