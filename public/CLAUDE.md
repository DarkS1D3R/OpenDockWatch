# CLAUDE.md — public/

Frontend architecture notes for OpenDockWatch's `public/**`. See the [root CLAUDE.md](../CLAUDE.md) for commands and repo-wide conventions, and [server/CLAUDE.md](../server/CLAUDE.md) for the backend half of anything that spans both.

There is no build step for the frontend — `public/js/*.js` is served as-is via native ES modules (`<script type="module">` in `public/index.html`). Most of it (`app.js`, `public/js/components/**`) is only syntax-checked, not unit-tested, since it's Vue/Cytoscape UI code with no meaningful behavior outside a browser - but pure logic with no DOM/cytoscape dependency has no such excuse: `format.js` (ANSI parsing, level detection, byte/rate formatting), `graph.js`'s `buildElements`/`aggregateGroups` (graph-building), and `public/js/lib/spark.js`/`lib/logStream.js` (sparkline coordinate math and the EventSource/buffering factory shared by `LogViewer`/`ContainerDetail`'s log streams - `EventSourceImpl` and the flush `schedule` are injectable specifically so this is testable under `node --test` with a stub source, without a browser) are all unit-tested. `test/format.test.js`, `test/graph.test.js`, `test/spark.test.js`, and `test/logStream.test.js` `import()` their module directly (dynamic import, since `require()` can't load an ES module - `node:test`'s `before()` hook loads each once and shares it across that file's tests). When pulling more logic out of a component in `public/js/components/`, prefer landing it in `public/js/lib/` if it's pure - that's the difference between it being tested and not.

**The poll loop's own budget discipline is the client half of "staying responsive"** (see `server/CLAUDE.md` for the server-side rules this pairs with — never leave a request unanswered, recover without a human — and for why `GET /hosts/:id/dashboard` bundles four fields into one request). Client-side, the poll loop is a chained `setTimeout` and never `setInterval` — a cycle awaits five or six requests, so on a slow host an interval starts a second cycle before the first finishes and they stack — plus a backoff on failure and a full stop while the tab is hidden. Anything long-lived that reconnects needs a budget too: `logStream.js` gives up after repeated disconnects with no line in between, since EventSource retries forever and each retry spawns a `docker logs` server-side. **The ~6 connections are a budget to be spent deliberately, and log streams are what spend it** — the Logs tab alone can hold four. So a stream only runs in the views its component is actually part of: `app.js`'s `detailPanelVisible` gates the detail panel (and `setView` closes the bottom Log Viewer) to List and Flow, the Logs tab owns its panes, Activity owns its event stream — worst case four, never six, leaving two for the poll loop. Streams also suspend themselves after `HIDDEN_SUSPEND_GRACE_MS` in a backgrounded tab (`logStream.js`), returning both the connection and the server-side `docker logs -f` child; the grace exists because resuming re-tails and therefore resets the pane, which is wrong for a two-second tab switch and right after a real absence. Raising `MAX_OPEN_LOG_PANES` spends that margin directly.

**Frontend is Vue 3 (Options API)**, no SFCs/build step — `public/js/**` is loaded as native ES modules via `<script type="module">`. `app.js` is the root component (~400 lines): session/role bootstrap, host list/selection, the 5s polling loop, containers/stats/alerts state, view switching, and `doAction`. Everything view-specific lives in `public/js/components/`: `SparkTile`/`HostCard` (the host-usage tiles), `ContainerList`/`ContainerDetail` (the List view and its detail panel), `MiniSpark`/`ContainerMetricsModal` (the per-container sparkline in each row and the full-history view it opens), `LogViewer` (the full-size log panel), `ActivityView` (the alerts/events tab), `SettingsPanel` (webhook/threshold/host config), and `FlowView` (the Cytoscape graph/tree view). `SparkTile` is the shared chart for both the host tiles and the modal, which is why its second series is `secondarySamples`/`secondaryLabel` rather than anything host-named - it carries the host total behind Docker's own usage on the host card, and the tx half of an rx/tx pair on the modal's I/O charts - and why `slotCount` is a prop: the host card's live window and the 1h/24h/7d ranges hold different numbers of buckets. **The hovered values are a rendered readout (`.spark-readout`), never a `title` attribute**, and that distinction was a real usability bug: a native tooltip needs the pointer held on the element itself for about a second and vanishes the moment that element moves — and the hover dots are 6px and move on every 5s poll, so reading one meant chasing a target that walked away. `onHover` already derives the slot index from horizontal position alone, so the readout rides the crosshair and stays up for as long as the pointer is anywhere over the chart. It is pinned to the top of the chart rather than following the dot vertically, deliberately: tracking the value would make it jitter on every redraw, which is the same complaint in a different form. It flips to the near side of the crosshair past the halfway mark instead of being clamped at the edge (clamping would park it on the line it annotates), and carries `pointer-events: none` because the `mousemove` positioning it belongs to the chart underneath — a readout that swallowed that event would freeze itself the instant it appeared. Hovering the still-empty padded region of a partly-filled chart correctly shows nothing at all, since `hoverPoints` returns null when neither series has a value there. **`HostCard` has the same 1h/24h/7d range strip as `ContainerMetricsModal`, plus a fourth `live` option, and the strip only renders in fullscreen** — a tile sharing a row has no space for it. `live` is the default and reads the root's `metricsHistory` prop (the rolling window the root already refetches every poll), so the card costs no extra request until someone actually widens the window; the other three re-read sqlite over the same `GET /metrics/history` the modal uses, minus its `containerId`. Every series reads one `activeHistory` computed rather than the prop directly, so a range switch moves both tiles together and they can't end up drawing different windows. Same two guards as the modal, plus one: a landing response is dropped if either the range **or the host** has changed since it was issued, and only `1h` keeps a refresh timer (24h/7d buckets are 5 and 30 minutes wide, so a 5s refetch would redraw an identical chart). Leaving fullscreen resets to `live` — the strip is the only way back, so a non-live range would otherwise be stranded with its timer still running behind a tile that can't show it. The `system_*` columns behind the "host total" overlay are `AVG`d by the same query at every bucket width, so that series works at 7d exactly as it does live. `MiniSpark` is deliberately not a variant of it; sharing that component for a table cell would mean `v-if`-ing away five of its six parts. Panels that are meaningfully transient (`LogViewer`, `ContainerDetail`, `ActivityView`, `SettingsPanel`) mount via `v-if`, each time fresh, so their own `mounted()`/`beforeUnmount()` own their stream or fetch lifecycle instead of the root orchestrating it (e.g. `ContainerDetail` watches its own `container.id` prop to reset/refetch on a same-mount container switch, since watching the whole `container` object would refire on every 5s poll — the root replaces its `containers` array wholesale each poll, so the object reference changes even when the id doesn't). `ContainerList` and `FlowView` instead stay mounted via `v-show` across List/Flow tab switches, since there's nothing external to tear down and rebuilding a Cytoscape graph from scratch on every switch would be wasteful for a host with many compose projects — they watch their own props (`topology`, `hostId`, `stateFilter`) to re-render instead of remounting. State that's genuinely shared across views (`selectedContainerId`, `selectedHostId`, `alerts`) stays in the root and flows down as props, with children emitting events back up (`select`, `action`, `close`, `open-log-viewer`, ...) rather than reaching into siblings; `fullscreen` on both `LogViewer` and `FlowView` is the one exception worth calling out — it's a real `v-model` (not fully internal) because the root's own layout needs to know about it directly, to hide the host card and other panels. Two sources feed the container charts and they are not interchangeable: the List row's `MiniSpark` reads the root's live in-memory buffer (`recordMetricsSample`, ~2 minutes, empty after a reload), while the modal reads the persisted sqlite history over `GET /metrics/history?containerId=`. Samples are right-aligned into the chart's slots by `padSlots`, so a series shorter than the window - a container created ten minutes ago, or a buffer still filling - draws in the right-hand part of the chart and grows leftward, rather than stretching to fit. `public/js/lib/` holds pure, unit-tested logic shared across components: `spark.js` (sparkline coordinate math, used by `SparkTile` and `MiniSpark`), `logSync.js` (**both** binary searches behind the Logs tab's multi-pane scroll sync — `closestIndexByTs` answers "where do I scroll to" and `topIndexByOffset` answers "where am I now"; the second lived inline in `LogViewer.js` reading `el.children` directly, which is why only one half of the feature was ever tested. It takes a lazy `offsetAt(i)` rather than an array because it runs on every frame of a drag over a pane holding up to `MAX_LOG_LINES` lines, and materialising the offsets would turn an O(log n) probe into an O(n) copy per frame. **Its tests budget every probe**, which is not belt-and-braces: `node --test` has no per-test timeout, so a non-terminating search does not fail, it hangs the whole run until something outside kills it — measured at exitCode 143 with zero tests reported. Budgeted, the same defect names itself in milliseconds. Give any case added there a budget too), `logPane.js` (the log pane's pure chrome: the match strip's resize arithmetic — including the subtracted drag delta, since the handle is the strip's **top** edge on a bottom-anchored pane — the space-to-pause predicate, and the status badge), `logLines.js` (per-line log decoration/filtering — see below), `format.js`'s `eventSeverity` maps docker event actions onto the same `critical`/`warning`/`ok` vocabulary the alert rows use, so one colour language covers both Activity columns — it drives both the event rows' left accent and their badges. Unlisted actions (`exec_create`, `attach`, `commit`, `resize`, …) stay deliberately neutral: colouring routine noise would drown the handful of rows worth spotting. `health_status:` is special-cased and tests the **negative first**, since `"unhealthy".includes("healthy")` is true and the obvious order gets the two exactly backwards. Severity is attached once per event at ingest (both `loadEvents` and the SSE `onmessage`), never derived in the template, for the same reason `logLines.js` exists — a method call from a `v-for` re-runs on every render. The row accent is an `inset` box-shadow on the first cell rather than a `border-left`, because the events table is `border-collapse` and a per-cell border fights the collapsed grid. `activityCounts.js` (`groupCounts`, behind the Activity tab's per-kind header badges — alerts by rule, events by action; counted off the _text-searched_ lists so the badges describe the rows the search box left — but deliberately not off the badge-filtered ones, see `activityFilter.js` below — sorted by count with a `localeCompare` tie-break that is the load-bearing part, since without it two kinds on the same count swap places as rows stream in and a badge row that reshuffles while you read it is worse than none, then capped with the remainder returned as a `+N more` badge), **`activityFilter.js`** (`filterAlerts`/`filterEvents`, the two filters each Activity column applies — see below for why they are two and not one), `logBuffer.js` (`pushCapped`, the append-and-trim shared by the visible line array, a paused pane's held buffer, and the drain of one into the other — pure and unit-tested precisely because the invariant that matters spans all three: `test/logBuffer.test.js` asserts that pausing and resuming lands on the same buffer as never pausing, cap included), and `logStream.js` (the EventSource/buffering factory both `LogViewer` and `ContainerDetail`'s log preview build on; the one module that isn't purely pure, since it also owns the hidden-tab suspension, which is why `doc`/`EventSourceImpl`/`schedule` are all injectable). `logLines.js` exists because per-line work has to happen **once at append**, not per render: `decorateLine` derives a line's level, timestamp and no-filter HTML when it arrives, and `selectLines` reuses that cached `baseHtml` unless a filter is actually active. Deriving it per recompute cost ~4.4ms for a 3000-line pane (~17.7ms across four, past a 60fps frame's 16.7ms); caching brings a pane to ~0.16ms. `ContainerDetail` had a worse variant — it called `highlightLine` from a template _method_, so the work re-ran on every render including the 5s stats poll — and its preview is capped at `PREVIEW_TAIL`, not `MAX_LOG_LINES`. **`highlightLine` matches against the line's raw text and escapes each piece on the way out, not the other way round** - escaping first and matching the raw filter against the already-escaped string let a search for a substring of an entity name (e.g. `"amp"`) match _inside_ the `&amp;` a literal `&` elsewhere on the line escapes to, and made a search for `<`/`&` themselves highlight nothing at all, disagreeing with `selectLines`' own raw-text `isMatch` check. `buildLineMatcher` is split out of it so `selectLines` compiles the pattern once per render instead of once per matching line. The same module also owns the Log Viewer's search cursor (`hitIndexFor`/`stepHitId`), and the rule there is that **the cursor is a line id, never a position**: `appendLines` trims the buffer from the front once a pane passes `MAX_LOG_LINES`, so every appended line shifts each index down by one and a positional cursor quietly comes to name a different line — the highlight walks the hit list on its own, with no user action, while the "26 / 30" counter keeps reporting the position it started from. It's invisible in a short pane and constant in a busy tailing one, which is why it shipped. `hitIndexFor` resolves the id back to a position on every render (a computed, so once per render pass and not once per line) and falls back to the first hit when the parked-on line has aged out or been filtered away; `LogViewer` clears the cursor in `startStream`/`onReset` because `logStream` restarts its ids from 0 for a new source, so a cursor held across a reconnect would otherwise point at whatever unrelated line inherits that id. Clicking a hit line sets `revealAll` rather than clearing the filter: `selectLines` gets a `hideNonMatching` option, and with it off, `filteredLines` renders every line (context included, matches still highlighted, non-matches reusing cached `baseHtml` so this isn't the O(n) `highlightLine` cost again) while `matchLines` - always computed with `hideNonMatching: true` - keeps the hits box counting and stepping through matches only, since the two arrays diverge once revealAll is on. `matchLines` derives from `filteredLines.filter(l => l.isMatch)` rather than a second `selectLines` pass over `this.lines`: every line `selectLines` returns already carries `isMatch` under the same filter args regardless of `hideNonMatching`, so the two computeds' outputs are always consistent with each other for free - the pane used to run the whole per-line highlight/escape pass twice per render whenever the hits box was open. Typing a further filter character (or toggling regex mode) drops `revealAll` back to false, since a new search term means "narrow down again"; clearing the filter to empty just turns `searchActive` off, which is what actually hides the box and the highlighting. Supporting modules: `api.js` (the only place `fetch` is called, wraps 401→redirect-to-login and JSON/error handling; also owns `reportClientError`, the client-error beacon - see `server/CLAUDE.md` for the route it reports to, its admin-exemption, and the server-side rate-limit contract), `format.js` (pure display formatting: ANSI-to-HTML for colored logs, byte/timestamp formatting, log-level detection, badge/icon lookups), `constants.js` (poll intervals, history lengths), `graph.js` (all Cytoscape.js flow-view logic: layout via dagre, edge/node styling, compose-group collapse/expand via cytoscape-expand-collapse, and `localStorage`-backed persistence of dragged node positions + camera zoom/pan + collapsed group ids, keyed per host so a reload doesn't reset your arrangement — owned by `FlowView`, which is the only component that imports it). The Flow view has two render modes sharing the same topology data: graph mode (`buildElements`, compose-group boxes, network/depends-on/manual edges) and tree mode (`buildTreeElements`, an ArgoCD-style `project → container → network/mount` DAG with no compound groups, network/volume pills deduped globally so shared infrastructure gets one node with multiple incoming edges). A tapped tree-mode pill (`proj:`/`net:`/`mount:` id) is filtered out inside `FlowView` before it ever reaches the root — routing it into `selectedContainerId` would trip `ContainerDetail`'s watcher into fetching `docker inspect` for a fake id — so it's kept as `FlowView`-local state (`pillSelection`), used only for fading and the tap-info bar. Container nodes are shared between both modes via `containerNodeEl`. Positions/camera are keyed per host _and_ per mode (`odw:flow:positions:<mode>:<hostId>`, etc.) since a dagre layout from one mode is meaningless in the other; the mode choice itself is also saved per host. Vendor libraries (Vue, Cytoscape, dagre, html2canvas-pro, cytoscape-expand-collapse) are checked into `public/vendor/` and loaded as global `<script>` tags, not npm/bundled — `eslint.config.js` declares them as browser globals for that reason. html2canvas-pro exists specifically because `cy.png()` only rasterizes cytoscape's own `<canvas>`, not the `cytoscape-node-html-label` DOM overlay that actually renders node content (name, icons, CPU/RAM bars, badges) — Flow view's "Export PNG" screenshots the real on-screen DOM instead (this means it has a fixed pixel resolution to manage - see `EXPORT_SCALE` and the container-resize dance in `exportPng`: html2canvas just copies cytoscape's existing CSS-pixel-resolution canvas bitmap, so a higher `scale` merely stretches an already-low-res source, which is why `exportPng` instead temporarily renders into a container `EXPORT_SCALE` times larger - scaling container size, zoom, and pan by the same factor is a uniform scale-up of `renderedX = graphX * zoom + pan.x`, so it frames the exact same crop with `EXPORT_SCALE` times as many real pixels to draw into). "Export SVG" sidesteps that entirely: `extractSvgGeometry` (impure, reads the live `cy` instance's positions/classes/data) feeds `renderSvg` (pure, geometry → an `<svg>` string, unit-tested the same way `buildElements` is) which hand-draws the same node/edge visual design `CY_STYLE` and the HTML templates already encode - no dependency on the DOM overlay or a rasterization step, so there's no resolution ceiling to manage for a host with a lot of compose projects. **The two `nodeHtmlLabel` templates (`containerNodeTpl`/`collapsedGroupTpl`) escape `name`/`status`/`label` before building their HTML** - the DOM overlay above is real markup, not canvas, so a docker/compose-supplied string with no charset restriction goes into it raw otherwise; defence-in-depth rather than a live fix, since CSP already has no `'unsafe-inline'` in `script-src` for anything injected to execute against. Pulled into their own exported functions specifically so a test can assert the escaping without a real cytoscape instance. expand-collapse physically removes a collapsed group's children from the graph, so `updateGraph`'s poll-driven diff skips them entirely while hidden rather than touching them (an earlier version briefly expanded/re-collapsed every poll to keep their data fresh, but that visibly flickered the collapsed box every 5s) — `expandcollapse.afterexpand` re-syncs a group's children from the latest poll's data the moment it's actually opened instead. Below `COMPACT_ZOOM_THRESHOLD` (graph.js), nodes render a compact HTML label (state/icon/name only, no metric bars) and shrink to match via a per-element style function on node height keyed off a `compact` data flag - flipped synchronously on every `viewport` event (immediate, unlike the debounced viewport-position save alongside it) so it reads as a direct consequence of zooming. **A container leaf's state class must come from `elements.js`'s `CONTAINER_STATE_CLASSES`, and every selector that means "any container" must be built from it** - `layout.js`'s `OVERLAP_NODE_SELECTOR` and `updateCompactFlag`, `graph.js`'s `nodeHtmlLabel` query, `svgExport.js`'s `svgNodeKind`. Nothing throws when one of the four misses a state; the node just quietly stops participating in whatever that selector drives, which is how `created` shipped absent from `layout.js`'s two: it never received a `compact` flag, so `node.created`'s height mapper always took the full-height branch and the node stayed full size (rendering the non-compact label) while every neighbour shrank on zoom-out, and it was neither an obstacle for nor a subject of overlap resolution, so it could sit on top of another node. `test/graph.test.js` sweeps every docker state through `buildElements` and asserts the class it emits is in that list, which catches a new branch added to `containerStateClass` without the list, but not a selector that forgot to derive itself - so derive, don't spell out.

**The Settings panel** (`public/js/components/`) is a tab-strip shell (`SettingsPanel.js`) over five independent sections — `SettingsGeneral.js`, `SettingsWebhook.js`, `SettingsThresholds.js`, `SettingsContainerRules.js`, `SettingsHosts.js` — each owning its own fetch/save/error/status state rather than one file juggling five prefixed copies of the same shape (the pre-split version's `webhookSaving`/`thresholdsSaving`/`hostsSaving` etc.). Tabs swap via `v-if`, not `v-show`: each child is a cheap admin-only GET-config panel with no stream to preserve across a switch, so remounting fresh on every click keeps data always-current (add a host, flip to Container Rules, its host dropdown already has it) at the cost of one harmless refetch. The repeated saving/error/status try/catch/finally across all five lives once in `public/js/lib/settingsSection.js`'s `withStatus(vm, savingField, fn)` — not pure (it mutates the passed component), so it sits alongside `logStream.js` as a shared-but-not-unit-tested helper rather than in the pure-logic part of `lib/`. `SettingsGeneral.js` is the odd one out among the five: its one setting (the default landing tab, `DEFAULT_VIEW`/`server/index.js`'s `getDefaultView()` - see `server/CLAUDE.md` for the validate-on-read behavior there) has no secrets and applies to every role, so unlike the other four its `GET /settings/default-view` route is still `requireAdmin` for symmetry with the panel it lives in (only admins ever open Settings), but the _value_ itself reaches every logged-in user for free as a `defaultView` field on `GET /api/session` - `app.js`'s `mounted()` calls `setView(session.defaultView || 'list')` once hosts are loaded (not a bare assignment, so a configured `'flow'` default also fires `fetchTopology()` immediately, the same as clicking the tab by hand).

**`ConfirmButton` is the app's only confirmation, and it is a two-step button rather than a dialog.** The Activity tab's two Clear buttons act on every alert or event on the host from a single click, which is the one place in the UI where a slip is worth a second of friction. It arms on the first click (label swaps to `Sure?`, fills red via `.confirm-btn.armed`) and runs on the second; the `ARM_MS` timeout, a blur, or unmounting all disarm it — the unmount case matters because the Activity tab is `v-if`, so switching tabs mid-arm would otherwise leave a timer firing against a component that no longer exists. Deliberately not `window.confirm`: it blocks the event loop this app spends a lot of effort keeping free, and a native dialog is the same kind of borrowed browser affordance as the `title` tooltip the sparkline readout replaced. Registered locally by `ActivityView` (`components: { ConfirmButton }`), the same way `SettingsPanel` registers its five tabs — root registration in `app.js` is local to the root, not global, so a nested component has to be declared by its parent. **Be aware the two Clear buttons are currently the only things using it**: `SettingsHosts`' "Remove" (which deletes a monitored host) and `SettingsContainerRules`' "Remove" are both still one click, and are the obvious candidates if this is meant to be the house pattern rather than one screen's.

**The Activity columns filter on two independent things, and collapsing them into one didn't work.** Each column has a free-text search box (substring, across a few fields) and a row of count badges that double as filter toggles. The badges first shipped by writing their key into the search box, which reused the filtering that already existed but was wrong in two ways that a badge filter cannot afford. It **over-matched**, because the search is a substring across several fields: clicking the events column's `start` badge also matched every `restart` row, and clicking an alert rule badge also matched any alert whose _message_ merely mentioned that rule — so the badge said 1 and the list showed 3. And because `groupCounts` runs off the searched list (deliberately, so the badges describe what's on screen), setting the search **collapsed the badge row to the one badge you just clicked**, leaving no way to switch from one filter to another without un-toggling first. `activityFilter.js`'s `filterAlerts`/`filterEvents` therefore return **`{ searched, shown }`**: `searched` is the text box alone and is what the badges are counted off, so every badge stays visible and clickable while one is active; `shown` is that narrowed by an exact match on the field the badges group by (`rule`/`action`), and is what the list renders. The two filters compose, and `alertRuleFilter`/`eventActionFilter` are their own component state rather than the search string — the "Clear filters" button clears both, which matters because a badge can drop out of the visible row (past `groupCounts`' limit) while its filter is still applied.

**Container state and health are two axes and both are rendered.** `stateEmoji(state, health)` colours a running container's dot by health (green/amber `starting`/red `unhealthy`) instead of a flat green, and `created` gets its own dashed accent icon rather than falling into the generic stopped branch. **The five colours those axes are drawn in live in `public/js/theme.js` and nowhere else.** They were previously hex literals in four places - `format.js`'s icons, `CY_STYLE`, `svgExport.js`'s `svgContainerNode`, and `style.css` - and the rule "add a new state colour to all of them" was documented here and enforced nowhere, so a change to one silently disagreed with the rest. `STATE_COLORS` is keyed by what the container _is_ (`running`/`stopped`/`created`/`starting`/`unhealthy`), with `ACCENT`/`MUTED` as the two palette tokens several non-state things also use; `format.js` maps docker's health vocabulary onto it (`healthy` → `running`) since that mapping is a `format.js` fact, not a palette one. `HEALTH_COLOR` still sits at the **top** of `format.js`, not beside `healthColor()` where it reads more naturally, because the icon constants build from it at module load and a `const` is in its TDZ until its own initializer runs. `ANSI_COLOR_MAP` is deliberately **not** wired to it despite three codes sharing the same hexes - that is a terminal palette reproducing what a container meant by "red", and pointing it at `STATE_COLORS` would tie log rendering to the dashboard's design.

Two seams an import cannot close, both covered by `test/theme.test.js`. **`style.css` is not importable**, so the four states with a custom property (`--ok`/`--muted`/`--accent`/`--warn`) are named in `theme.js`'s `CSS_VAR_FOR_STATE` and the test reads them back out of the `:root` block and fails if the two drift; `unhealthy` is exempt on purpose, since the CSS has no counterpart (`--danger` is a different red for error text, and conflating them would repaint every error message in the app). **`svgExport.js` restates `CY_STYLE`'s selector-order precedence by hand** in `svgContainerNode` - `created → starting → unhealthy → selected`, the more urgent fact winning the border - because an SVG string has no cascade; `test/graph.test.js` asserts that chain as a chain, since the bug it guards is an `if` landing in the wrong order and no single-state assertion can see it. **Those colour assertions read `STATE_COLORS`, never a hex literal.** They used to pin literals, which was worse than having no test: they passed while `svgExport` and `CY_STYLE` disagreed, which is the one failure they look like they exist to catch.

**The Logs tab remembers what was open, in `sessionStorage`, per host** (`public/js/lib/logsPersistence.js`). The tab mounts under a `v-if`, so leaving it unmounts every pane — which is deliberate, since that is what gives the connections back — but it also lost the whole selection, so coming back meant rebuilding it by hand. Only the _choice_ is kept (`viewMode`, `openIds`, `mainId`, `disabledSyncIds`); the streams are not, and neither are the scroll positions (`lastSyncTsMs`/`joinTsMsById`), since every pane re-tails on return and a saved timeframe would land the group where the logs no longer are. **`sessionStorage`, not the `localStorage` `graph/persistence.js` uses next door**, and that difference is the point: that module remembers a layout someone arranged by hand and is worth keeping for weeks, while this remembers which containers you were reading a minute ago — a selection restored days later is more often a puzzle than a convenience. Per browser tab is also the right grain, so two dashboards open on different things stay on different things. **Nothing reaches the server**; the Logs tab's selection is not state the backend has any use for. **`app.js`'s `logout()` calls `clearAllOpenPanes()`**, because `sessionStorage` is scoped to the tab and not to the account signed into it — without it, the next person to sign in on the same machine inherits whichever containers the last one had open. Nothing secret is exposed (any authenticated user can list containers), but arriving at a selection you did not make is a confusing way to start.

Two things about it are easy to get wrong. `normalizeOpenPanes` **validates on the way out, not merely parses** — this is hand-editable storage that decides which log streams get opened, so a stored list longer than `MAX_OPEN_LOG_PANES` would open more `EventSource`s than the ~6-per-origin budget allows, a `mainId` naming a closed pane would put the group in leader-follower mode with no leader on screen, and a stale `disabledSyncIds` entry would suppress sync for a pane nobody can see is opted out. Same discipline as `getDefaultView()` validating a stored `defaultView` on read (see `server/CLAUDE.md`). And `restoreOpenPanes` **deliberately does not filter against the current container list**: `app.js`'s `selectHost` does not clear `containers`, so straight after a host switch that list is still the _previous_ host's — filtering there would check the newly restored ids against the wrong host's containers, drop all of them, and persist that emptiness as the answer, wiping the memory it had just read. The existing `allContainers` watcher prunes instead, and it runs on the first poll carrying a real list (which is every poll, since the root replaces `containers` wholesale).

**The Logs tab's multi-pane scroll sync** (`LogsView.js`/`LogViewer.js`): a `viewMode` toggle at the top of the side list picks between `'single'` (one pane; clicking a row swaps its container, clicking the open row closes it - `openIds` never exceeds length 1) and `'multi'` (clicking a row toggles it open/closed, `openIds` capped at `MAX_OPEN_LOG_PANES`) rather than always replacing a single selection, so up to four `<log-viewer embedded>` panes can render side by side. Switching `'multi'` → `'single'` with more than one pane open collapses `openIds` down to the main pane if one was set, else whichever was opened most recently, and clears `disabledSyncIds`/`mainId`/`joinTsMsById` along with it - none of those apply to a lone pane. `setViewMode` is a no-op when nothing needs to collapse (0 or 1 panes open, or already in that mode). Each pane's `onScroll` emits `scroll-sync` with `{containerId, tsMs}` - the epoch-ms timestamp of whichever line is now at the top of its viewport - only when the _user_ scrolled it. **Every scroll the pane makes itself goes through `scrollWithoutBroadcast(fn)`**, which sets `_programmatic` and clears it a frame later, once the native scroll event it caused has fired and been ignored — one writer, one reader (`onScroll`), where there used to be three hand-rolled copies of the same set-then-rAF-clear. Without it a sync-driven scroll re-broadcasts and the panes ping-pong forever, and a live tail drags panes the user deliberately scrolled back into history. **`scrollToBottom({ broadcast })` is the one place the distinction is a judgement call rather than a mechanism**: pressing ▼ is the user navigating and should carry the siblings exactly as dragging the scrollbar down would, while the live tail and the catch-up after un-pausing are the pane's own bookkeeping and stay silent. Resuming used to broadcast — it was the one call site that bypassed the flag, which is exactly the kind of omission a single helper makes hard to repeat. `LogsView`'s `broadcastFrom` is the single place a sync event actually moves other panes: peer-to-peer by default (whoever scrolls drives the rest), but designating one pane `mainId` switches the group to leader-follower (only the main's scrolling drives anyone - `broadcastFrom`'s first check enforces this even though every pane's events keep arriving). `disabledSyncIds` lets a pane opt out entirely, in both directions (it doesn't broadcast and isn't moved). `toggleSync`/`setMain` broadcast the affected pane's _current_ position immediately when re-enabling sync or marking main, rather than waiting for its next scroll event - that's what lets you scroll a pane to a spot of interest while desynced, then have the rest jump to match it the moment you flip sync back on. `lastSyncTsMs` is kept so a pane opened after the group has already scrolled somewhere joins at that same timeframe instead of live-tailing at the bottom while its siblings look at history. `LogViewer`'s `embedded`/`multiPane`/`wrap` props split standalone mode (root overlay, `fullscreen` v-model, its own wrap toggle) from embedded mode (a `LogsView` pane: no fullscreen, `wrap` fed from one tab-level toggle instead of repeating it per pane) - `multiPane` is independent of `embedded` and only turns on once 2+ panes are open, since a single embedded pane has no close/sync/main controls to show (picking a different row is the close equivalent).

**The log panel header is two rows, and its breakpoints are measured rather than guessed.** The container name owns the top row alone — `white-space: nowrap` with an ellipsis and the full name on `title`, since compose-prefixed names run long and used to wrap to two lines in a side-by-side pane. Row two is the status badge pinned left with the control strip pushed right by `margin-left: auto`. The badge is **always present** and reads `▶ active` / `⏸ paused` / `⏸ suspended` from one `statusBadge` computed: "active" is only legible as a state because it sits exactly where "paused" would, so a streaming pane says so rather than saying nothing. Manual pause outranks suspension, because if the user paused it that's the answer to "why isn't this moving". Three `@container log-panel` tiers, each set from a measured natural width (the strip needs 993px in a multi-pane header and 1140px in a standalone one, which also carries Matches/Fullscreen/Wrap/Close): **≤1150px** drops the button labels and narrows the search box to 150px — this is the one that matters, since two panes on a 1080p screen land at ~985px each and were wrapping; **≤900px** swaps the four level buttons for the `☰ Levels` dropdown, for the 2×2 grid at ~865px; **≤760px** finally collapses the search box to an icon that expands on focus. That last one is deliberately still 760 rather than folded into the tier above — between 760 and 900 the level dropdown alone buys back enough, and seeing what you filtered on is worth more than the 120px. Below ~800px it does wrap to two control rows; that's accepted degradation, not a target. Re-measure rather than eyeball if controls are added: one more button moves every boundary.

**Pause and the match strip (`LogViewer.js`).** Space toggles a manual pause on the log body. It deliberately does **not** stop the stream: the EventSource stays connected and incoming lines go into a non-reactive `_pendingLines` buffer capped at the same `MAX_LOG_LINES`, so resuming shows what actually arrived instead of paying for a reconnect and a re-tail (and a container left paused for an hour can't grow the buffer without bound). The keydown listener is on `document`, so it's live without the pane needing focus first — guarded against firing while typing (`INPUT`/`TEXTAREA`/`SELECT`/`BUTTON`/`contenteditable`), against any modifier, and with `preventDefault` so space doesn't also scroll the page. Every open pane carries that listener, so in multi-pane the **hovered** pane takes the keypress or one space would pause all four; a lone pane needs no hover. It's distinct from `suspended` (the background-tab connection handback) and badged differently, since "I paused this" and "the tab did" are different states — and `onReset` force-unpauses, because that path has just wiped the buffer and staying paused would leave an empty pane that never fills, which reads as broken rather than paused. **The match strip** is a filtered-results pane, the long-standing log-viewer pattern of listing the hits separately and clicking one to jump to it: `matchLines` (which already exists for the hits counter) rendered as a short scrollable list under the log body, each row clicking through to `selectMatch` — the same reveal-in-context path clicking a hit line in the body takes. Single-pane only (`matchPaneVisible` is `showMatchPane && !multiPane`): a quarter-width cell in the 4-up grid has no vertical room to give up. **While it's open the log body stops narrowing to matches** — `showAllLines` is `revealAll || matchPaneVisible`, so the strip makes reveal-mode the default rather than something you get only after clicking a hit. Filtering both would be redundant, and worse than redundant: the strip's whole purpose is jumping into surrounding context, which a filtered body doesn't have. The level toggles still apply — those aren't search. Rows never wrap, since a wrapped row would eat two or three of the handful the strip shows at once. The standalone pane sizes its body against the viewport, so `.has-match-pane` takes the strip's height back out of that calc; the embedded pane is already a flex column and needs no such adjustment. **The strip is its own component, `LogMatchPane.js`**, registered locally by `LogViewer` the way `SettingsPanel` registers its five tabs. It owns the drag entirely; `LogViewer` keeps exactly two things, and both for a reason. The **height** stays in the parent as a `v-model:height` because the list sits behind two `v-if`s — the pane toggle, then `searchActive` — so a height held in the child would be lost the moment either one closes, which is the same reason it was never an inline style the drag wrote directly. And the **cap** stays in the parent as a `maxHeightFor(paneHeight)` **function prop**, not a number: the strip may take whatever the log body can spare above `MIN_LOG_BODY_PX`, only `LogViewer` can measure the body, and `offsetHeight` is not reactive — so the cap has to be read at the moment of the drag rather than passed at render time. The child watches its own `activeId` prop to keep the highlighted row on screen, rather than the parent reaching in, which is what let `LogViewer`'s `activeHitId` watcher disappear entirely. **The strip resizes by dragging its own header bar (`.log-match-pane-header`), deliberately not by `resize: vertical`.** The native handle is wrong here in three separate ways, worth keeping written down because it is the obvious thing to reach for again: it lives on the bottom-right corner, which on a pane anchored to the _bottom_ of the panel is diagonally opposite the only edge that moves; dragging it down grows the strip downward off the end of a fixed-height panel rather than into the log; and it is invisible until stumbled upon. A dedicated hairline grip was the first replacement and was still a thing to hunt for — the header is better because it already exists, already _is_ the boundary between log and strip, and is a full-width 34px bar you can grab without aiming. A centred `::after` pill brightens on hover/focus (a bare `cursor: ns-resize` is only discoverable by sweeping the mouse across it), and `tabindex="0"` plus ↑/↓ handling resizes it without a pointer at all. **`startMatchResize` bails on `ev.target.closest('button')`**: the ✕ lives inside the handle, and without that guard pressing it starts a zero-distance drag whose `preventDefault` eats the click. **The drag maths inverts the delta** (`startH - (e.clientY - startY)`), because the handle is the top edge and dragging up has to make it taller. Listeners go on `window`, not the handle: a fast drag outruns the element under the cursor, and the pointer routinely ends up over the log body or outside the panel entirely. **The bound is measured, not declared** — `matchMaxHeight()` is the current height plus whatever the log body can give up above `MIN_LOG_BODY_PX`, read live off `logView.offsetHeight`. CSS can't express that: the log body is `flex: 1; min-height: 0` in both flex-column panels and so yields all the way to zero, and the panel's own height differs by mode (fullscreen is a viewport calc, embedded is measured by `LogsView.updateWrapHeight`), so a px cap eats the whole log on a short window while a `vh` cap can only ever be right for one of the two modes. The height itself lives in `LogViewer.js`'s `matchListHeight` rather than as an inline style the drag writes directly, because the element sits behind two `v-if`s (the pane toggle, then `searchActive`) and would otherwise lose it the moment the strip is hidden or the filter cleared.

**Live updates arrive over Server-Sent Events**, not WebSockets — `LogViewer`, `ContainerDetail`'s log preview, and `ActivityView`'s event stream all consume their respective route (`GET /api/hosts/:id/containers/:id/logs`, `GET /api/hosts/:id/events/stream`) with a plain `EventSource`. See `server/CLAUDE.md` for the server side (`eventWatcher`'s `Broadcaster` in `server/sse.js`).

**Chart colors** are the four `--seq-*`/`--accent` custom properties in `style.css`, validated as a categorical set (lightness band, chroma, contrast, and colorblind separation on every pair) against the tile surface rather than picked by eye - the header comment above them records what passed and what failed, including the obvious purple that turns out to be indistinguishable from `--accent` for deutan viewers. Re-validate rather than eyeball if they ever change; the `dataviz` skill carries the validator.
